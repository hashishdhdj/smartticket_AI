### 2. 关键技术判断

1. **`TicketVO` 必须补 `@JsonCreator` 才能从缓存还原**。它的字段全为 `final`、无 setter、构造器私有，Jackson 无法用常规方式实例化，直接 `readValue` 会抛 `InvalidDefinitionException`。这是一个"写完不测就必炸"的坑，因此补了一个 12 参数的、显式标注 `@JsonProperty` 的构造器，与原有「实体 → 出参」构造器并列。
2. **缓存 `TicketVO` 而非 `Ticket` 实体**。后者是 `@Data`、Jackson 开箱可反序列化，看似更省事；但缓存内容应等于"接口需要的数据"，缓存 VO 才能避免把 `deleted` 这类内部字段写进 Redis。已有用例断言缓存 JSON 不含 `deleted`。
3. **删缓存范围补上 `assign`**（清单遗漏）。指派同时改 `status` 与 `assignee_id`，不删就是 10 分钟的脏读。这是第5天「允许重开」决策的连带影响：凡改动工单数据的写路径都要覆盖。
4. **顺序固定为「先改库，后删缓存」**。反序的话，改库失败会留下"缓存已删、数据未变"的无谓失效。
5. **读路径的异常处理不对称，这是刻意的**：反序列化失败（缓存内容不可信，如被人为改动、VO 结构升级）→ 记 WARN、删除坏 key、继续回源，**不让缓存故障影响查询**；序列化失败（自身对象结构有问题）→ 直接抛 `SYSTEM_ERROR`，因为这是代码缺陷，不该被静默吞掉。
6. **`timeout: 3s` 的第二个用途**：第8天设它是为了守护配置前缀，本次实测证明它也限制了 Redis 不可达时的阻塞时长（失败用例在 1~2 秒内就报错，而不是长时间挂住）。

**核心用例的证明手法**（`secondQueryIsServedFromCache`，不依赖日志、可自动断言）：

1. 第一次 `getById` 建立缓存；
2. 用 `JdbcTemplate` **绕过 Service 直接改库**，title 由「旧标题」改为「新标题」；
3. 第二次 `getById` → 断言仍返回**「旧标题」**（证明这次没碰数据库）；
4. 删掉缓存 key 后再查 → 断言返回「新标题」（**双向反证**，排除"改库其实没生效"这一替代解释）。

只做第 3 步是不充分的：若改库语句本身失败，第 3 步同样会"通过"。第 4 步才是这条证据链的关键。

## 发现的问题

1. **缓存层故障会导致详情查询整体失败（无降级）——本次最有价值的发现**。回归过程中 Docker 引擎未启动，MySQL 与 Redis 同时不可达，`getById` 在第一步读缓存时就抛 `RedisConnectionFailureException`，没有任何机会回源数据库。理想行为应是"缓存不可用则直接查库"。已在决策记录中登记为遗留问题，未擅自实现（属可用性加固，超出最小骨架范围）。
2. **Docker 环境第 4 次中断**：本次是 Docker Desktop 引擎未启动（前三次分别在第3、5、6天）。已通过 `Start-Process` 拉起引擎 + `docker compose up -d` 恢复。该问题重复出现，建议开启 Docker Desktop 开机自启。
3. **指导清单第9天漏了「指派删缓存」**：清单只写「更新删缓存、关闭删缓存」，但指派同样改工单数据。已在第四节补充说明并实现。
4. **同批文件编辑中 import 行未落盘（第 2 次遇到）**：`TicketServiceImpl` 与 `TicketApiTest` 的 Redis import 各失败一次，工具返回成功但文件内无该行，导致两轮编译失败。应对方式：批量编辑后用 grep 一次性复核所有新增符号（本日复核 19 处符号）。这与第7天记录的同类问题是同一现象。
5. **第7天验收单仍待签署**（延续遗留）。

## 面试价值

1. **Cache-Aside 的完整闭环**：读回填、写删除、TTL 兜底、防穿透，四个点都有代码与测试对应。
2. **"断言必须能失败"的第二次实践**：`secondQueryIsServedFromCache` 的双向反证，与第7天修掉的 JsonPath 假通过是同一思维模式——先问"这个断言在实现错误时会通过吗？"
3. **识别出序列化的隐藏依赖**：`StringRedisTemplate` + 手工 JSON 看似比 `RedisTemplate<String,Object>` 麻烦，但它避开了"Jackson 反序列化不可变 VO"和"LocalDateTime 需要 JavaTimeModule"两个坑。第8天做模板选型时的判断，在第9天得到了验证。
