## AI输出摘要

### 1. 交底要点（执行前）

- **定位**：第4天是"接口契约层"，不碰数据库；`Result` 是所有接口的统一外形，`GlobalExceptionHandler` 是统一兜底。
- **与第3天的关系**：第3天解决"怎么读写数据库"，第4天解决"失败怎么对外表达"；第6天每个接口都会用到今天的两个类。
- **风险判断**：代码量小，但**约定风险高**——码值、HTTP 状态、分段规则一旦定错，第6~7天要全面返工，因此先决策再动手。

### 2. 产出（4 个主类）

| 文件 | 内容 |
|---|---|
| `enums/ErrorCode.java` | 5 个码：`SUCCESS(0)`、`BUSINESS_ERROR(10000)`、`PARAM_INVALID(40000)`、`REQUEST_BODY_UNREADABLE(40001)`、`SYSTEM_ERROR(50000)` |
| `common/Result.java` | 三字段全 final + 私有构造 + 4 个静态工厂（`success()`/`success(data)`/`fail(ErrorCode)`/`fail(ErrorCode, message)`） |
| `exception/BusinessException.java` | 继承 `RuntimeException`，携带 `ErrorCode` |
| `exception/GlobalExceptionHandler.java` | 处理 5 类异常：业务异常、`BindException`（含 `@Valid`）、`ConstraintViolationException`、`HttpMessageNotReadableException`、`Exception` 兜底 |

### 3. 关键技术判断（有据可查，非凭记忆）

用 `javap` 核实 Spring 6.1.21 的类型关系：

```text
public class MethodArgumentNotValidException extends org.springframework.validation.BindException
```

因此 `@RequestBody @Valid` 与表单绑定**共用一个 `BindException` 处理器**，省掉一份重复代码。

另外为"不泄露内部细节"这条验收标准，测试里主动在异常中塞入连接串，再用 `not(containsString(...))` 断言其**没有**出现在响应里——让要求被测试守住，而不是靠人自觉。

## 采纳情况

| 内容 | 是否采纳 | 原因 |
|---|---|---|
| 成功码用 0 | 是（用户决策） | 与 HTTP 状态码解耦 |
| 业务异常返回 HTTP 200 | 是（用户决策） | 前端只处理一种 HTTP 状态；4xx 噪声不淹网关日志 |
| 三段式错误码 | 是（用户决策） | 段位语义清晰，后续扩展不冲突 |
| 测试目录内的 Controller + MockMvc 验证 | 是（用户决策） | 生产代码零多余接口，验证可重复且不依赖 Docker |
| `Result` 不用 `@Data` | 是 | 避免 setter 让返回体可变、可被拼出非法组合 |
| 只放通用错误码、不预埋工单业务码 | 是 | 业务码在第6天按需定义，避免提前定义再改 |
| 一个 `BindException` 处理器覆盖两种校验异常 | 是 | javap 核实继承关系，去掉重复代码 |
| 用 `not(containsString(...))` 断言防信息泄露 | 是 | 让"不暴露堆栈"成为可执行的验收，而非口头约定 |
| 未处理 404 / 405 的统一返回 | 是（有意） | 阶段一指导未要求，需额外配置，不擅自扩大范围；已记录为已知边界 |
| 未修改 `default-property-inclusion: non_null` | 是 | 属第1天既定配置，是否改为 `always` 由用户决定，不擅自改契约 |

## 发现的问题

1. **`@WebMvcTest` 与启动类上的 `@MapperScan` 冲突（本次最有价值的坑）。**
   首次跑测试 5 个用例全部 ERROR：

   ```text
   Error creating bean with name 'ticketLogMapper': Property 'sqlSessionFactory' or 'sqlSessionTemplate' are required
   ```

   原因：Web 切片只装配 Web 相关自动配置，**不含 MyBatis 的 `SqlSessionFactory`**；而 `@MapperScan` 写在启动类上，切片仍会注册 Mapper Bean，`MapperFactoryBean` 因拿不到 SqlSessionFactory 而初始化失败。
   修法：切片测试中用 `@MockBean` 顶掉两个 Mapper。
   **教训**：切片测试切掉的不只是自动配置，还包括你可能依赖的 Bean；被切掉的依赖必须在测试里显式替换。

2. **统一返回体有两个已知边界（已如实披露，未擅自扩大范围）。**
   - 404（路径不存在）/ 405（方法不支持）仍返回 Spring 默认错误 JSON，不走 `Result`；需 `spring.mvc.throw-exception-if-no-handler-found` 等配置才能统一。
   - `data` 为 null 时该字段被省略（受第1天 `default-property-inclusion: non_null` 影响），因此失败响应只有 `code`、`message` 两个字段。

3. **`surefire` 默认不把测试中的 `print()` 输出落盘。**
   想留存响应报文作为证据时，默认只在控制台可见；需要显式配置（`redirectTestOutputToFile`）或用其他方式抓取。这提醒"验证证据"要提前设计留存方式，否则事后取证成本高。

4. **日期跨天，文档命名需按实际日期。**
   第3天的验证发生在 2026-09-16，第4天在 2026-09-17；日志命名以实际执行日期为准，避免多天工作挤在同一份记录里。

## 面试价值

- 是否可作为踩坑案例：**是**
  1. `@WebMvcTest` 切片的边界——切掉自动配置导致 `@MapperScan` 注册的 Mapper 因缺 `SqlSessionFactory` 启动失败；
  2. 用 `javap` 核实框架类的继承关系，避免写重复的异常处理器，而不是凭印象写代码；
  3. "不暴露堆栈"用 `not(containsString(...))` 断言固化，把安全要求变成可执行测试。
- 是否可作为技术决策案例：**是**
  1. 成功码用 0 而非 200（业务码与传输层解耦）的取舍；
  2. 业务异常返回 HTTP 200 的理由与代价（前端简单 vs 不够 RESTful）；
  3. 错误码三段式分段的设计动机（可扩展、语义清晰、不复用数值）。
