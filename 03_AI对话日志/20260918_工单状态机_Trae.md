### 3. 关键技术判断

- **白名单不能用枚举常量的构造参数声明**：Java 不允许在枚举常量构造参数里引用其它枚举常量（`illegal forward reference`），必须用静态块构建。
- **期望矩阵在测试里独立写一份**：不复用实现中的集合，否则"用实现测实现"，实现写错时测试跟着错。
- **穷举 + 计数断言**：遍历 36 种组合逐条比对，最后断言合法边恰好 14 条，任何一条边被误加/误删都会立刻失败。

## 发现的问题

1. **`unmodifiableMap` 挡不住内层集合被修改（本次最有价值的缺陷）。**
   首次跑测试 2 个用例失败，且互为因果：

   ```text
   ① allowedNextStatusesIsUnmodifiable → 期望抛 UnsupportedOperationException，但没抛
      → 原因：只对 Map 做 unmodifiableMap，内层 EnumSet 仍可变
      → 后果：该用例真的往共享集合 add 成功
   ② illegalTransitionThrowsBusinessException → 期望抛业务异常，但没抛
      → 原因：① 把「待分配 → 已解决」变成了"合法"（跨用例状态污染）
   ```

   修法：内层改为 `Set.of(...)`（构造即不可变）。
   **教训**：`Collections.unmodifiableXxx` 只做浅层保护，嵌套结构必须逐层不可变，否则"看起来只读"的集合仍可被篡改。

2. **枚举允许两个常量取相同码值，编译器不报错。**
   `ErrorCode` 中出现 `10001`、`10002` 各两次（其一是用户手动预加、其一是本次插入），编译与运行都不报错。已合并去重，并新增 `ErrorCodeTest` 在构建期拦截重复码值与越界码值。

3. **Docker 引擎未启动导致全量测试失败（第 3 次遇到）。**
   `TicketMapperTest` 报 `Connection refused`；拉起 Docker Desktop 后恢复。已建议开启开机自启。

4. **日期跨天**：第5天的实现与验证发生在 2026-09-18，文档命名以实际执行日期为准。

## 面试价值

- 是否可作为踩坑案例：**是**
  1. `Collections.unmodifiableMap` 的浅层保护陷阱，以及由此引发的**跨用例状态污染**（一个用例的失败暴露了另一个无关用例的问题）；
  2. 用"穷举 + 计数断言"验证状态机，而不是挑几个用例抽样；
  3. 枚举允许重复码值而编译器不报错，需要守护测试兜底。
- 是否可作为技术决策案例：**是**
  1. 状态机规则放在枚举内部、对外只留唯一校验入口（而非散落 if-else）；
  2. 「已关闭可重开」这一业务决策对缓存一致性的连带影响（第9天必须处理）；
  3. 用应用层状态机而非 DB CHECK 约束保证状态合法性的取舍。
