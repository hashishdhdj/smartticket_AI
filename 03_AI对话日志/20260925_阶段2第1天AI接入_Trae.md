## AI输出摘要

### 1 前置升级：Spring Boot 3.3.13 → 3.5.14

Spring AI 1.x 官方兼容矩阵是 Spring Boot 3.4.x / 3.5.x（1.x 基于 Spring Framework 6.2）。留在 3.3.13 只有两个选择：用 1.0.0-Mx 里程碑版（已停止维护），或自研 HTTP 客户端（等于放弃章程指定的「集成 Spring AI」任务）。故选择升版。

连带自动提升的依赖：`mysql-connector-j` 8.3.0 → 9.7.0、`lombok` 1.18.38 → 1.18.46、`spring-data-redis` → 3.5.11、`lettuce-core` → 6.6.0。已用实际依赖树核对并记入依赖清单。

### 2 依赖引入

| 项 | 值 |
|---|---|
| BOM | `org.springframework.ai:spring-ai-bom:1.1.6` |
| 模块 | `org.springframework.ai:spring-ai-starter-model-openai:1.1.6` |

选 OpenAI **兼容协议** starter 而非某家厂商专用 starter：DeepSeek、通义千问、Moonshot、本地 vLLM 都实现 `/v1/chat/completions`，换厂商只改 `base-url` + `model` 两行。

### 3 模型配置（`application.yml`）

```yaml
spring:
  ai:
    openai:
      base-url: ${AI_BASE_URL:https://api.deepseek.com}
      api-key: ${AI_API_KEY:not-configured}     # 占位值，见下
      chat:
        options:
          model: ${AI_MODEL:deepseek-chat}
          temperature: 0.2
    retry:
      max-attempts: 1                            # 关掉 Spring AI 默认的 10 次
  http:
    client:
      connect-timeout: 3s
      read-timeout: 20s
smartticket:
  ai:
    enabled: true
```

**占位值为什么不是空串**：Spring AI 装配 `OpenAiApi` 时用 `Assert.hasText` 校验密钥，留空会让**应用直接启动失败**。这一条是读框架字节码（`OpenAIAutoConfigurationUtil`）确认的，不是猜的。

**重试为什么必须关**：Spring AI 默认 `max-attempts=10`、初始退避 2s、倍数 5，即 2s → 10s → 50s…。一次模型故障就足以占住 Web 线程数分钟，与 DEF-002 是同一类故障放大。

**HTTP 超时为什么设在这里能生效**：读 `OpenAiChatAutoConfiguration` 字节码确认，它装配 `OpenAiApi` 时通过 `ObjectProvider<RestClient.Builder>` 注入容器里的 builder，因此 Spring Boot 的 `spring.http.client.*` 对它生效。

### 4 代码

新增 `com.smartticket.ai` 包（AI 相关类型不与阶段1 的 `service` / `vo` 混放）：

| 文件 | 职责 |
|---|---|
| `ai/AiCallResult.java` | record；一次调用的快照（success / content / errorCode / failureDetail / costMs / model） |
| `ai/AiChatService.java` | 接口；契约三条：不抛异常、不发无用请求、可观测 |
| `ai/impl/AiChatServiceImpl.java` | 薄封装 Spring AI `ChatClient`；构造期装配，启动即知道通道是否可用 |
| `enums/ErrorCode.java` | 新增 `AI_NOT_CONFIGURED(10006)` / `AI_CALL_FAILED(10007)` |

**核心设计**：把「降级」做成返回值形状而不是 try/catch 要求。上层拿到的永远是 `AiCallResult`，因此章程验收标准里的「AI 失败时不会导致工单创建失败」在结构上不可能被违反——而不是靠"每个调用点记得写 try"。

### 5 测试（新增 14 个用例）

| 测试类 | 数量 | 验证层次 |
|---|---|---|
| `AiChatServiceImplTest` | 7 | 纯单元，Stub `ChatModel`；4 条不可用路径 + 成功 + 超时 + 空返回 |
| `AiConfigurationTest` | 4 | 真实 Spring 上下文：`ChatClient.Builder` 存在、yml 配置真的绑定、`RetryTemplate` 真的只跑 1 次、占位密钥下应用照常启动 |
| `AiOpenAiProtocolTest` | 3 | **真实 HTTP 往返**：JDK 内置 `HttpServer` 冒充 OpenAI 兼容厂商 |

其中第三类是本期的关键补位：它让「base-url 是否拼成 `/v1/chat/completions`」「model 与 temperature 有没有写进请求体」「厂商返回 500 会不会被吃掉」变成可自动运行的断言，**不需要 API Key、不产生费用、离线可跑**。

## 追加：真实密钥配置与真实厂商调用验证（同日续）

### 背景

用户配置了 DeepSeek 真实密钥。因为用户明确说过「之前泄漏过 API Key」，本次先加固防泄漏再谈配置，顺序刻意如此。

### 一、防泄漏三层 + 演练

| 层 | 机制 | 覆盖的场景 |
|---|---|---|
| 1 | `.gitignore` 收严为 `application-local.*` / `.env*` / `*.pem`、`*.key`、`*.p12`、`*.jks` | 改后缀绕过（`.yaml`、`.yml.bak`）、`.env.bak` 等变体 |
| 2 | `.git/hooks/pre-commit`（本地，不进版本控制） | ① `git add -f` 强推本地配置文件；② 暂存内容含真长度密钥特征（阈值 20 字符，测试占位符不误报；命中只回显前 6 位） |
| 3 | 人工约定 | 不把密钥粘贴进对话框——对话要归档到本目录并提交，粘贴即泄漏 |

演练证据（都是真跑出来的）：

```text
A 强制暂存 application-local.yml   -> 拦截，退出码 1
B 暂存含 39 位伪造密钥的文件        -> 拦截，退出码 1，回显脱敏为 sk-Zq7... (masked)
C 只有合法改动                     -> 放行，退出码 0，无误报
```

配置完成后的泄漏复查（全部通过）：文件仍被忽略（`.gitignore:27`）、未被追踪、未进暂存区、`git grep` 全仓库无 `sk-` 后接 20 位以上字符、工作区干净。

### 二、真实厂商调用验证

启动日志的「AI 通道就绪」只证明密钥非空，证明不了密钥有效、base-url 正确、模型名存在。因此新增 `AiRealVendorSmokeTest` 做一次真实调用：

```text

[真实调用] success  = true | cost = 908ms | errorCode = null
```

四件事一次性验证完：

| 验证项 | 若不成立的表现 |

### 三、冒烟测试为什么默认跳过

用 `@EnabledIfEnvironmentVariable(named = "AI_SMOKE", matches = "true")` 而不是 `-D` 系统属性：环境变量一定能传到 surefire fork 出的测试 JVM，系统属性是否传递取决于 surefire 配置，容易变成"看着开了其实没开"。

全量结果：**107 个用例，0 失败，1 跳过**（跳过的就是它）。
