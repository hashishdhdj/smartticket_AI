## 输入内容

用户在看完"整条链路讲解"后指出关键一点：

> 「这个过程都没有用上RAG啊：① 用户提交问题 … ⑦ 全程可追溯」

这是本次工作的起点——**用户的观察是对的**：三条业务线（工单主线 / AI 分析 / RAG）当时是**并联**的，
没有一处代码把它们串起来，RAG 是一间"上了锁但没装门"的房间。

随后用户做了 3 个决策：

1. **先做插入点 A**（提交前检索）——而不是 B（并进分析接口）或 C（创建时落库）
2. 章程要求的「返回相似问题」用**模型改写**成问句的形态
3. 「建议」与「相似问题」**并入同一次模型调用**（输出改为 JSON），而不是另开一次

## AI输出摘要

### 1. 先确认"章程本来是要用上的"

查了章程模块三（L266-277），原文明确写着"用户提交工单前，先进行知识库检索"。
所以这不是"要不要加"的问题，而是**已经排期但还没做的一环**。同时做了一份逐条对照表：

| 章程要求 | 现状 |
|---|---|
| 用户提交工单前先检索 | ❌ 未接（RAG 无 HTTP 入口） |
| 返回相似问题 | ⚠️ 半成品（只能返回"来源小节"，不是"相似问题"形态） |
| 返回推荐解决方案 | ✅ 引擎能生成，但**没接到任何接口** |
| 处理人回复时推荐 | ❌ 未接 |
| 低置信度强制走人工 | ⚠️ 引擎有 `needHuman`，工单侧没有落点 |

### 2. 为什么先做插入点 A

- **它是章程的原话**，最能体现"用知识库把工单挡在前面"的产品意图
- **不改表、不改任何现有代码**——只在既有引擎外加上一层接口，风险最低
- **C 现在做不了**：AI 调用 1~2 秒，塞进 `create()` 的 `@Transactional` 会长时间占住数据库连接，
  正是 `connection-timeout=5000` 想防的那类故障。正确形态是"先落库返回、再后置补写"，而**异步是模块四**的事

### 3. 交付物

| 分类 | 文件 |
|---|---|
| 接口 | `controller/KnowledgeController`（`POST /api/ai/knowledge/answer`）、`dto/KnowledgeQueryDTO`、`vo/KnowledgeAnswerVO` |
| 解析 | `rag/RagAnswerParser` + `rag/RagAnswerPayload`（结构化输出的执法点） |
| Prompt | `rag-answer-v1` → **`v2`**：输出改为 JSON `{suggestion, similarQuestions[]}` |
| 调整 | `RagAnswer` 增加 `similarQuestions` 与 `costMs`；`RagAnswerServiceImpl` 改为解析结构化输出 |
| 测试 | `RagAnswerParserTest`(14) + `KnowledgeControllerTest`(6) 新增；`RagAnswerServiceImplTest`(10→11) 与 `RagAnswerPromptFactoryTest` 更新 |

### 4. 一处刻意的"不一致"

`KnowledgeAnswerVO` **不**像 `TicketAnalysisVO` 那样带降级原因码。理由写进了 VO 的类注释：
对"提交前检索"来说，调用方对**"没查到知识"与"检索降级"的处置完全相同**（都引导提单），
既然调用方不区分，透出原因码只会多一个没人用的字段。降级细节写日志，`degradedSources` 保留"哪条路挂了"。

### 5. 解析器校验到哪一层为止

沿用 `AiClassificationParser` 的严格风格（一个字段不合规就整份作废），但**只校验结构与长度，不校验措辞与语义**：

| 校验 | 不校验 |
|---|---|
| 是否合法 JSON、字段齐不齐、是否多字段 | 问句是否以问号结尾（外观） |
| 建议 ≤200 字、相似问题 1~5 条且 ≤40 字 | 这条问句是否**真的出自资料**（需语义判断，正是模型在做的事） |

**这条界线必须写明**，否则会误以为解析器能挡住一切跑偏——本次实测它确实没挡住一类跑偏（见"发现问题"第 2 条）。

## 采纳情况

全部采纳：接口、DTO/VO、解析器、Prompt v2、测试、文档。

**未采纳但记录在案的**：

- **另开一次模型调用改写相似问题**：保住原 Prompt、失败隔离，但用户在提单页等着，
  多一次往返的延迟与计费不划算；改成并入同一次调用
- **为 RAG 输出再建一个 JSON Schema 文件**（分类那套有一个）：边界已写在模板（对模型）与解析器常量（对代码）两处，
  再加第三个文件就是同一份契约的第三份拷贝，违背本项目"不接受多份真值"的原则
- **给 VO 加降级原因码**：调用方不区分，属过度设计
- **先做插入点 C（创建时落库）**：依赖模块四的异步，硬做会引入已知会坏的形态
- **把相似问题改成"与资料一一对应"并校验条数**：能迫使模型逐条对着资料写，但资料只有 1 条时展示会单薄。
  取舍留到有真实用户反馈后再定，**现在不提前优化**

## 发现问题

| 序号 | 问题 | 处理 |
|---|---|---|
| 1 | **Docker 引擎没启动**导致首次真实验证失败：两条检索路都因 `CannotGetJdbcConnectionException` 降级 | 不是代码问题。日志里两条路各等 3003ms（= 配置的 `connection-timeout-ms: 3000`）说明是连不上库。**测试断言如实失败而没有静默通过**，这一点是对的——按约定由用户拉起 Docker 后重跑通过 |
| 2 | **相似问题会"顺着主题发散"**：实测 4 条里有 2 条（"退款到账需要多长时间？""支付渠道账号已注销还能退款吗？"）在知识库中查不到对应内容 | 如实登记为局限；解析器只能校验结构，**无法校验语义是否出自资料**。给出候选改进（改成与资料一一对应 + 服务层校验条数），但**不现在实施**——留到有真实用户反馈后再定 |
| 3 | **新接口会真实调用模型并计费，但项目没有任何鉴权与限流** | 章程明确"不要实现复杂权限"，所以不是遗漏是范围；但"没有权限的接口"与"没有权限且会花钱的接口"是两件事——后者可被用来刷账单。已登记为**上线前必须补**的遗留项 |
