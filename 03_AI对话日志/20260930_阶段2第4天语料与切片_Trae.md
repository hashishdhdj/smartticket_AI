### 2. 关键设计决策

| 决策 | 选择 | 关键理由 |
|---|---|---|
| 语料从哪来 | 自造**演示语料**并在三处显式声明 | 本项目没有真实 FAQ/工单数据；不造语料则第4~5周的切分、检索、评估全都无从谈起。但把构造内容当真实数据陈述是事实性错误，必须标注 |
| 切分边界 | Markdown 的 `##` 二级标题 | 中文无空格分词，固定字符滑窗会把句子劈成两半，"前半句"和"后半句"各自都检索不到完整语义；`##` 是天然的语义边界 |
| 长度上限 | 500 字符 | 依据实测语料规模（FAQ 150~350 字、工单 250~450 字），让绝大多数小节**整节一个切片**——切不开就不会丢语义 |
| 重叠 | 80 字符，且从**完整句子**开始 | 按字符截尾会得到从半句开始的片段，既不通顺也可能因截断改变原意 |
| 重叠范围 | 只在同节内 | 跨节重叠会把不相关内容粘在一起，**制造出本来不存在的语义关联** |
| 扫描范围 | 白名单 `faq/` + `tickets/`，不递归整个 `knowledge/` | 否则根目录的 `README.md` 会被当成知识检索出来。用目录边界而非"文件名排除列表"——后者要维护 |
| 扫描顺序 | 按文件路径排序 | `classpath*:` 返回顺序不作保证；不排序则切片顺序会漂移，"可复现"无从谈起，第5周灌向量库时会得到不同的行 |

完整理由与代价见决策记录 `20260930_RAG语料与切片策略.md`（10 节，含 7 项已知限制）。

## 发现问题

| 序号 | 问题 | 处理 |
|---|---|---|
| 1 | 切片长度上界定义为 580（500+80），实测却是 **581** | **off-by-one**：重叠正文与后一块之间还要插一个换行，重叠预算没把拼接符算进去。修复：`overlapOf` 内 `int budget = OVERLAP_CHARS - 1`。**教训：上限必须连同拼接开销一起核算**——凡是在长度预算之外还要加分隔符的地方都有同类偏差，且这类偏差不报错，只会让边界断言失败 |
| 2 | `DOC_TITLE` 预扫描取不到文档标题 | 正则缺 `(?m)`：不带多行标志时 `^` 只匹配整段文本开头，除"标题恰好在第一行"外一律失效。同时把 `\s` 换成 `[^\n]`，避免把换行吃掉而匹配到别的行 |
| 3 | `overlapOf` 的注释与实现自相矛盾 | 注释写"宁可重叠短也要从完整句开始"，代码却在找不到边界时返回半句。改为从句首向后扫取**范围内最长的合法重叠**，找不到才退化为按字符截尾 |
| 4 | `KnowledgeCorpusLoader` 曾设计 `countFiles()` 重复扫描目录，且日志里调用两次 | 冗余设计，删掉；改为循环内 `fileCount++` |
| 5 | 新终端里 `mvn` 未识别 | 每个 RunCommand 都是新 shell，上一轮设置的 `JAVA_HOME` / `PATH` 不保留。须在同一命令内先设环境变量再执行 mvn（README 的"手工启动"三步也是这个原因） |
| 6 | 全量回归输出中文乱码（`ģ��ģ�ͳ�������`） | 控制台代码页为 GBK 而日志是 UTF-8，属显示层问题，不影响测试结果。**脚本自身输出仍须只用 ASCII**（既有约定） |

## 验证证据

**语料规模（实测，由 `KnowledgeCorpusLoaderTest` 打印）**

```text
[知识库规模] 切片总数=26 | FAQ 切片=17 | 历史工单切片=9 | 涉及文档数=7
[INFO] KnowledgeCorpusLoader -- 知识库语料加载完成 | 文件数=7 | 切片数=26 | 平均每份文件切片数=3.7142857142857144
```

**交叉核对**：7 份文件的 `##` 小节数恰好也是 **26**（FAQ 5+4+4+4 = 17，工单 3+3+3 = 9）。
切片数 == 小节数，说明**没有任何小节触发退化切分**——500 这个上限对当前语料是"不切开"的，
即上限取值与语料规模是相匹配的。这条核对是"参数取值是否合理"的直接证据，而非主观判断。

**全量回归**

```text
[INFO] Tests run:  14, Failures: 0, Errors: 0 -- KnowledgeChunkerTest（新增）
[INFO] Tests run:   6, Failures: 0, Errors: 0 -- KnowledgeCorpusLoaderTest（新增）
[INFO] Tests run: 172, Failures: 0, Errors: 0, Skipped: 2
[INFO] BUILD SUCCESS
```

Skipped 的 2 个是 `AiRealVendorSmokeTest`（真实调用厂商，默认跳过）。
本次新增 20 个用例，测试总数 152 → **172**（与预期一致）。

**为什么切分要测到 14 条**：切分是 RAG 里"错了很难发现"的一环——切坏了不会报错，
只会在检索时表现为"明明有这条知识却召不回来"。因此不测"能跑"，
而是把每条规则钉死：按什么切、在哪里不切、重叠从哪开始、元数据齐不齐。
