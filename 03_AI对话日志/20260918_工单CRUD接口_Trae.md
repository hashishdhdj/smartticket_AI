### 3. 关键技术判断

1. **分页必须注册 `PaginationInnerInterceptor`**：不注册时 `selectPage` 不生成 `LIMIT`，会把全表当"第一页"且 total 不准。第3天引入的 `mybatis-plus-jsqlparser` 正是该插件的依赖（3.5.9 起从主包拆出），今天才真正用上。
2. **PUT 采用全量替换语义，因此不能用 `updateById`**：MyBatis-Plus 默认跳过 null 字段，无法把 `description`/`tags` 置空；改用 `LambdaUpdateWrapper` 显式 `set` 每个字段。
3. **`insert` 不回填数据库默认值**：MyBatis-Plus 只回填主键，`created_at`/`updated_at` 由 DB 默认值生成，不回读就会返回 `createdAt=null`（实测缺陷，已修）。
4. **不直接返回 MyBatis-Plus 的 `Page`**：它会序列化 `orders`、`optimizeCountSql`、`searchCount` 等内部字段，既污染契约又随框架版本变化；改为只暴露 5 个字段的 `PageVO`。
5. **状态筛选复用状态机校验**：`TicketStatus.fromCode(status)` 使非法状态值返回 10002，而不是静默查空——第5天的成果在此处被真正调用。
6. **测试数据必须物理删除**：业务代码走逻辑删除（`@TableLogic`），`deleteById` 只置 `deleted=1`，会污染其他测试对"表为空"的断言；因此测试用 `JdbcTemplate` 直接 `DELETE`（`spring-boot-starter-jdbc` 由 MyBatis-Plus 传递引入，`JdbcTemplate` 已自动装配）。

## 发现的问题

1. **`insert` 后返回的 `createdAt` 为 null（真业务缺陷）。**
   `createTicketReturnsExpectedPayload` 断言 NPE，定位后发现 MyBatis-Plus 只回填主键，数据库默认值生成的时间戳不会被带回实体，又因 `default-property-inclusion: non_null` 被整个省略 —— 前端会拿到"没有创建时间"的工单。修法：创建后回读一次再返回，与 `update` 保持一致。

2. **过滤型 JsonPath 断言会"假通过"。**
   `jsonPath("$.data.records[?(@.title=='x')]").exists()` 在结果为空时**也会通过**（路径求值为空数组而非 null），无法证明筛选真的生效。改用 `records[*].title` + Hamcrest 的 `hasItem / not(hasItem) / everyItem`，并额外**直插一条 `CLOSED` 数据**做双向验证（包含/不包含都断言），才能证明筛选没有被忽略。

3. **`JsonNode.get("缺失字段")` 返回 Java null，不是 `MissingNode`。**
   `MissingNode` 只用于 JSON 里显式为 `null` 的场合，字段缺失时 `get` 直接返回 null，调用 `.isMissingNode()` 会 NPE。改用 `has(...)` 判断字段是否存在。

4. **`Pattern` 导入歧义导致编译失败。**
   `jakarta.validation.constraints.Pattern` 与 `java.util.regex.Pattern` 同名，同时 import 会 "对Pattern的引用不明确"。改为只导入 regex 版，注解处使用全限定名。

5. **Docker 引擎未启动（第3次）**：集成测试依赖真实 MySQL，Docker 未启动时全部连接失败。

6. **已知边界（有意保留，未擅自扩大范围）**：
   - 更新接口不写操作日志（规格只要求创建时写）；
   - 日志查询不分页；
   - 接口返回英文状态码，不返回中文描述；
   - `data` 为 null 时字段被省略（受第1天配置影响）。

## 面试价值

- 是否可作为踩坑案例：**是**
  1. `insert` 不回填数据库默认值（时间戳）导致出参缺字段，且被 `non_null` 序列化配置进一步掩盖；
  2. MyBatis-Plus 默认跳过 null 字段，导致"支持清空字段"的更新语义必须改用 `UpdateWrapper`；
  3. 分页插件不注册时 `selectPage` 静默退化为全表查询；
  4. JsonPath `exists()` 的假通过问题，以及"直插对照数据做双向断言"的测试设计；
  5. `JsonNode` 的 null 与 `MissingNode` 的语义差异。
- 是否可作为技术决策案例：**是**
  1. PUT 全量替换语义的取舍（与 PATCH 的对比、必填字段的选择）；
  2. 不直接返回框架 `Page` 类型而封装 `PageVO` 的理由；
  3. 工单编号生成方案的选择（无额外表、可读、撞键重试 vs 雪花/UUID/回填自增）；
  4. 用应用层状态机校验筛选参数（非法值 10002 而非静默查空）。
