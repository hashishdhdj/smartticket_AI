### 2. 关键技术判断

1. **关闭 = 一次状态流转**，因此直接调用 `TicketStatus.checkTransitionTo(CLOSED)`：按第5天矩阵，只有「待分配」「已解决」可以直接关闭，「处理中 → 已关闭」会被拒绝——这是关闭接口真正的校验价值，也是「状态机校验生效」这条验收的落点。
2. **指派不是纯粹的状态流转**：待分配时指派 = 流转到处理中（走状态机）；其他状态指派 = 只换人（`from_status == to_status`）。因此不能无脑调用 `checkTransitionTo`（会命中"禁止自身流转"），需要先按当前状态判定是否流转。
3. **已关闭工单拒绝指派（10005）**：矩阵中 `CLOSED → PROCESSING` 是合法的，但那是"**重开**"语义。若允许指派，等于让指派接口隐式把工单重开，业务上不可接受，因此单独拒绝并给出明确提示（重开留作独立操作）。这是对用户决策「按状态决定是否流转」的合理细化，已记入遗留问题待产品确认。
4. **日志动作值使用表注释中既有的 `ASSIGN` / `CLOSE`**，`from_status`/`to_status` 直接取枚举名，便于审计回溯。
5. **`assign`/`close` 与日志写入同事务**（`@Transactional`），避免"状态变了但没日志"。
6. **`TicketCloseDTO` 不含目标状态**：目标固定为已关闭，不接受调用方指定，避免绕过状态机。

## 发现的问题

1. **同批编辑中有 2 处未持久化（工具层问题，非代码问题）。**
   一次批量修改中，`TicketServiceImpl` 的 import 与 `TicketService` 的两个方法声明虽然返回成功，但实际未写入文件，导致两次编译失败：

   ```text
   [ERROR] TicketServiceImpl.java:[151,37] 找不到符号 符号: 类 TicketAssignDTO
   [ERROR] TicketService.java … 方法不会覆盖或实现超类型的方法
   ```

   处理：重新落盘后编译通过。
   **教训**：批量编辑后不要只信工具回执，关键改动要用 grep 复核文件真实内容（本次正是靠 grep 一次性确认了全部 16 处符号都在位）。

2. **第 3 天的测试断言是"脆弱断言"。**
   `TicketMapperTest` 原先断言 `ticket 表当前应为空表`。第 7 天数据库里有了真实数据（人工验证产生的 2 条工单）后，该断言直接失败——**任何人用 Postman 建一条工单，构建就会挂**。
   处理：改为「查询能跑通」语义（计数非负），并注明失败条件（连接失败/表不存在/SQL 错误）。修正后在**数据库非空**状态下 51 个用例全绿。
   **教训**：断言"环境为空"这类外部状态的测试，会随业务演进必然失效；应断言行为而非环境。

3. **"无解决接口"导致的覆盖缺口（如实登记）。**
   `RESOLVED → CLOSED` 是矩阵中的合法边，但当前没有接口能让工单进入 `RESOLVED`，因此该用例只能通过 `JdbcTemplate` 直插数据来覆盖（`closeResolvedTicketSucceeds`）。这是阶段1 范围决定的，不是缺陷，但必须记录，避免后人误判为漏测。

4. **Postman 集合的两处结构性问题（已修）。**
   - 追加用例块时漏了 JSON 对象起始符，导致 JSON 非法（用 `ConvertFrom-Json` 校验时被发现）；
   - 关闭类用例需要第二个处于待分配状态的工单，因此把「1.2 创建工单」的响应 id 写入新变量 `{{closedId}}`，并补充集合变量声明。
   两处均已用 `ConvertFrom-Json` 复验：6 个分组、22 个请求、3 个变量。

5. **Docker 未启动的问题本轮未再出现**（引擎在本次会话中保持运行），但第3/5/6天已累计遇到 3 次。

## 面试价值

- 是否可作为踩坑案例：**是**
  1. "断言环境为空"的脆弱测试如何在业务演进后必然失效，以及"断言行为而非环境"的修正思路；
  2. 状态机的第一个真实调用方会暴露设计细节问题：「关闭」是纯流转（可直接校验），而「指派」不是（需先判断是否流转），二者不能用同一套调用方式；
  3. 已关闭工单的指派 = 隐式重开，属于典型的"接口职责越界"陷阱；
  4. 批量编辑后靠 grep 复核落盘状态，而非轻信工具回执。
- 是否可作为技术决策案例：**是**
  1. 指派语义的两种设计（仅待分配可指派 vs 按状态决定是否流转）及其对接口数量的影响（后者省掉"转派接口"）；
  2. 关闭接口直接复用状态机校验，使"状态机校验生效"成为可执行验收而非口头约定；
  3. 用 10005 区分"非法流转"（10001）与"状态不允许该操作"，让前端能区分处理；
  4. 第1周验收单逐项挂实测证据（命令+输出），把"验收"从勾选清单变成可复现的证物链。
