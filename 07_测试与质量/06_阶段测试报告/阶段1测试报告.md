### 3.2 测试过程中的缺陷自省

本阶段共发现 **4 个"测试自身"的问题**，均已修复。它们的共同点是：**用例"通过"了，但什么都没验证**。

| # | 问题 | 性质 | 修复 |
|---|---|---|---|
| 1 | JsonPath 过滤断言 `[?(@.title=='x')].exists()`，结果为空也通过 | 假通过 | 改用 `records[*].title` + Hamcrest `hasItem/not(hasItem)` |
| 2 | `TicketMapperTest` 断言"表为空" | 脆弱断言：测的是环境状态而非代码行为，人工跑一次 Postman 就必然失败 | 改为"查询可跑通"（计数非负） |
| 3 | Redis healthcheck 用 `redis-cli ping`，密码错误也返回 `PONG` | 恒真 | 改用 `REDISCLI_AUTH` + `AUTH` 失败时退出码非 0，并用错误密码验证其**能失败** |
| 4 | `assertEquals("PROCESSING", ticket(...).getStatus())` 自己和自己比 | 无效断言 | 改为断言 `UpdateWrapper` 的参数，验证真的写入了预期值 |

## 四、边界测试结果（第13天）

### 4.1 指导清单逐条结果

| # | 边界场景 | 结果 | 证据 / 说明 |
|---|---|---|---|
| 1 | 创建工单缺少参数 | 通过 | `title` 空白、缺 `creatorId` 均返回 `40000` |
| 2 | 创建工单标题过长 | 通过 | **双向验证**：200 字符通过、201 字符返回 `40000`（本次新增） |
| 3 | 查询不存在的工单 | 通过 | `10003` |
| 4 | 更新不存在的工单 | 通过 | `10003`，且不执行更新 |
| 5 | 非法状态流转 | 通过 | `10001`（处理中 → 已关闭） |
| 6 | 重复关闭工单 | 通过 | `10001`（自身流转） |
| 7 | 指派给不存在的处理人 | **不符合预期** | 不校验处理人存在性 → 登记为 **DEF-005**（阶段1 无用户表，无从校验，标记"不适用"） |
| 8 | Redis 不可用时查询详情 | **发现缺陷并修复** | → **DEF-001**（高），修复后实测降级成功 |
| 9 | MySQL 不可用时创建工单 | **发现新缺陷** | 返回 `50000` 符合预期，但**耗时 30077ms** → **DEF-002**（中） |

**第 2 条为什么做双向验证**：只测"201 字符被拒绝"是不够的——如果 `@Size` 被误配成 `max=0`，连合法标题也会被拒绝，而"201 被拒绝"这条断言照样通过。加上"200 通过"这条，才算真正锁住了边界位置。

### 4.2 环境故障演练（真实停容器）

与单元测试里用 mock 模拟异常不同，本轮额外做了**真实容器停启**的演练，验证的是"真的把 Redis/MySQL 停掉时的行为"。

**演练一：Redis 不可用**

```text
① 创建: code=0 id=282 status=PENDING_ASSIGN
② 第一次查询(建立缓存): code=0 title=第13天边界-Redis故障演练
③ 停掉 Redis 容器
④ Redis 已停，再查详情: code=0 title=第13天边界-Redis故障演练 status=PENDING_ASSIGN
⑤ 恢复 Redis 容器
```

**结论**：修复生效。Redis 停止后查询降级为直接查库，接口保持可用。修复前此处的表现是 `50000`。

**演练二：MySQL 不可用**

```text
⑥ 停掉 MySQL 容器
⑦ MySQL 已停，创建工单: code=50000 message=系统繁忙，请稍后重试 耗时=30077ms
⑧ MySQL 已停，查 id=282 详情(Redis 缓存命中): code=0 title=第13天边界-Redis故障演练
⑨ 恢复 MySQL 容器
smartticket-mysql | Up 20 seconds (healthy)
smartticket-redis | Up About a minute (healthy)
```

**结论**：

- ⑦ 错误码 `50000` 符合设计（系统级故障对外不暴露细节），但**30 秒的响应耗时是缺陷** → DEF-002
- ⑧ 意外收获：MySQL 停止期间，**已缓存的详情查询依然成功**。这从反面印证缓存的真实价值——它不只是"查得快"，在数据库故障时确实能保住部分读能力

**演练后环境已还原**：两个容器恢复 healthy，演练数据（id=282 及对应缓存 key）已清理，库回到 0 行。

## 八、结论

1. **功能正确性**：82 个自动化用例全部通过；7 个接口的主流程、异常分支、边界值均被覆盖。
2. **边界健壮性**：指导清单 9 条边界中，7 条通过；1 条（Redis 不可用）暴露高严重度缺陷并已修复；1 条（MySQL 不可用）暴露响应耗时缺陷，已登记。
3. **测试有效性**：本轮修复了 4 个"测试自身"的假通过/脆弱断言问题。**一个不能失败的断言价值为零**，这一点在本阶段被反复验证。
4. **环境依赖**：集成测试占 51%，对 Docker 强依赖。本轮出现过一次因容器中断导致的 40 用例失败，排查耗时约 30 分钟——**区分"代码坏了"与"环境断了"应作为标准排查动作的第一步**（先 `docker version`，再看应用日志）。

**总体评价**：阶段1 的代码质量达到"最小骨架"目标，主要遗留问题集中在功能完整性与配置准确性，无阻塞性问题。建议按第七节的时机表逐项处理。
