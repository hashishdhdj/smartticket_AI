## 一、通用约定

### 1.1 统一返回格式

本节保留阶段1/2的HTTP200历史示例。当前版本必须同时检查HTTP状态与业务code；认证、权限、版本冲突和频控分支可返回401/403/409/429。现行调用以[阶段四角色与API契约](../02_接口测试/阶段四_角色矩阵与接口说明.md)为准，不能继续假设所有HTTP均为200。

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | `0` 表示成功；非 0 见 [1.4 错误码表](#14-全局错误码表) |
| `message` | string | 提示信息，成功时为 `"成功"` |
| `data` | object / array | 业务数据；**失败时该字段不出现** |

成功（携带数据）：

```json
{
  "code": 0,
  "message": "成功",
  "data": { "id": 225, "ticketNo": "ST-20260923-175436-7A1A", "status": "PENDING_ASSIGN" }
}
```

失败：

```json
{
  "code": 10003,
  "message": "工单不存在或已删除，id=999999999"
}
```

**为什么 HTTP 不用 4xx/5xx**：调用方（前端、Postman、后续的 AI 服务）只需判断 `code` 一个字段，不必同时处理 HTTP 状态码与业务码两套体系。代价是 404/405 这类容器级错误仍会返回 Spring 默认错误 JSON，未经统一包装（见已知边界）。

### 1.2 null 字段不会输出（重要）

项目启用 `spring.jackson.default-property-inclusion: non_null`，**值为 null 的字段不会出现在 JSON 中**。因此：

- 未指派的工单**没有** `assigneeId` 字段（而不是 `"assigneeId": null`）
- 创建工单产生的日志**没有** `fromStatus` 字段（因为它确实为 null）
- `description`、`category`、`tags` 未填时同样不出现

**前端/调用方必须用"字段是否存在"判断，不能假设字段一定存在。**

### 1.3 日期时间格式（实测与配置不符，特别注意）

实测返回格式为 **ISO-8601**：`2026-09-23T17:54:36`（`T` 分隔）。

`application.yml` 中配置了 `spring.jackson.date-format: yyyy-MM-dd HH:mm:ss`，但该配置**只作用于 `java.util.Date`**；`LocalDateTime` 由 Jackson 的 `JavaTimeModule` 按 ISO-8601 序列化，**不受该配置影响**。调用方按 ISO-8601 解析。

### 1.4 全局错误码表

| code | 含义 | 触发场景 | 实测响应示例 |
|---:|---|---|---|
| `0` | 成功 | — | `{"code":0,"message":"成功","data":{...}}` |
| `10001` | 工单状态流转不合法 | 状态机白名单拒绝的流转 | `"不允许的状态流转：处理中(PROCESSING) → 已关闭(CLOSED)"` |
| `10002` | 未知的工单状态值 | 分页筛选传入未定义的 status | `"未知的工单状态：NOT_A_STATUS"` |
| `10003` | 工单不存在 | 按 id 查/改/指派/关闭时目标不存在（或已被逻辑删除） | `"工单不存在或已删除，id=999999999"` |
| `10004` | 工单编号生成冲突 | 编号含随机段，撞唯一键且重试 3 次仍失败（理论上极罕见） | — |
| `10005` | 当前工单状态不允许此操作 | 指派已关闭的工单 | `"已关闭的工单不能指派，如需继续处理请先重开，id=226"` |
| `10006` | AI 能力未配置 | **不通过响应体 `code` 返回**，只出现在 AI 分析的 `data.degradedReasonCode`；含义：未配密钥 / AI 总开关关闭 / 模型未装配 | 见 [3.9](#39-ai-分析阶段2) |
| `10007` | AI 调用失败 | 同上；含义：超时、网络不通、鉴权失败、厂商 5xx | 见 [3.9](#39-ai-分析阶段2) |
| `10008` | AI 返回内容不符合约定格式 | 同上；含义：不是合法 JSON、字段缺失或多余、取值越界 | 见 [3.9](#39-ai-分析阶段2) |
| `40000` | 参数校验失败 | `@NotBlank` / `@Size` / `@Positive` / `@Min` / `@Max` 等未通过 | `"title: 标题不能为空"` |
| `40001` | 请求体格式错误，无法解析 | 请求体不是合法 JSON | `"请求体格式错误，无法解析"` |
| `50000` | 系统繁忙 | 未预料的异常（对外不暴露内部细节） | `"系统繁忙，请稍后重试"` |

码值分段规则：`1xxxx` 业务类 / `4xxxx` 客户端类 / `5xxxx` 系统类。

> **AI 段错误码（10006~10008）是唯一不走响应体 `code` 的错误码。** 原因：AI 分析是"附加建议"，
> AI 不可用时请求本身仍然成功，接口返回 `code = 0` 并在 `data.degraded` 中说明情况
> （理由见 [3.9](#39-ai-分析阶段2)）。因此这三个码只作为 `degradedReasonCode` 出现，
> 用于区分"没配 AI / 模型挂了 / 模型不守规矩"三种排查方向不同的情况。

## 二、状态机流转矩阵

理解「关闭」「指派」两个接口的行为前，必须先看状态规则。

### 2.1 合法流转（14 条边）

| 当前状态 | 可流转到 |
|---|---|
| 待分配 `PENDING_ASSIGN` | 处理中、已挂起、**已关闭** |
| 处理中 `PROCESSING` | 待反馈、已解决、已挂起、待分配 |
| 待反馈 `PENDING_FEEDBACK` | 处理中、已解决、已挂起 |
| 已解决 `RESOLVED` | 已关闭、处理中 |
| 已挂起 `SUSPENDED` | 处理中 |
| 已关闭 `CLOSED` | 处理中（重开） |

### 2.2 一律拒绝的两类

1. **自身流转**（任意 `X → X`）——例如「已关闭」再次关闭
2. **跳步流转**——例如「待分配 → 已解决」、「处理中 → 已关闭」

违反上述规则返回 `10001`。

### 2.3 当前实现的边界

- **「解决」接口已补齐**（阶段1 收尾）：`POST /api/tickets/{id}/resolve` 可将「处理中」「待反馈」流转到「已解决」，因此 `RESOLVED` 状态与 `RESOLVED → CLOSED` 这条边均已能通过接口到达。此前该状态无法抵达，而「处理中 → 已关闭」又被状态机拒绝，导致处理中的工单无法正常关闭（缺陷登记表 DEF-003）。
- **无独立「重开」接口**：`CLOSED → PROCESSING` 在矩阵中合法，但没有接口暴露；指派接口会**明确拒绝**已关闭工单（返回 `10005`），避免把"重开"隐式塞进指派语义。

## 三、接口清单

所有路径以 `/api/tickets` 为前缀。

### 3.1 创建工单

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/api/tickets` |
| 说明 | 创建工单，状态固定为「待分配」，编号由服务端生成，同时写入一条 `CREATE` 操作日志 |

**请求参数（JSON body）**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `title` | string | 是 | ≤ 200 字符，不可空白 | 工单标题 |
| `description` | string | 否 | ≤ 65535 字符 | 描述 |
| `category` | string | 否 | ≤ 50 字符 | 分类，自由文本 |
| `priority` | string | 否 | `LOW`/`MEDIUM`/`HIGH`/`URGENT` | 不传时取 `MEDIUM` |
| `tags` | string | 否 | ≤ 255 字符 | 标签，逗号分隔 |
| `creatorId` | long | 是 | 正整数 | 创建人 ID（阶段1 无登录体系，显式传入） |

**请求示例**

```json
{
  "title": "接口文档-打印机无法连接",
  "description": "二楼打印机离线，无法打印",
  "category": "硬件",
  "priority": "HIGH",
  "tags": "打印机,硬件",
  "creatorId": 1
}
```

**成功响应**（真实返回）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "id": 225,
    "ticketNo": "ST-20260923-175436-7A1A",
    "title": "接口文档-打印机无法连接",
    "description": "二楼打印机离线，无法打印",
    "category": "硬件",
    "priority": "HIGH",
    "status": "PENDING_ASSIGN",
    "creatorId": 1,
    "tags": "打印机,硬件",
    "createdAt": "2026-09-23T17:54:36",
    "updatedAt": "2026-09-23T17:54:36"
  }
}
```

**可能错误**

| code | 场景 |
|---:|---|
| `40000` | `title` 为空 → `"title: 标题不能为空"`；`creatorId` 缺失或非正数；`priority` 取值非法 |
| `40001` | 请求体不是合法 JSON |
| `10004` | 编号撞唯一键且重试 3 次仍失败（极罕见） |

**备注**

- 工单编号格式：`ST-yyyyMMdd-HHmmss-4位十六进制随机`，例如 `ST-20260923-175436-7A1A`
- 入参**不含** `status`、`assigneeId`，这两个字段由服务端控制（状态固定 `PENDING_ASSIGN`，处理人初始为空）
- 响应不含 `deleted`（逻辑删除标记属内部字段，不对外暴露）

### 3.3 分页查询工单

| 项 | 内容 |
|---|---|
| 方法 | `GET` |
| 路径 | `/api/tickets` |
| 说明 | 分页查询，支持按状态筛选。默认按 `created_at DESC, id DESC` 排序 |

**Query 参数**

| 参数 | 类型 | 必填 | 默认 | 约束 | 说明 |
|---|---|---|---|---|---|
| `current` | long | 否 | `1` | ≥ 1 | 页码，从 1 开始 |
| `size` | long | 否 | `10` | 1 ~ 100 | 每页条数，上限 100 |
| `status` | string | 否 | — | 必须是已定义状态值 | 状态筛选，非法值返回 `10002` |

**请求示例**

```
GET /api/tickets?current=1&size=3
```

**成功响应**（真实返回）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "records": [
      {
        "id": 225,
        "ticketNo": "ST-20260923-175436-7A1A",
        "title": "接口文档-打印机无法连接",
        "priority": "HIGH",
        "status": "PENDING_ASSIGN",
        "creatorId": 1,
        "createdAt": "2026-09-23T17:54:36",
        "updatedAt": "2026-09-23T17:54:36"
      }
    ],
    "total": 1,
    "current": 1,
    "size": 3,
    "pages": 1
  }
}
```

**分页字段说明**

| 字段 | 说明 |
|---|---|
| `records` | 当前页数据数组 |
| `total` | 符合条件的总记录数 |
| `current` | 当前页码 |
| `size` | 每页条数 |
| `pages` | 总页数，由服务端按 `total`/`size` 计算，避免各端算法不一致 |

**可能错误**

| code | 场景 |
|---:|---|
| `10002` | `status` 传了未定义的值 → `"未知的工单状态：NOT_A_STATUS"` |
| `40000` | `current < 1`、`size < 1` 或 `size > 100` |

**备注**

- `status` 的取值校验复用状态机的 `fromCode`，与状态定义单一来源；**非法值会明确报错，而不是静默返回空列表**
- 返回的是专用 `PageVO`，不是 MyBatis-Plus 的 `Page` 对象（后者会带出 `orders`、`optimizeCountSql` 等内部字段）

```json
    "createdAt": "2026-09-23T17:54:36",
    "updatedAt": "2026-09-23T17:54:37"
  }
}
```

**可能错误**

| code | 场景 |
|---:|---|
| `10003` | id 不存在 |

- **入参结构里没有 `status` 字段**，从结构上杜绝"通过更新接口改状态"；即使 JSON 里多传 `status`，也会被 Jackson 忽略

### 3.6 指派工单

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/api/tickets/{id}/assign` |
| 说明 | 指派处理人。**语义按当前状态决定**（见下） |

**路径参数**：`id`（long，必填）

**请求参数（JSON body）**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `assigneeId` | long | 是 | 正整数 | 处理人 ID |
| `operatorId` | long | 是 | 正整数 | 操作人 ID |
| `remark` | string | 否 | ≤ 500 字符 | 备注，不传时服务端填默认文案 |

**语义规则**

| 当前状态 | 行为 | 结果状态 |
|---|---|---|
| `PENDING_ASSIGN` 待分配 | 指派 + **状态流转** | → `PROCESSING` 处理中 |
| 其它未关闭状态 | 视为**转派**：只换处理人 | 状态不变 |
| `CLOSED` 已关闭 | **拒绝**（返回 `10005`） | 状态不变 |

**请求示例**

```json
{ "assigneeId": 2, "operatorId": 1, "remark": "指派给运维2号" }
```

**成功响应**（真实返回）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "id": 225,
    "ticketNo": "ST-20260923-175436-7A1A",
    "title": "接口文档-打印机无法连接（已更新）",
    "priority": "URGENT",
    "status": "PROCESSING",
    "creatorId": 1,
    "assigneeId": 2,
    "createdAt": "2026-09-23T17:54:36",
    "updatedAt": "2026-09-23T17:54:37"
  }
}
```

**可能错误**

| code | 场景 |
|---:|---|
| `10003` | 工单不存在 |
| `10005` | 指派已关闭的工单 → `"已关闭的工单不能指派，如需继续处理请先重开，id=226"` |
| `40000` | `assigneeId` 或 `operatorId` 缺失、非正数 |

**备注**

- 指派成功后**会删除详情缓存**，避免接口继续返回旧处理人
- 同一接口承担「指派」与「转派」两种语义，由当前状态区分，不需要两个接口

### 3.7 关闭工单

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/api/tickets/{id}/close` |
| 说明 | 关闭工单，**需通过状态机校验** |

**路径参数**：`id`（long，必填）

**请求参数（JSON body）**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `operatorId` | long | 是 | 正整数 | 操作人 ID |
| `remark` | string | 否 | ≤ 500 字符 | 备注，不传时默认「关闭工单」 |

**请求示例**

```json
{ "operatorId": 1, "remark": "重复提交，直接作废" }
```

**成功响应**（真实返回）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "id": 226,
    "ticketNo": "ST-20260923-175452-37A1",
    "title": "接口文档-会议室投影仪无信号",
    "priority": "MEDIUM",
    "status": "CLOSED",
    "creatorId": 1,
    "createdAt": "2026-09-23T17:54:52",
    "updatedAt": "2026-09-23T17:54:52"
  }
}
```

**可能错误**

| code | 场景 |
|---:|---|
| `10001` | 非法流转 → `"不允许的状态流转：处理中(PROCESSING) → 已关闭(CLOSED)"` |
| `10003` | 工单不存在 |
| `40000` | `operatorId` 缺失或非正数 |

**备注**

- 按矩阵，只有「待分配」与「已解决」可以直接关闭；「处理中 → 已关闭」会被拒绝（需先经"解决"环节）
- 重复关闭（`CLOSED → CLOSED`）属自身流转，同样返回 `10001`
- 入参**不含目标状态**，目标固定为「已关闭」，不接受调用方指定，避免绕过状态机
- 关闭成功后**会删除详情缓存**

### 3.8 解决工单

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/api/tickets/{id}/resolve` |
| 说明 | 把工单标记为「已解决」，**需通过状态机校验** |

**路径参数**：`id`（long，必填）

**请求参数（JSON body）**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `operatorId` | long | 是 | 正整数 | 操作人 ID |
| `remark` | string | 否 | ≤ 500 字符 | 解决说明，不传时默认「处理完毕，已解决」 |

**请求示例**

```json
{ "operatorId": 1, "remark": "已重启服务并修复配置" }
```

**成功响应**（真实返回，其余字段与创建接口一致，此处省略）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "id": 316,
    "title": "第14天-解决接口实测",
    "priority": "HIGH",
    "status": "RESOLVED",
    "creatorId": 1,
    "assigneeId": 2
  }
}
```

**可能错误**

| code | 场景 |
|---:|---|
| `10001` | 非法流转 → 例如从「待分配」直接解决属跳步：`"不允许的状态流转：待分配(PENDING_ASSIGN) → 已解决(RESOLVED)"`；重复解决（自身流转）同样返回该码 |

- 入参**不含目标状态**，目标固定为「已解决」，不接受调用方指定
- 解决成功后**会删除详情缓存**
- 本接口补齐了工单生命周期的关键一环。补上后完整链路才走得通：`待分配 → 处理中 → 已解决 → 已关闭`（此前第三步无入口，见缺陷登记表 DEF-003）

### 3.9 AI 分析（阶段2）

| 项 | 内容 |
|---|---|
| 路径 | `POST /api/ai/tickets/analyze` |
| 用途 | 对工单文本做分类与优先级推荐，同时给出关键词与判断理由 |
| 副作用 | **无**。只返回建议，不写库、不改动任何工单数据 |
| 依赖 | 需要配置模型密钥（见 `ticket-service/README.md` 的「AI 配置」）；未配置时按降级返回 |

**为什么分类与优先级合成一个接口**：章程把两者列为两项能力，但它们由**同一次模型调用**产出
（v1 Prompt 同时要求 category 与 priority）。拆成两个 HTTP 接口会让同一工单分析两次、付两次费，
且两端拿到的判断理由可能不一致。详见决策记录 `20260926_阶段2AI提示词与输出结构.md`。

**请求**

```json
{
  "title": "支付页面点击提交后一直转圈，钱被扣了但订单没生成",
  "description": "我在 10 点 23 分下单，页面一直转圈，等了 5 分钟后刷新，发现银行卡已经扣款成功，但订单列表里没有这笔订单。再下一单直接提示失败。"
}
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `title` | string | 是 | 1~200 字 | 工单标题 |
| `description` | string | 否 | ≤65535 字 | 工单描述。**超过 2000 字的部分不会发给模型**（截断并标记），避免 token 成本失控 |

**响应字段**

| 字段 | 类型 | 出现条件 | 说明 |
|---|---|---|---|
| `degraded` | boolean | 恒有 | `true` = 本次没有 AI 建议，应按人工处理 |
| `degradedReasonCode` | int | 仅降级时 | `10006` 未配置 / `10007` 调用失败 / `10008` 格式不符 |
| `degradedReason` | string | 仅降级时 | 固定文案，不含内部细节（细节只进日志） |
| `category` | string | 仅成功时 | 受控取值之一：`账户问题` / `支付问题` / `功能异常` / `其他` |
| `priority` | string | 仅成功时 | `LOW` / `MEDIUM` / `HIGH` / `URGENT` |
| `confidence` | number | 仅成功时 | 模型把握度 0~1 |
| `keywords` | string[] | 仅成功时 | 1~8 个关键词 |
| `reason` | string | 仅成功时 | ≤200 字的判断理由 |
| `promptVersion` | string | 恒有 | 产生本结果的 Prompt 版本，便于追溯 |
| `model` | string | 成功时 | 实际调用的模型名 |
| `costMs` | long | 恒有 | 本次 AI 调用耗时（毫秒） |

**示例 1：分析成功**（2026-09-28 真实调用，DeepSeek `deepseek-chat`，耗时 1101ms）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "degraded": false,
    "category": "支付问题",
    "priority": "URGENT",
    "confidence": 0.95,
    "keywords": ["支付页面", "转圈", "扣款成功", "订单没生成", "下单失败"],
    "reason": "用户支付后扣款成功但订单未生成，属于资金损失且影响核心交易功能，问题严重需紧急处理，故判为支付问题并定级URGENT。",
    "promptVersion": "ticket-classify-v1",
    "model": "deepseek-chat",
    "costMs": 1101
  }
}
```

**示例 2：描述为空**（真实调用，耗时 987ms）—— 注意 `confidence` 降到 0.5，且 `reason` 主动说明依据有限。
这是 v1 Prompt 要求的"信息不足时必须给低分"的实际效果：

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "degraded": false,
    "category": "功能异常",
    "priority": "MEDIUM",
    "confidence": 0.5,
    "keywords": ["打印机连不上", "三台电脑都打不了"],
    "reason": "描述为空，仅依据标题判断，依据有限。打印机无法连接影响办公，但未涉及账户或支付，归为功能异常；影响范围有限，暂定中优先级。",
    "promptVersion": "ticket-classify-v1",
    "model": "deepseek-chat",
    "costMs": 987
  }
}
```

**示例 3：AI 未配置**（真实调用；启动参数 `--smartticket.ai.enabled=false`，耗时 0ms——**未发起任何网络请求**）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "degraded": true,
    "degradedReasonCode": 10006,
    "degradedReason": "AI 能力未配置，已降级为人工处理",
    "promptVersion": "ticket-classify-v1",
    "costMs": 0
  }
}
```

**示例 4：模型不可达**（真实调用；启动参数 `--spring.ai.openai.base-url=http://127.0.0.1:9`，耗时 130ms）

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "degraded": true,
    "degradedReasonCode": 10007,

  }

```

**可能错误**

| code | 场景 |
|---:|---|
| `40000` | `title` 缺失或为空白：`"title: 标题不能为空"` |
| `40001` | 请求体不是合法 JSON |

> 上表只有这两个"真错误"。**AI 侧的任何异常都不返回非 0 的 `code`**，而是 `code = 0` +
> `degraded = true`，理由见 1.4 的错误码说明。

**备注**

- 本接口**只给建议、不写库**：AI 输出的正确率在第5周评估之前是未知的，让它直接改数据等于把未经验证的结果写进生产数据
- `confidence` 原样透出，**是否转人工由调用方按阈值自行决定**——阈值属第5周（章程第5周任务 3），在有评估数据之前定阈值等于拍数字
- 降级时可以放心当作"没有建议"处理：接口不报错、不阻塞，前端只需判断 `degraded`
- `10008`（模型返回格式不符）未采集真实样例——它需要模型"答了但不守规矩"，无法稳定构造。
  该路径由 `AiControllerTest`（MockMvc 集成，6 个用例）与 `AiClassificationParserTest`（15 个用例）覆盖

## 六、已知边界（与接口契约相关）

| # | 边界 | 影响 |
|---:|---|---|
| 1 | 无独立「重开」接口 | 已关闭工单无法通过接口恢复处理 |
| 2 | 404 / 405 不走统一返回体 | 访问不存在的路径或错误方法时返回 Spring 默认错误 JSON |
| 3 | `data` 为 null 时字段被省略 | 见 [1.2](#12-null-字段不会输出重要) |
| 4 | 更新接口不写操作日志 | 日志无法完整反映所有变更 |
| 5 | AI 分析未采集 Token 消耗 | 响应与日志都没有 `usage`，无法核算单次成本 |
| 6 | AI 分析未做输入脱敏 | 工单描述原文会发往模型厂商，涉及隐私合规判断，当前未处理 |
| 7 | `confidence` 阈值未定 | 接口透出把握度但不判定转人工，阈值待第5周评估数据 |

**已在阶段1 收尾修复的边界（保留记录）**：

| 原边界 | 修复情况 |
|---|---|
| 无「解决」接口，`RESOLVED` 状态不可达 | 已补 `POST /api/tickets/{id}/resolve`（DEF-003） |
| 缓存层故障时详情查询整体失败 | 已改为降级：Redis 不可用时回源数据库，接口保持可用（DEF-001） |
