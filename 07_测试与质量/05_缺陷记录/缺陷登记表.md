## 三、详细记录

### DEF-001：Redis 不可用时工单详情接口整体不可用

| 项 | 内容 |
|---|---|
| 严重度 | 高 |
| 发现日期 | 2026-09-22（第9天） |
| 发现方式 | Docker 引擎中断导致集成测试全线失败，从异常堆栈中定位 |

**现象**

第 9 天为 `getById` 引入 Cache-Aside 缓存后，只要 Redis 不可用，工单详情查询**整体失败**，返回 `50000`——尽管 MySQL 完全正常。

**根因**

`getById` 的第一步就是读缓存，而 `stringRedisTemplate.opsForValue().get(...)` 抛出的 `RedisConnectionFailureException` 未被捕获，直接导致整个方法失败，**根本没有机会走到回源数据库那一步**。

当时的代码只对**缓存内容**做了容错（JSON 解析失败 → 清 key 后回源），没有对**缓存连接**做容错。

**影响**

缓存本意是"加速"，实际却成了**单点依赖**：Redis 一挂，一个本来只依赖数据库的读接口跟着不可用。Redis 重启、网络抖动在真实环境都会发生。

**复现步骤**

```powershell
# 1. 建一条工单并查询一次（建立缓存）
# 2. 停掉 Redis
docker stop smartticket-redis
# 3. 再查详情 → 修复前返回 50000，修复后返回 code=0 与正确数据
```

**修复（2026-09-24 第13天）**

给缓存的**读、写、删**三个动作都加上容错，把缓存降级为"尽力而为"：

| 动作 | 方法 | 失败后的行为 |
|---|---|---|
| 读 | `readCacheQuietly` | 返回 null（等同未命中），回源数据库 |
| 写 | `writeCacheQuietly` | 记 WARN，不影响本次返回 |
| 删 | `evictDetailCache` | 记 WARN，待 TTL 到期自愈 |

**一个有意的例外**：`writeJson`（VO 序列化）刻意留在 try 之外。序列化失败属于**代码/结构问题**（VO 改了但缓存逻辑没跟上），应当暴露而不是被当作缓存故障吞掉；Redis 写入失败才是可降级的环境问题。

**修复后验证**

真实停容器演练（2026-09-24）：

```text
② 第一次查询(建立缓存): code=0
③ 停掉 Redis 容器
④ Redis 已停，再查详情: code=0 title=第13天边界-Redis故障演练 status=PENDING_ASSIGN
```

另有 3 个单元测试长期守护（`getByIdFallsBackToDatabaseWhenRedisIsDown`、`getByIdStillReturnsDataWhenCacheWriteFails`、`closeSucceedsWhenCacheEvictionFails`）。

### DEF-002：MySQL 不可用时请求需等待 30 秒才返回错误

| 项 | 内容 |
|---|---|
| 严重度 | 中 |
| 发现日期 | 2026-09-24（第13天） |
| 发现方式 | 边界演练：停掉 MySQL 容器后实测创建接口 |

**现象**

MySQL 停止后，`POST /api/tickets` 要**等待 30 秒**才返回 `50000`：

```text
⑦ MySQL 已停，创建工单: code=50000 message=系统繁忙，请稍后重试 耗时=30077ms
```

**根因**

HikariCP 的 `connectionTimeout` 默认为 **30 秒**。数据库不可用时，每个请求都会阻塞等待连接池超时，而不是快速失败。

**影响**

这是比"接口报错"更危险的形态：**错误返回得不够快**。

- Tomcat 默认 200 个工作线程。若平均每个请求占用 30 秒，**约 200 个并发请求就能把线程池打满**
- 线程池打满后，**即使数据库已恢复，健康请求也拿不到线程**，服务表现为整体无响应
- 这就是典型的"故障放大"：一个下游故障演变成整个服务雪崩

**建议修复方向**

把 `spring.datasource.hikari.connection-timeout` 从默认 30000ms 下调到 **3000~5000ms**：故障时快速失败，把线程尽快释放。同时建议给 `validation-timeout`、`maximum-pool-size` 一并复核。

**修复（2026-09-24，阶段1 收尾）**

在 `application.yml` 中把 `spring.datasource.hikari.connection-timeout` 由默认的 30000ms 下调为 **5000ms**。放在 `application.yml` 而非 `application-local.yml`：它不属于密钥类配置，应当随代码走。

修复后实测（停掉 MySQL 容器）：

```text
⑥ 创建: code=50000 message=系统繁忙，请稍后重试
⑦ 耗时: 5021ms（改造前 30077ms）
```

错误码与失败行为不变，但失败速度从 30 秒降到 5 秒，单个请求占用工作线程的时间减少约 83%。

**附：本次演练的附加收获**

MySQL 停止期间，**查询详情反而成功了**——因为该工单的详情已在 Redis 缓存中：

```text
⑧ MySQL 已停，查 id=282 详情(Redis 缓存命中): code=0
```

这从反面印证了缓存的真实价值：它不只是"查得快"，在数据库故障时确实能保住部分读能力。

### DEF-003：无「解决」接口，`RESOLVED` 状态不可达

| 项 | 内容 |
|---|---|
| 严重度 | 中 |
| 发现日期 | 2026-09-20（第7天） |
| 状态 | 待确认（需产品侧决定） |

**现象**

状态机定义了 6 个状态、14 条合法流转边，但对外只有 5 个会改状态的接口（创建、更新、指派、关闭、查询日志）。**没有任何接口能把工单置为「已解决」**。

**影响**

- `RESOLVED` 状态只能通过数据库直插产生，无法通过接口到达
- 状态机矩阵中 `RESOLVED → CLOSED`、`RESOLVED → PROCESSING` 两条边在实际使用中不可达
- 「处理中 → 已关闭」被状态机拒绝（要求先经"解决"环节），但**"解决"这一步没有入口**——这意味着**处理中的工单目前无法正常关闭**，只能先一直挂在那里

**这一条的影响比看起来大**：它使正常的工单生命周期（待分配 → 处理中 → 已解决 → 已关闭）在第三步断了。

**修复（2026-09-24，阶段1 收尾）**

补 `POST /api/tickets/{id}/resolve` 接口：一次纯流转，调用 `checkTransitionTo(RESOLVED)`。「处理中」「待反馈」可流转到「已解决」；「待分配」直接解决属跳步、重复解决属自身流转，均被拒绝（10001）。

修复后实测完整生命周期，四步全部通过真实 HTTP 完成：

```text
① 创建: code=0 status=PENDING_ASSIGN
② 指派: code=0 status=PROCESSING
③ 解决: code=0 status=RESOLVED
④ 关闭: code=0 status=CLOSED
⑤ 日志 4 条: CREATE -> ASSIGN -> RESOLVE -> CLOSE
```

工单生命周期至此闭环，且留下完整审计链。

### DEF-004：更新工单不写操作日志

| 项 | 内容 |
|---|---|
| 严重度 | 中 |
| 发现日期 | 2026-09-20（第7天） |
| 状态 | 待处理 |

**现象**

创建、指派、关闭三个操作都会写 `ticket_log`，**唯独更新不写**。

**证据**

更新标题与优先级后查询日志，仍只有 1 条 `CREATE`：

```text
action=CREATE from= to=PENDING_ASSIGN operator=1 remark=创建工单
```

**影响**

`ticket_log` 本应作为工单的完整变更审计线索。更新是**内容变更最频繁的操作**，不记录会导致审计链断裂——"谁在什么时候改了什么"无法回答。

**建议**

补 `UPDATE` 动作的日志写入，`remark` 记录变更摘要（例如改动了哪些字段）。

### DEF-005：指派接口不校验处理人是否存在

| 项 | 内容 |
|---|---|
| 严重度 | 低 |
| 发现日期 | 2026-09-24（第13天） |
| 状态 | 不适用（阶段1 缺少实现前提） |

**现象**

指导的第13天边界清单要求「指派给不存在的处理人」。实测确认：`assign` 接口**不校验 `assigneeId` 对应的人是否存在**——传 `assigneeId = 999999` 也会成功，工单会被指派给一个不存在的人。

**为什么当前不做**

阶段1 **没有用户体系**（无 `user` 表、无登录），`assigneeId` 本身就是调用方自由传入的裸数字，服务端没有任何依据去校验其存在性。当前仅通过 `@NotNull` + `@Positive` 保证它是正整数。

**建议**

阶段2/3 引入用户体系后，在 `assign` 中补存在性校验，并新增错误码（如 `10006 处理人不存在`），同时把 `assignee_id` 加成外键或至少补索引校验。

### DEF-006：404 / 405 不走统一返回体

| 项 | 内容 |
|---|---|
| 严重度 | 低 |
| 发现日期 | 2026-09-20（第7天） |
| 状态 | 待确认 |

**现象**

项目约定所有接口返回 `{code, message, data}` 且 HTTP 恒为 200。但访问**不存在的路径**或**用错 HTTP 方法**时，返回的是 Spring 默认错误结构：

```json
{"timestamp":"...","status":404,"error":"Not Found","path":"/api/xxx"}
```

**注**：路径参数非法（如 `/api/tickets/abc`）属于类型转换失败，**已被统一返回体覆盖**，通过 `MethodArgumentTypeMismatchException` 处理。未覆盖的只有"路径本身不存在"和"方法不匹配"两类容器级错误。

**影响**

调用方若统一按 `code` 判断结果，遇到 404/405 时需要额外处理一套格式。

**建议**

要么补 `ErrorController` / `NoHandlerFoundException` 处理器纳入统一返回，要么在接口文档中明确声明这一边界（当前文档已在「已知边界」中声明）。

### DEF-007：`spring.jackson.date-format` 对 `LocalDateTime` 不生效

| 项 | 内容 |
|---|---|
| 严重度 | 低 |
| 发现日期 | 2026-09-23（第11天） |
| 状态 | 已确认（文档已说明实际格式） |

**现象**

`application.yml` 中配置了：

```yaml
spring:
  jackson:
    date-format: yyyy-MM-dd HH:mm:ss
```

但实测接口返回的是 **ISO-8601**：`"createdAt": "2026-09-23T17:54:36"`（`T` 分隔）。

**根因**

`spring.jackson.date-format` **只作用于 `java.util.Date`**。项目实体统一使用 `LocalDateTime`，由 Jackson 的 `JavaTimeModule` 处理，默认按 ISO-8601 序列化，**完全不受该配置影响**。

**影响**

- 该配置属于"写了但没生效"，容易误导后续维护者以为时间格式已被统一
- 前端若按 `yyyy-MM-dd HH:mm:ss` 解析会失败

**当前处理**

不改配置（改则需引入 `@JsonFormat` 注解或自定义序列化器，属格式统一问题，阶段1 不必展开）。**在接口文档中如实写明实际返回为 ISO-8601**，调用方按 ISO 解析。

**这是本项目第 2 次遇到"配置写了、看着生效、实际没生效"**（第 1 次是第 8 天的 `spring.data.redis` 前缀）。两者的共同点：**不报错、不告警、静默失效**，只能靠实测发现。
