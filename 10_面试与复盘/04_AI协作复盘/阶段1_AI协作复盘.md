> 复盘日期：2026-09-24
> 复盘依据：15 篇 AI 对话日志、3 篇决策记录、7 个缺陷记录、82 个自动化测试用例

## 一、AI 做得好的地方

### 1. 不盲从指令，对不合理处给出理由并提替代方案

**案例（第8天）**：指导清单要求"编写 Redis 配置类"。AI 判定选 `StringRedisTemplate` 后自动配置已提供该 Bean，且默认序列化就是可读的 String，**写配置类只能是空壳**。它没有照做，而是分析了这个类唯一有价值的风险点（前缀写错），改用一个断言前缀的测试用例守住，并在对话日志里写明理由备查。

**价值**：避免了"为满足清单而写无用代码"。`AI协作总则` 第 5/6 条本意就是防止无约束生成，此处是正向执行。

### 2. 验证做到"断言必须能失败"

这是本阶段质量意识最集中的一处。AI 主动识别并修复了 **4 个"能通过但验证力为零"**的问题：

| # | 问题 | 性质 |
|---|---|---|
| 1 | JsonPath 过滤断言 `[?(@.title=='x')].exists()`，结果为空也通过 | 假通过 |
| 2 | `TicketMapperTest` 断言"表为空" | 脆弱断言（测的是环境状态，人工跑一次 Postman 就必然失败） |
| 3 | Redis healthcheck 用 `redis-cli ping`，密码错也返回 PONG | 恒真 |
| 4 | `assertEquals("PROCESSING", ticket(...).getStatus())` | 无效断言（自己和自己比） |

配套的正面做法也一贯执行：

- "二次查询走缓存"用**双向反证**证明——用 `JdbcTemplate` 绕过 Service 改库后断言仍返回旧标题，再删缓存断言返回新标题。只做前半段的话，万一改库语句失败，测试照样通过。
- 第13天标题长度做**双向边界**：200 字符必须通过、201 字符必须拒绝。只测拒绝侧的话，一个把 `@Size(max=0)` 写错的版本也能全绿。
- Redis healthcheck 用**错误密码**验证它真的会失败。

### 3. 如实报告问题，包括自己的错误

**案例（第10天）**：发现库中第7天留存的两条验收数据（id=70/71）消失了。AI 用三条元数据收敛可能性（表 `CREATE_TIME` 未变排除重建、`AUTO_INCREMENT` 仍为 164/192 证明是"删空"、哨兵法排除测试代码误删），最终定位为"某条 `DELETE` 所为"，并**主动认领**第7天自己给出的清理指令 `WHERE id >= 70` 条件过宽——该条件会随数据增长改变语义，是指令设计缺陷。随后提出约束建议并修正。

**价值**：没有把问题推给"环境异常"了事，而是留下了可复用的判断链。

### 4. 把"踩过的坑"固化为可复用经验

每份对话日志都包含「发现的问题」与「是否需要更新 AI 约束」两节。本阶段累计提出 4 条约束建议（见第五节），均来自真实失败，而非泛泛而谈。

## 二、AI 出现的问题

### 1. 工具报成功但内容未落盘（发生 2 次）

| 时间 | 表现 | 后果 |
|---|---|---|
| 第7天 | 批量编辑中 `TicketServiceImpl` 的 import 与 `TicketService` 的方法声明未写入 | 编译失败 |
| 第9天 | `TicketServiceImpl` 与 `TicketApiTest` 各一次 import 未写入 | 连续两轮编译失败 |

**应对**：批量编辑后**用 grep 一次性复核所有新增符号**（第9天复核了 19 处）。此为该问题的通用对策，已建议纳入约束。

### 2. 交出的指令/脚本未考虑执行环境差异（发生 3 次）

| 时间 | 表现 |
|---|---|
| 第11天 | 给出的数据库查询指令用 `sh -c '...'` 嵌套单引号，**在 AI 自己的终端能跑通，用户的 PowerShell 报 SQL 语法错** |
| 第14天 | `start.ps1` 保存为无 BOM 的 UTF-8，Windows PowerShell 5.1 按 GBK 解析，中文路径变乱码、找不到 JDK |
| 第14天 | 脚本回显含中文的完整路径，控制台输出编码不匹配导致显示乱码（能跑但看不懂） |

**共性**：都是"在我这里通过"就交付了。**用户环境与 AI 环境不一致**是必然，验证必须在贴近用户环境的前提下做。

### 3. 代码层面的低级错误

| 时间 | 错误 | 根因 |
|---|---|---|
| 第6天 | `对Pattern的引用不明确` | `jakarta.validation` 与 `java.util.regex` 的 `Pattern` 同名 |
| 第12天 | `对insert的引用不明确` | `BaseMapper` 同时有 `insert(T)` 与 `insert(Collection<T>)`，`any(Ticket.class)` 仍歧义，需 `ArgumentMatchers.<T>any()` |
| 第12天 | 4 个用例报 `can not find lambda cache for this entity` | 纯单元测试中没有 MyBatis 上下文，`Wrappers.lambdaUpdate` 依赖的 `TableInfo` 缓存需手动初始化 |
| 第13天 | 脚本三轮才跑通 | 编码问题（见上） |

**说明**：第12天那两条属于"脱离框架默认运行路径"后的必然代价，本身有价值（见第六节），但**第一轮就应预料到**——既然要绕开 Spring，就该先想清楚哪些东西是 Spring 提供的。

### 4. 测试写得不严谨（4 次，见第一节第 2 点）

值得注意的是：**这 4 个问题都是 AI 自己写出来的**，也都是 AI 自己后续发现的。说明"写测试"和"审计测试"是两种能力，后者需要刻意切换。

### 5. 对同一环境故障反复误判（6 次）

Docker 引擎在本阶段中断 **6 次**。前几次的表现是"连接被拒绝"，AI 的初始判断是"Docker 没启动"，而实际原因包括"GUI 已开但 WSL2 后端未就绪"。直到第11天才形成稳定的排查顺序：

```text
请求失败 → 应用日志拿根因 → 容器状态 → Docker 引擎 → WSL 发行版状态
```

**教训**：同一个故障重复出现时，应该尽早固化成检查清单，而不是每次重新摸索。

## 三、Prompt 哪里不清楚

### 1. 每日"交底"与"执行"的边界不明确

用户在不同日期的指令形式差异较大：

- 「先介绍一下第五天的工作」「先介绍第七天的工作安排，简短一点」—— 明确只要交底
- 「开始第十二天的测试」「开始第十三天」—— 语义上像执行，但 AI 判断仍需要交底

**影响**：AI 每次都要自行判断，判断不一致会造成体验波动。建议固定为"交底 → 确认 → 执行"三段式，或在指令中显式说明。

### 2. "简短"等程度词没有量化

「简短一点」—— 是只列任务清单，还是含现状盘点？本阶段的做法是"简短 = 现状 + 缺口 + 决策点"，但这是 AI 自行定义的。

### 3. 指导清单的任务粒度与实际进度不同步

`阶段一指导.md` 是按"空白项目"写的，而实际执行中存在大量提前完成的情况。例如：

- 第10天的 4 项任务**全部**在第2天就已完成（唯一缺口是"初始化 SQL 从未真正验证"）
- 第11天的 4 项任务有 3 项已在第6/7天完成
- 第12天的 4 项任务有 3 项已具备

**影响**：每天开工第一件事都是"盘点现状"，这在当前协作模式下是必要的，但说明**指导文档与执行进度之间缺少同步机制**。

### 4. 验收项只写了"做什么"，没写"证据形式"

例如"服务可一键启动"——"一键"到什么程度？脚本？还是能敲命令跑起来即可？本阶段通过与用户确认解决（选择写脚本），但这类歧义在 16 项验收里还有若干。

**建议**：阶段2 开始时，验收项直接写成"可验证的断言"形式（如"执行 X 命令，输出 Y"）。

### 5. 前后指令存在矛盾

第10天用户先说「我和你配合一条一条的去做」，后又改为「全部执行完毕吧，不用询问我，最后给我结果」。两种模式各有适用场景（前者适合有决策点的任务，后者适合机械执行），但混用时 AI 需要自行判断当前该用哪种。

## 五、是否更新 AI 约束

本阶段累计提出 **4 条**约束建议，建议全部纳入 `02_AI约束与规范`：

### 建议 1：破坏性指令必须精确匹配（第10天提出）

> 涉及删除数据、清理资源的指令，匹配条件必须精确到具体行或按属主限定；禁止使用会随数据增长而改变语义的条件（如 `id >= N`）。

**依据**：第7天给出的清理指令 `WHERE id >= 70` 语义会随时间变化，导致第10天发现"数据莫名消失"。

### 建议 2：批量编辑后必须复核落盘（第9天提出）

> 批量修改文件后，必须用检索工具复核所有新增/修改的关键符号确实已写入，再进入编译或测试环节。

**依据**：第7天、第9天各发生一次"工具报成功但内容未落盘"。

### 建议 3：配置变更必须实测验证生效（第11天提出）

> 新增或修改配置项后，必须用实测输出验证该配置确实生效，并在文档中记录实测值；不得仅凭"配置已写入"就认为生效。

**依据**：本阶段**两次**遇到同类问题——`spring.data.redis` 前缀（Boot 3 改名）与 `spring.jackson.date-format`（只对 `java.util.Date` 生效）。两者都是**不报错、不告警、静默失效**。

### 建议 4：边界测试必须双向验证（第13天提出）

> 边界值测试必须同时验证边界两侧（如"恰好等于上限应通过"与"超过上限应拒绝"）。

**依据**：只验证拒绝侧，无法排除"条件被误配成一律拒绝"。

## 六、是否可作为面试踩坑案例

以下 6 个案例**均已在本项目中真实发生、定位、修复并留下证据**，适合作为面试素材。

### 案例 1：配置写了，但没生效（两次）

**现象**：`spring.jackson.date-format: yyyy-MM-dd HH:mm:ss` 配了，接口返回的却是 `2026-09-23T17:54:36`（ISO-8601）。

**根因**：该配置**只作用于 `java.util.Date`**；项目用 `LocalDateTime`，由 `JavaTimeModule` 按 ISO 序列化。

**可讲的点**：这类问题的共性是**静默失效**——不报错、不告警。本阶段还遇到一次同类的 `spring.data.redis` 前缀问题（Spring Boot 3 把 `spring.redis` 改成了 `spring.data.redis`）。**"配置写了"和"配置生效"是两件事。**

### 案例 2：MyBatis-Plus 的 insert 只回填主键，不回填数据库默认值

**现象**：创建工单成功后，返回的 `createdAt` 是 null，且因 `non_null` 配置整个字段消失。

**根因**：`insert` 只回填主键，数据库生成的 `created_at` / `updated_at` 不会回填到实体。

**可讲的点**：修复只需在插入后回读一次。更深的价值在于——**这个问题单元测试永远发现不了**（假 Mapper 会返回我编好的时间），只有集成测试或真实调用才会暴露。这直接说明了测试分层为何必要。

### 案例 3：缓存从"加速器"变成"单点依赖"

**现象**：引入 Redis 缓存后，Redis 一挂，**明明 MySQL 正常，查询详情也整体失败**。

**根因**：`getById` 第一步读缓存，`getConnection` 抛出的异常未被捕获，**根本没机会走到回源那一步**。

**可讲的点**：修复时做了一个有意区分——**Redis 连接失败降级（环境问题），VO 序列化失败继续抛出（代码问题）**。把两者混在一个 catch 里，短期看不出问题，长期会掩盖真正的 bug。

### 案例 4：接口"规范地报错"了，但 30 秒才返回

**现象**：停掉 MySQL 后，创建接口返回 `50000`，一切看起来正常——**除了耗时 30077ms**。

**根因**：HikariCP 的 `connectionTimeout` 默认 30 秒。

**可讲的点**：这是比"报错"更危险的形态。Tomcat 默认 200 线程，每请求占 30 秒 → **约 200 个并发就打满线程池**；打满后即使数据库恢复，健康请求也拿不到线程。**一个下游故障放大成整服务雪崩。** 能把失败模式与线程模型联系起来看，是这道题的价值所在。

### 案例 5：`Collections.unmodifiableMap` 只保护最外层

**现象**：状态机测试有 2 个用例失败且互为因果。

**根因**：`unmodifiableMap` 只锁住外层，内层装的 `EnumSet` 仍可 `add`。测试在构造场景时真的改动成功了，导致跨用例污染。

**可讲的点**：这不只是"测试污染"，而是**生产代码把可变内部结构暴露了出去**——哪天有人在别处误改一下，状态机规则就静默失效。修复是内层改用 `Set.of`。

### 案例 6：测试通过了，但什么都没验证

**现象**：本阶段发现 4 个"能通过但验证力为零"的断言，包括 JsonPath 过滤断言（结果为空也通过）、断言"表为空"（人工跑一次就失败）、healthcheck 恒真。

**可讲的点**：识别这类问题只需要一个自问：**"如果我把被测代码改坏，这个断言会失败吗？"** 答不上来，这个断言就该重写。配套的正面做法是双向验证（第13天标题长度 200/201）。

## 七、总体评价

| 维度 | 评价 |
|---|---|
| **过程留痕** | 好。15 篇对话日志 + 3 篇决策记录 + 7 个缺陷记录，关键决策与失败都有据可查 |
| **质量意识** | 好。主动审计出 4 个假通过断言，并建立了"断言必须能失败"的标准 |
| **主动纠错** | 好。能指出用户的手动改动问题，也能认领自己的指令缺陷 |
| **不盲从** | 好。对无用任务（Redis 配置类）给出理由并提替代方案 |
| **环境适配** | **偏弱**。3 次因"在我这里能跑"而交付失败的指令/脚本，是当前最需要改进的点 |
| **框架边界预见性** | **偏弱**。脱离 Spring 做单测时，未预先想到 `TableInfo`、重载歧义等问题 |

**下一阶段的重点改进方向**：**交付前先在贴近用户的环境验证**。本阶段的失败几乎都集中在这一点上——代码逻辑类的错误一次就能发现并修好，而"环境差异"类的问题反复出现，且每次都要消耗一到三轮往返。
