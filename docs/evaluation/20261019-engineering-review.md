## 实际发现的死锁

新增并发探针在 5、10、20 个同账号工作线程下均复现预算账本异常。原逻辑先 INSERT IGNORE，再条件 UPDATE；重复键路径上的共享锁可能在并发更新时发生锁升级冲突。修复为先通过不改变数据的 ON DUPLICATE KEY UPDATE 获取排他锁，再执行原有受额度限制的扣减，没有放宽额度或增加自动重试。[MySQL 官方锁行为说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)支持该锁行为分析。

新增测试还验证：10 个并发请求、额度为 3 时，必须恰好放行 3 个、拒绝 7 个，账本累计为 3；数据库异常不能被误算成正常拒绝。

## 阻塞模型探针

每档先让指定数量的分析工作线程进入阻塞模型替身，断言该调用点没有活动业务事务；保持阻塞时再执行 3 次创建并更新工单。数据库连接池上限为 10。

| 阻塞模型数 | 等待时活跃 DB 连接采样 | 核心写入 p50 | 核心写入 p95（最近秩） | 错误 |
|---|---|---|---|---|
| 5 | 0 | 28ms | 30ms | 0 |
| 10 | 0 | 25ms | 26ms | 0 |
| 20 | 0 | 22ms | 23ms | 0 |

这是同一 Windows 主机与 Docker Desktop 隔离中间件上的小规模可用性探针。每档只有 3 次核心写入，p95 实际为该档最大样本；不能用作稳定吞吐、生产容量或 RabbitMQ 全链路性能结论。模型解除阻塞后所有相应分析任务成功结束。

新增服务层并发用例同时验证同版本更新只有一个成功，失败返回 409，版本只增加一次，UPDATE 审计只保存一条。原人工确认、权限、租约和 MQ 故障用例一并回归。
