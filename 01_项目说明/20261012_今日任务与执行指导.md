## 5. 第四步：可评审的异步契约初稿

下列设计供下一步编码使用，**尚未创建数据库表、生产者或消费者**。今日先理解并在对应决策记录中确认；沿用当前AI协作总则的“表变更先记录、代码先raw后人工审查”流程。

### 5.1 触发点与结果语义

- 每次新建工单，事务内写工单、CREATE日志、分析任务、Outbox；请求只等待MySQL提交，不等待模型或broker确认。
- 投递器独立发送事件；消费者复用`TicketAnalysisService.analyze`，外部模型调用不持有长数据库事务。
- 初版结果作为建议存储，人工分类/优先级不被覆盖。新增查询`GET /api/tickets/{id}/analysis`返回最新任务状态与可用建议，必须对象级鉴权。
- 工单输入版本变化后，旧任务结果可保留审计但不作为当前建议。首版编辑工单不自动创建新分析任务；显式重新分析作为后续入口。

### 5.2 事件JSON（初稿）

```json
{
  "schemaVersion": 1,
  "eventId": "evt-demo-001",
  "taskId": "task-demo-001",
  "ticketId": 123,
  "inputVersion": 0,
  "traceId": "trace-demo-001",
  "occurredAt": "2026-10-12T10:00:00+08:00"
}
```

时间仅作格式示例。事件不含用户正文；taskId贯穿重试不变，eventId用于投递事件去重，traceId用于排障。重放终态失败任务生成新taskId，并保存原任务引用。

### 5.3 数据设计（拟议，增量迁移后才生效）

| 对象 | 必需内容 | 约束与目的 |
|---|---|---|
| ticket.version | 整数版本，初始0 | 写操作递增；保护旧AI输入与并发写入；实体、写路径、缓存VO同步 |
| ai_analysis_task | taskId、ticketId、inputVersion、generation、status、attempts、nextRetryAt、leaseUntil、traceId、errorCode、时间 | UNIQUE(taskId)及UNIQUE(ticketId,inputVersion,generation)；首次generation=0，重放产生新taskId并递增generation |
| analysis input snapshot | title/description快照，或版本匹配的当前读取策略 | 初版建议消费者领取后读当前工单并比版本；不匹配直接STALE，不试图还原已覆盖文本 |
| ai_analysis_result | taskId、输入版本、分类、优先级、confidence、sourceType、model、promptVersion、costMs、errorCode | UNIQUE(taskId)，与任务终态更新同一事务；规则兜底明确sourceType=RULE |
| outbox_event | eventId、taskId、eventType、payload、status、attempts、nextAttemptAt、leaseUntil、时间 | UNIQUE(eventId)，事务内记录；投递器租约防多实例并发领取；重发是允许行为 |

本初稿选择generation方案，以避免重放与唯一键冲突；同输入首次任务不重复创建，显式重放新增一代。重放接口自身仍须请求幂等键或单次确认机制，避免重复请求创建多代任务；具体迁移前在决策记录固定，不能留给AI随意生成。

现有MySQL数据卷不会自动重跑初始化SQL。新增`02_async_analysis.sql`增量迁移，先在测试库验证、再应用到本地库；同步初始化脚本以支持全新环境，禁止删除现有数据卷升级。具体字段长度、ID类型、索引及回滚方案由决策记录固定。

### 5.4 消息与重试

初始命名：direct exchange `smartticket.ai`、routing key `ticket.analysis.requested`、队列`smartticket.ai.analysis`；持久化交换机/队列及持久消息。业务队列名称与匿名连通测试队列分开。

消费建议采用1次初始尝试+最多2次业务重试，初始退避5秒/30秒，随后终态失败/死信。此为待验证初值。模型SDK维持当前单次尝试，禁止叠加框架默认多轮重试。消费concurrency和prefetch初值各1，先限制模型并发再根据耗时调整。

消息重试使用明确的重试队列/定时调度，不在监听线程内sleep，也不无上限requeue。结果事务成功后ACK；业务降级终态保存后ACK；数据库暂时失败不当作模型成功或终态人工降级。无配置/401等确定性失败不反复计费，非法JSON首版直接降级。任务RUNNING租约与重试调度由下一次实现，不仅靠状态字段名称。

“重复消息不重复落库”不等于“绝不重复模型计费”。消费者在模型调用后、结果入库前崩溃仍有重复调用窗口；记录该限制，后续按厂商幂等能力/请求缓存改善。
