| 序号 | 决策事项 | 结论 |

## 二、为什么升 Spring Boot，而不是留在 3.3.13

| 方案 | 评估 | 结论 |
|---|---|---|
| A. 留在 3.3.13 + Spring AI 1.0.0-M5/M6 | 里程碑版，API 仍会变动；1.0.0-Mx 线已停止维护 | 否 |
| B. 留在 3.3.13 + 自研 HTTP 客户端调 `/v1/chat/completions` | 可控，但等于放弃「集成 Spring AI」这一章程任务；后续 RAG 的 VectorStore / Advisors / 结构化输出都要自己造 | 否 |
| C. **升到 3.5.14 + Spring AI 1.1.6** | 两者都是 GA；3.5.x 是 3.x 线仍在维护的版本，长期支持到 2026 之后 | **采用** |

**官方兼容矩阵是硬约束**：Spring AI 1.x 基于 Spring Framework 6.2，官方声明支持 Spring Boot 3.4.x / 3.5.x；本项目原为 3.3.13（Spring Framework 6.1），不在支持范围内。

**升级风险评估**：3.5.x 相对 3.3.x 未更换 Jackson 主版本（仍是 Jackson 2），MyBatis-Plus、Spring Data Redis、Validation 的用法均兼容。实际回归结果见第六节：107 个用例 0 失败，无既有用例失败。

## 三、为什么选 OpenAI 兼容 starter

| 方案 | 评估 |
|---|---|
| 某家厂商专用 starter（如仅 OpenAI 官方） | 换厂商要换依赖 + 改代码 |
| **`spring-ai-starter-model-openai`** | **采用**。DeepSeek、通义千问（百炼兼容模式）、Moonshot、本地 vLLM/Ollama 都实现了 `/v1/chat/completions`，**换厂商只改 `base-url` 与 `model` 两行配置**，代码零改动 |

对应的取舍：拿不到各家的私有能力（如某些厂商专有的推理参数、内置联网检索）。阶段2 的需求是「分类 + 优先级推荐 + RAG 检索」，都不依赖厂商私有特性，因此可移植性优先。

候选厂商与配置示例已写进 `application.yml` 注释，避免下次换厂商时又要查文档。

## 四、AI 通道的可用性契约（本次最关键的设计）

AI 是**可选增强**，不是主流程的必需依赖。章程的验收标准里有一条「AI 失败时不会导致工单创建失败」，本设计把它从"要注意的编码要求"变成"结构上不可能违反"：

```text
上层（分类/推荐服务）
        │  只依赖 AiChatService，返回 AiCallResult
        ▼
AiChatService.chat(system, user)
        │
        ├─ 未启用 / 未配密钥 / 模型未装配 → 立刻返回 AI_NOT_CONFIGURED（不发网络请求）
        ├─ 调用抛异常（超时/401/限流/500/解析失败） → 捕获后就地转成 AI_CALL_FAILED
        └─ 正常 → 返回内容 + 耗时 + 模型名
```

三条契约：

1. **不抛异常**：任何失败都以结果对象返回。调用方不需要写 try/catch，也就不会出现"某个调用点忘了包 try"而把工单主流程带崩的情况。
2. **不发无用请求**：未配密钥时直接返回。若不做这层短路，未配置的环境会在每次调用时先撞一次连接超时，白白占用线程（与 DEF-002 同一类问题）。
3. **可观测**：成功与失败都记录 `costMs` 与 `model`，日志里能回答"模型是不是变慢了"。

**为什么密钥占位值不是空串**：Spring AI 装配 `OpenAiApi` 时用 `Assert.hasText` 校验密钥，**留空会让应用直接起不来**（注意是启动失败，不是运行时报错）。因此占位值取 `not-configured`，由业务侧的 `AiChatServiceImpl` 识别该值并降级——框架启动期与业务降级期两件事被分开处理。

## 五、两处容易踩的默认值

### 1. Spring AI 默认重试 10 次、退避 2s → 10s → 50s…

默认值是给"偶发网络抖动"设计的，对本项目是灾难：一次模型故障会让一个 Web 线程被占住数分钟。**已改为 `max-attempts: 1`（不重试）**。分类失败立刻降级更符合工单场景——重试与否应由业务层按幂等性决定，而不是框架默认决定。

### 2. HTTP 超时

模型侧排队时单次调用可能几十秒。不设超时等价于把"慢依赖"直接暴露给 Tomcat 线程池。已设 `connect-timeout: 3s` / `read-timeout: 20s`。

**生效路径已验证**：Spring AI 的 `OpenAiChatAutoConfiguration` 装配 `OpenAiApi` 时会注入容器中的 `RestClient.Builder`（通过 `ObjectProvider` 取），因此 Spring Boot 的 `spring.http.client.*` 对它生效——这一点是读框架字节码确认的，不是照文档猜的。

**三段验证的分工（为什么不是"写个测试就行"）**：

| 测试类 | 验证的层次 | 不覆盖什么 |
|---|---|---|
| `AiChatServiceImplTest` | 本类的分支逻辑：4 条不可用路径、成功、超时、空返回 | Spring AI 的 HTTP 与解析（被 Stub 跳过） |
| `AiConfigurationTest` | 真实 Spring 上下文装配：`ChatClient.Builder` 存在、yml 配置真的绑定、`RetryTemplate` 真的只跑 1 次 | 请求体长什么样 |
| `AiOpenAiProtocolTest` | **真实 HTTP 往返**：起一个 JDK 内置 `HttpServer` 冒充 OpenAI 兼容厂商 | 真实厂商的鉴权与配额 |
| `AiRealVendorSmokeTest` | **真实厂商调用**：密钥是否有效、base-url 与模型名是否对 | 默认跳过（`AI_SMOKE=true` 才跑）；不验证业务逻辑 |

其中 `AiOpenAiProtocolTest` 是本期最有价值的一条：它让「base-url 是否拼成 `/v1/chat/completions`」「model 与 temperature 有没有真的写进请求体」「厂商返回 500 会不会被吃掉」这三件最容易出问题的事，变成了可自动运行的断言，且**不需要任何 API Key、不产生费用、离线可跑**。

**测试与「本机是否配了密钥」解耦（重要）**：三个 AI 测试类各自把 `spring.ai.openai.api-key` 钉成自己需要的值（占位值 / `sk-stub-key`），不读本机 `application-local.yml`。原因是：一旦开发者在本地填了真实 Key，`AiConfigurationTest` 里「通道应判为不可用」的断言就会失败——那是配置生效了，不是代码坏了，但测试会报红灯。已用反证验证过这一风险真实存在（去掉钉值 + 设置 `AI_API_KEY` → 该断言确实失败）。测试属性优先级高于 profile 配置文件，因此钉得住。

`AiConfigurationTest` 存在的直接原因：本项目已在 **Redis 前缀（`spring.redis` vs `spring.data.redis`）** 与 **Jackson 日期格式** 上各踩过一次「配置看着生效、实际没生效」。属性名拼错、前缀写错、被默认值覆盖，都必须在这里被挡住。

## 八、启用自己的模型 Key（操作说明）

两种方式，任选其一：

```powershell
# 方式一：环境变量（推荐，不落文件）
$env:AI_API_KEY = "sk-你的密钥"
$env:AI_BASE_URL = "https://api.deepseek.com"
$env:AI_MODEL = "deepseek-chat"
```

```yaml
# 方式二：application-local.yml（已被 .gitignore 忽略，不会入库）
spring:
  ai:
    openai:
      api-key: sk-你的密钥
      base-url: https://api.deepseek.com
      chat:
        options:
          model: deepseek-chat
```

配置生效的判据：启动日志中 **不再** 出现

```text
WARN  c.smartticket.ai.impl.AiChatServiceImpl : AI 通道不可用，相关能力将降级为人工处理 | reason=...
```

而是出现

```text
INFO  c.smartticket.ai.impl.AiChatServiceImpl : AI 通道就绪 | protocol=openai-compatible | model=...
```

这条日志本身就是"到底有没有真的接上 AI"的唯一可信依据——没有它，很容易出现"以为接了 AI、其实一直走人工"的静默失效。
