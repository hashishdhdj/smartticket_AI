## 一、本次决策事项

| 序号 | 决策事项 | 结论 |
|---|---|---|
| 1 | 双路结果怎么合并 | **RRF（Reciprocal Rank Fusion）**：`score = Σ 1/(60 + rank)`，**只吃名次不吃分数** |
| 2 | 并列名次怎么算 | **dense rank**：分数相同给相同名次，下一名次不跳号 |
| 3 | RRF 的平滑常数 k | **固定 60，不做成配置项**（没有评估集，调它没有依据） |
| 4 | 融合后返回几条 | `fusion.top-n = 3`，**小于**每路的 `top-k = 5`（融合是精排） |
| 5 | 关键词路门槛 | 由 `0.0` 抬高到 **`0.2`**（按实测分数分层标定） |
| 6 | 结果里要不要标注来源 | **要**。`FusedHit.sources()` 记录来自哪几条路，`fromBothPaths()` 标记两路都召回 |
| 7 | 一条路降级了怎么办 | **部分降级照常融合**，但保留两路原始结果，`degradedSources()` 显式指出哪条路降级 |
| 8 | 两条路是串行还是并行 | **串行**。并发隔离留到阶段3（见第八节） |

## 二、为什么是 RRF：分数不可直接加权

第6天的实测留下一个无法回避的事实（见 `20261008_RAG双路检索.md` 第二节）：

| 查询 | 向量路分数 | 关键词路分数 |
|---|---|---|
| `重复扣款如何申请退款` | 0.65 ~ 0.81 | 0.1818 / **0.3636** |
| `钱被扣了但订单没出来` | 0.6495 ~ 0.7649 | 全是 0.0909 |
| `我的账号登不进去了，怎么办` | 0.5649 ~ 0.7010 | 全是 0.1429 |

两条路的分数**量纲完全不同**：向量路的余弦相似度集中在 0.5~0.8，关键词路的 `word_similarity`
集中在 0.09~0.36。这不是"换算一下"能解决的，因为两者不是同一把尺子：

- 把两者的分数**归一化后加权**：权重要按查询类型调，没有评估集就调不出合理值；
- 把两者的分数**直接相加**：向量路的贡献会系统性压倒关键词路（0.7 对 0.1），双路退化成单路。

RRF 绕开了这个问题——**它只看名次，不看分数**：

```text
score(切片) = Σ_runs 1 / (k + rank(切片在该路的名次))     k = 60
```

**这里的"名次"是真的信号**：不管两路的分数量纲差多少，"在这条路里排第几"是可比的。
某条切片如果在向量路排第 1、关键词路也排第 1，它的融合分就是 `1/61 + 1/61`，
自然压过"只在一条路排第 1"的切片（`1/61`）。

`k = 60` 是 RRF 原论文的取值，作用是**压平头部差距**（让 `1/61` 与 `1/62` 不至于差太多，
避免单路的第一名一票否决）。**它刻意没做成配置项**——本项目还没有评估集，
把 k 暴露成配置项等于邀请别人在没有依据的情况下乱调。

## 三、dense rank：并列必须给相同名次

第6天遗留的第 1 条问题就是它（见上游记录第八节）：**关键词路的分数大量并列**，
而并列时的顺序是由 tie-break（`source_file, chunk_index`）决定的——那是**字典序，不是相关性**。

如果按"位置"排名次（`rank = 下标 + 1`），并列的四条会被拆成第 1、2、3、4 名，
于是 RRF 把**字典序当成了相关性信号**。dense rank 修正这一点：

```text
分数序列：  0.3636, 0.1818, 0.1818, 0.1818
位置名次：   1,      2,      3,      4       ← 错：把字典序当相关性
dense rank： 1,      2,      2,      2       ← 对：并列同分同名
```

实现上不需要预先给整列排名——**在累加贡献的那一次遍历里就能算出来**：

```java
int rank = 0;
Double previousScore = null;
for (RetrievalHit hit : hits) {
    if (previousScore == null || Double.compare(hit.score(), previousScore) != 0) {
        rank++;                    // 分数变了才是新名次
        previousScore = hit.score();  // 分数相同则沿用上一个名次
    }
    ...
}
```

## 四、门槛标定：`keyword-min-score` 由 0.0 抬高到 0.2

第6天遗留的第 2 条问题：关键词路在"零字面重合"的查询上会返回**有分数但毫不相关**的结果，
这些结果如果原样进融合，会污染最终结果。**这不是推理，是实测**——
在一次向量路因网络超时降级的运行里，融合结果直接暴露了污染：

```text
---------- [融合] query = 我的账号登不进去了，怎么办 | hits=3 | 降级来源=[VECTOR]
[融合] #1 faq/02-支付问题.md > 支付成功但订单未生成怎么办     ← 与"账号登不进去"无关
[融合] #2 faq/02-支付问题.md > 如何申请开具发票             ← 无关
[融合] #3 faq/04-工单流程与通用问题.md > 如何查询工单处理进度  ← 无关
```

### 标定依据（同一批语料、同一模型实测）

把门槛从 0.0 调到 0.2 之前，先看**分数是怎么分层的**：

| 查询 | 门槛=0.0 | 门槛=0.2 | 被挡掉的分数 |
|---|---|---|---|
| `我的账号登不进去了，怎么办` | 3 条（全无关） | **0 条** | 0.1429 ×3 |
| `钱被扣了但订单没出来` | 4 条（全无关） | **0 条** | 0.0909 ×4 |
| `重复扣款如何申请退款` | 5 条 | **1 条** | 0.1818 ×4 |

三组数据给出清晰的分层：

```text
0.3636       查询词在正文中连续出现（真词命中）          → 保留
0.1818       多个实词零散命中                           → 挡掉
0.09 ~ 0.14  只命中"的/怎/么/办"这类虚词（与问题无关）  → 挡掉
```

**0.2 恰好落在 `0.1818` 与 `0.3636` 之间的空档里**，因此它不是拍脑袋取的中间值，
而是唯一一个能同时做到"挡住噪声"与"保留精确命中"的位置：

- `我的账号登不进去了，怎么办`：3 条无关 → **0 条**（挡住噪声）；
- `重复扣款如何申请退款`：精确命中那条 **0.3636 完好保留**（不误伤真命中）。

**局限（已写入配置注释）**：该值基于当前 **26 条演示语料**标定，语料大改后应重新标定。
它不是一个"通用最优阈值"，而是"这批语料上唯一落在空档里的值"。

## 六、来源标注与部分降级可见

### 6.1 `FusedHit` 记录来源

```java
public record FusedHit(KnowledgeChunk chunk, double fusedScore, Set<RetrievalSource> sources) {
    public boolean fromBothPaths() { return sources.size() > 1; }
}
```

- `sources` 用 `EnumSet` 拷贝：枚举的迭代顺序是**声明顺序**（VECTOR、KEYWORD），
  结果稳定、日志可读；换成 `Set.copyOf` 顺序就变成未定义，会让日志与测试断言随实现漂移。
- `fromBothPaths()` 让"两路都召回的切片"一眼可辨——**它是融合后最值得看的一类结果**。

（第6天曾把 `source` 放在 `RetrievalHit` 上，后因与 `RetrievalResult.source()` 构成两个真相而移除；
这里 `FusedHit.sources` 是**集合**，语义是"融合后这条切片由哪些路贡献"，与单条路的 `source` 不冲突。）

### 6.2 部分降级必须可见

`KnowledgeSearchResult` 同时保留**融合结果**与**两条路的原始结果**：

```java
public record KnowledgeSearchResult(List<FusedHit> hits,
                                    List<RetrievalResult> pathResults,
                                    long costMs) {
    public List<RetrievalSource> degradedSources() { ... }
    public boolean fullySuccessful() { return degradedSources().isEmpty(); }
}
```

**为什么不只返回 `hits`**：如果只返回融合后的 3 条，调用方分不清
"结果少是因为库里确实没有"还是"一条路挂了导致召回面变窄"。保留 `pathResults`
让第 5 周的置信度判断能拿到真实依据——**降级时的"低置信度"应当触发转人工，而不是被当成"没找到"。**

`KnowledgeSearchServiceImpl` 的日志也相应分两档：全成功记 `INFO`，有降级记 `WARN`（含 `degradedSources`）。

## 七、去重：融合键 `source_file#chunk_index`

第6天遗留的第 5 条（未做检索结果去重）在这里自然解决：
融合时以 **`source_file#chunk_index`** 作为切片的唯一键做累加。

```java
private static String keyOf(KnowledgeChunk chunk) {
    return chunk.sourceFile() + '#' + chunk.chunkIndex();
}
```

这个键与向量表的唯一约束 `uk_knowledge_chunk_source` 一致，因此**同一小节的不同切片不会互相覆盖**
（切片的 `chunk_index` 不同），**同一切片在两条路里只会累加成一个候选**（键相同）。

另外对"同一条路"做了保护：`Accumulator.add(source, contribution)` 只在 `sources.add(source)`
返回 true（首次见到这条路的贡献）时才累加分数，避免同一条路对同一切片重复计分。

## 八、串行执行，不引入并发

`KnowledgeSearchServiceImpl` 现在是**串行**调用两条路：

```java
RetrievalResult vectorResult  = retrievalService.searchByVector(query);
RetrievalResult keywordResult = retrievalService.searchByKeyword(query);
```

实测耗时：向量路是瓶颈（一次嵌入调用 0.3~1.7s），关键词路是毫秒级（1~33ms）。
两者加起来约等于向量路本身——**串行没有带来额外的可观开销**。

**为什么不在第7天就并发**：这需要引入线程池与超时隔离，属于"跨调用恢复"的基础设施，
是阶段3 的范畴。现在做会把一个纯函数式的融合逻辑，绑进一个需要管理生命周期的组件里，
**在第5周还要反复调检索参数的阶段，这是负债而不是收益。**
