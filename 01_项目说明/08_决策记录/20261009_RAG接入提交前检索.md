## 一、本次要解决的问题

前两周（第4~5周）把 RAG 的**引擎**做完了：切分、向量化、双路检索、RRF 融合、置信度阈值、建议生成——
**全部有实测数据支撑，但没有一个人能调用它**。它是一间上了锁、还没装门的房间。

章程模块三（L266-277）写的核心功能，有一半是**流程接线**：

> - 用户提交工单前，先进行知识库检索；
> - 返回相似问题；
> - 返回推荐解决方案；
> - 处理人回复时，AI推荐历史工单和处理方案；
> - 低置信度时强制走人工流程。

本次完成的，就是其中最靠前、也最能体现价值的那一条：**提交前检索 + 返回相似问题**。

## 二、插入点：三个候选，为什么先做 A

| 插入点 | 形态 | 改表？ | 风险 | 结论 |
|---|---|---|---|---|
| **A 提交前检索** | 新增 `POST /api/ai/knowledge/answer`，薄 Controller 暴露现有引擎 | 否 | 极低 | **本次采用** |
| B 并进 AI 分析接口 | 在 `POST /api/ai/tickets/analyze` 的返回里加上建议与来源 | 否 | 低 | 后续 |
| C 创建工单时落库 | 在 `TicketServiceImpl.create()` 里调 AI+RAG 并把结果写回工单 | **是**（需加 `ai_*` / `need_human` 列） | 高 | 后续（依赖模块四的异步） |

**为什么先做 A**：

1. **它是章程的原话**（L273"用户提交工单前"），最能体现"用知识库把工单挡在前面"这个产品意图；
2. **不改表、不改任何现有代码**——只在既有引擎外面加一层接口，风险最低；
3. 它是**验证闭环的第一步**：引擎再准，没有门就没有任何价值能被观测到。做完 A，整条链路第一次可以用 Postman 跑通。

**C 为什么不能现在做**：AI 调用要 1~2 秒，把它塞进 `create()` 的 `@Transactional` 里会长时间占住数据库连接——
正是 `connection-timeout=5000` 想防的那类故障（DEF-002 同源）。正确形态是"先落库返回、再后置补写"，
而**异步是模块四**的事。硬做会引入一个已知会坏的形态。

## 三、接口设计

```
POST /api/ai/knowledge/answer
  { "query": "重复扣款如何申请退款" }
→ Result<KnowledgeAnswerVO>
  { matched, needHuman, confidence, suggestion, similarQuestions[],
    sources[{sourceFile,title,score,summary}], degradedSources[], costMs }
```

| 决定 | 理由 |
|---|---|
| 新开 `KnowledgeController`（前缀 `/api/ai/knowledge`）而不是塞进 `AiController` | 与 `AiController` 用 `/api/ai/tickets` 同一取舍：本接口不以某个工单 id 为主键，是"对一个文本问题做检索"，与工单的资源层级不同 |
| 必须有 `KnowledgeQueryDTO` / `KnowledgeAnswerVO` | 硬约束：入参用 DTO 带校验，出参用 VO。**`RagAnswer` 是内部记录，不能直接当接口出参**，否则内部结构一改就是接口契约变更 |
| query 长度上限 500 | 与切片上限同值。过长不是"更能检索到"而是**稀释**：嵌入会把多个意图平均掉，关键词相似度的分母也变大。比一条切片还长的"问题"本质已是描述，该走工单 |

## 四、表述层：降级为什么走成功响应

与 `TicketAnalysisVO` 同一取舍（见其类注释），但**有一处刻意不同**：

| | AI 分析接口 | 知识库接口 |
|---|---|---|
| 降级时的返回 | `code=0` + `degraded=true` + `degradedReasonCode` | `code=0` + `needHuman=true` + `degradedSources` |
| 是否带原因码 | 带（10006/10007/10008） | **不带** |

**不带原因码的理由**：对"提交前检索"来说，调用方对**"没查到知识"与"检索降级"的处置完全相同**——
都引导用户继续提单。既然调用方不区分，透出原因码只会多一个没人用的字段（那正是"过度设计"）。
降级细节写日志，`degradedSources` 保留"哪条路挂了"用于排查。

而 `needHuman` 这一个布尔值就够调用方做决策：

```
needHuman=false → 展示建议 + 相似问题 + 依据来源，用户可能自助解决
needHuman=true  → 引导用户继续提单，进入人工流程
```

## 五、Prompt v2：为什么改成结构化输出

章程要求「返回相似问题」，而 `rag-answer-v1` 只输出一句自由文本。两个选择：

| 方案 | 代价 |
|---|---|
| **并入同一次调用**，输出改成 JSON `{suggestion, similarQuestions[]}` | 要改刚验证过的 Prompt，并新增一条"解析失败"路径 |
| 另开一次调用专门改写问句 | 保住原 Prompt、失败隔离，但**每个高置信查询多一次往返（约 1 秒）与一次计费** |

**选第一种**。关键理由是**这个接口的使用场景**：用户在提单页等着，两次串行调用会把等待拉到 2 秒以上；
而 RAG 的两条检索路当前也是串行的，本就没有并发余量。**延迟对"提交前检索"是体验问题，不是纯技术指标。**

**代价是可控的**，因为项目已经有成熟先例：`AiClassificationParser` + `AiResponseInvalidException` 这套
"结构化输出 + 严格校验 + 失败即降级"的写法，照搬即可。

## 六、解析器：校验到哪一层为止

`RagAnswerParser` 沿用分类解析器的严格风格：**要么全部通过、要么抛异常，不存在"部分合法就先用着"**。
一个字段不合规就整份作废——因为模型少字段/多字段/超长，都说明它没有按结构走，同一响应里别的字段同样不可信。

**但校验只到"结构与长度"为止，不到"措辞与语义"**：

| 校验 | 不校验 |
|---|---|
| 是不是合法 JSON | 问句是否以问号结尾（外观，缺了不影响能不能用） |
| 字段是否齐全、是否多出字段 | 这条问句是否**真的出自资料**（需要语义判断，正是模型在做的事） |
| 建议 ≤200 字、相似问题 1~5 条且每条 ≤40 字 | 建议是否"好" |

**这条界线必须写明**，否则会误以为解析器能挡住一切跑偏。实测中它确实没挡住一类跑偏——见第九节。

**关于为什么没有配套的 JSON Schema 文件**（分类那套有一个）：
那个 schema 的存在价值是"语言无关的契约 + 由测试守护 Java 常量"。
但 RAG 输出的边界**已经写在模板（对模型）与解析器常量（对代码）两处**，
再加第三个文件就是同一份契约的第三份拷贝——本项目一贯不接受"多份真值"。
如果将来需要把这份契约交给外部工具校验，再补不迟。

## 八、一个必须记下的运维风险

**这个接口会真实调用模型并计费，而项目当前没有任何鉴权与限流。**

- 章程明确"不要实现复杂权限"，所以这不是遗漏，是范围；
- 但**"没有权限的接口"与"没有权限且会花钱的接口"是两件事**：
  前者最多被人乱查，后者可以被用来刷账单；
- 本次只加接口、不加防护，**属已知边界**。上线前必须至少补一层：接口鉴权 + 调用频控 + 单日成本上限。

已登记为遗留项。

## 九、已知限制与遗留

| # | 问题 | 影响 | 处理时机 |
|---:|---|---|---|
| 1 | **相似问题会"顺着主题发散"**：实测 4 条里有 2 条在知识库中查不到对应内容 | 用户点进去会看到"没查到"，不至于误导，但不符合 Prompt 约定 | 候选方案见下 |
| 2 | 检索两路 + 模型生成**全是串行**，端到端约 1.9s | 用户在提单页等待 | 阶段3（并发隔离） |
| 3 | 无鉴权、无频控、无成本上限（第八节） | 接口可被滥用刷账单 | 上线前必须补 |
| 4 | 语料仍是 26 条演示数据 | 阈值 0.66 只对这批语料成立 | 接入真实 FAQ 后重新标定 |
| 5 | 未做 B（并进分析接口）与 C（创建时落库） | "AI 自动填单"的闭环仍未打通 | 后续；C 依赖模块四的异步 |
| 6 | 该接口**不写库** | 检索结果没留痕，无法统计"有多少工单本可被知识库挡掉" | 若要看这个指标，需要落一张检索日志表 |

**第 1 条的候选改进（本次未实施）**：把相似问题从"自由发散"改为**与资料一一对应**——
Prompt 改成"为每一条资料各生成一条，条数与资料条数相同"，并在**服务层**（不是解析器）校验
`similarQuestions.size() == sources.size()`。
好处是条数变成可机械校验的约束，迫使模型逐条对着资料写；代价是资料只有 1 条时展示会单薄。
**取舍留到有真实用户反馈后再定，现在不提前优化。**
