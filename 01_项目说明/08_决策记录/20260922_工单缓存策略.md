## 二、采用模式：Cache-Aside

```text
读（getById）：
  查 Redis ──命中──→ 反序列化为 TicketVO → 返回
      │
      未命中
      ↓
   查 MySQL（requireTicket）→ 转 VO → 写回 Redis（TTL 10 分钟）→ 返回

写（update / close / assign）：
  改 MySQL → 删 Redis        ← 是「删除」，不是「更新缓存」
```

**为什么写路径删缓存而不是更新缓存**：更新缓存需要重新组装完整对象，并要处理两个并发写互相覆盖的问题；删除只有一个动作，代价仅是下一次读回源一次。复杂度低且不易出错。

**为什么缓存的是 `TicketVO` 而不是 `Ticket` 实体**：缓存内容应当就是"接口需要的数据"，这样缓存与出参语义一致，且不会把 `deleted` 这类内部字段写进 Redis（已有测试断言守护）。

## 三、缓存 key 与 TTL

| 项 | 取值 | 理由 |
|---|---|---|
| key 前缀 | `ticket:detail:` | 冒号分层，便于 `redis-cli --scan` 按前缀查看，也为后续 `ticket:list:*` 预留命名空间 |
| 完整 key | `ticket:detail:{id}` | 详情是 `id → 单据` 的点对点映射，天然适合 key-value |
| TTL | 10 分钟 | **TTL 是兜底而非主角**：一致性靠写操作主动删除；TTL 只保证「万一某条写路径漏删」时脏数据不会永久驻留 |

选择「只缓存详情、不缓存分页列表」的原因：分页的条件组合（页码 × 条数 × 状态）会膨胀出大量 key，命中率低且失效边界难以界定；详情查询的 key 唯一、失效目标明确。

## 四、删缓存覆盖范围（对指导清单的补充）

指导清单第 9 天只列出「更新工单时删除缓存」「关闭工单时删除缓存」。本次实际实现覆盖**三处**：

| 写操作 | 修改的数据 | 是否删缓存 | 说明 |
|---|---|---|---|
| `update` | title / description / category / priority / tags | 是 | 清单已列 |
| `close` | status → CLOSED | 是 | 清单已列 |
| `assign` | **status（待分配→处理中）、assigneeId** | 是 | **清单未列，本次补充** |

补充 `assign` 的理由：指派会同时改动状态与处理人，若不清缓存，接口在 10 分钟内会返回"旧处理人 + 旧状态"，是明确的脏读。这与 `20260918_工单状态机.md` 中「允许重开」的决策构成连带影响——凡改动工单数据的写路径，都在删缓存范围内。

**顺序约定**：一律「先改库，后删缓存」。反过来的话，若改库失败，缓存已被删掉，用户会看到"缓存白删 + 数据没变"的组合。

## 五、已知限制

### 1. 事务内删缓存存在并发窗口期

```
T1: 改库(未提交) → 删缓存 → 提交
T2: 在 T1 提交前读缓存 → 未命中 → 查库读到旧值 → 把旧值回填进缓存
结果：缓存中驻留旧数据，直到 10 分钟 TTL 到期才自愈
```

彻底解决需把删缓存挂到事务 `afterCommit` 阶段。**本次不实现**：指导清单明确要求「不实现延迟双删」，且阶段1 是单实例最小骨架，无并发压测场景。此处登记为已知限制。

### 2. 缓存层故障会导致详情查询失败（无降级）

`getById` 的第一步是读 Redis，**Redis 不可用时整个查询抛 `RedisConnectionFailureException`**，不会自动降级为直接查库。这一现象在第9天回归测试中被真实触发（Docker 引擎未启动导致 3306/6379 同时不可达）。

阶段1 最初不处理的理由：降级逻辑（try-catch 包住缓存操作、失败则走库）属于可用性加固，不在最小骨架范围内。**但它是一个真实缺陷**，已登记至下方遗留问题。

**2026-09-22 更新（用户决定）**：本项**改为纳入阶段1 收尾处理**，不再作为"不处理"项。判断依据是：缓存是可选的加速层，其故障不应导致工单详情这一核心查询整体不可用——这属于可用性问题，而非可选增强。具体实现方式（缓存操作异常捕获范围、是否记录降级日志）留到收尾时确认。

### 3. 缓存无防击穿保护

热点 key 失效瞬间的并发回源未做互斥（不加分布式锁，符合清单要求）。

**关键用例 `secondQueryIsServedFromCache` 的证明手法**（不依赖日志，可自动断言）：

1. 直插工单 → 第一次 `getById` 建立缓存；
2. **绕过 Service 用 `JdbcTemplate` 直接改库**，把 title 从「旧标题」改成「新标题」；
3. 第二次 `getById` → 断言返回的**仍是「旧标题」**（说明这次读取没有碰数据库，只可能来自缓存）；
4. 删掉缓存 key 后再查 → 断言返回「新标题」（**双向反证**，排除"数据库更新失败"这一替代解释）。

若只有第 3 步，无法排除"改库没生效"；加了第 4 步才构成完整证据链。

其余用例覆盖：首次查询回填 + TTL 在 (0, 600] 秒、更新/关闭/指派三处删缓存、不存在的 id 抛 10003 且不写缓存（防穿透）、缓存内容为可读 JSON 且不含 `deleted`。
