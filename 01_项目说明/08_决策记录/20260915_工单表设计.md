## 三、与阶段一指导第2天约束的逐条核对


## 四、关键取舍与理由

| 取舍 | 选择 | 理由 |
|---|---|---|
| 状态/优先级存储 | VARCHAR 而非 ENUM | 增删取值不需要 DDL；且状态合法性由第5天状态机在应用层单点保证，避免"DB 与应用两份真相" |
| 逻辑删除 | `deleted TINYINT` | 与 MyBatis-Plus `@TableLogic` 的 0/1 语义直接对齐 |
| 时间戳维护 | 交给 DB 默认值与 `ON UPDATE` | 应用层不必重复赋值；代价是逻辑删除等操作也会刷新 `updated_at` |
| 日志表无 `deleted` / `updated_at` | 只追加不修改 | 操作日志是审计数据，不允许删改；加这两个字段反而会诱导误用 |
| 日志表保留 `from_status`/`to_status` 两个字段 | 保留 | 状态流转审计需要"从哪到哪"，只有 `to_status` 无法还原 |
| 主键自增策略 | 单库自增 BIGINT | 当前是单体单库（章程 1.5.2 明确不做分库分表），分布式 ID 无收益 |

## 五、被否决的方案

| 方案 | 否决理由 |
|---|---|
| `status` / `priority` 用 ENUM | 每次调整取值都要 DDL，且与 MyBatis-Plus 枚举映射、状态机校验重复 |
| 日志与工单合表（不加 `ticket_log`） | 一个工单会多次流转，合表会破坏主表字段语义，也无法保留完整审计链 |
| `tags` 用 JSON 类型或独立关联表 | 阶段1 只做最小骨架，关联表属于范围外；JSON 多值索引在检索场景尚未确认 |
| `ticket_no` 用主键代替 | 业务编号需要对外可读、可检索，且不应暴露自增规模 |
| 所有查询键都建单列索引 | 索引越多写入越慢；`idx_status_priority` 的最左前缀已能覆盖 `idx_status` 的场景 |
