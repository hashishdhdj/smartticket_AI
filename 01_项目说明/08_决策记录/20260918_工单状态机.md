## 三、合法流转矩阵

| 当前状态 | 允许流转到 | 业务理由 |
|---|---|---|
| 待分配 `PENDING_ASSIGN` | 处理中 / 已挂起 / 已关闭 | 指派后开始处理；等外部信息可挂起；误创建可作废 |
| 处理中 `PROCESSING` | 待反馈 / 已解决 / 已挂起 / 待分配 | 请用户确认→待反馈；处理完→已解决；挂起；转派→回待分配 |
| 待反馈 `PENDING_FEEDBACK` | 处理中 / 已解决 / 已挂起 | 用户回复→继续处理；用户确认→已解决；长期无响应→挂起 |
| 已解决 `RESOLVED` | 已关闭 / 处理中 | 确认关闭；或发现未修复→重新打开 |
| 已挂起 `SUSPENDED` | 处理中 | 恢复处理 |
| 已关闭 `CLOSED` | 处理中 | 重开 |

**白名单边数 = 14**（3+4+3+2+1+1），6×6=36 种组合中其余 22 种全部拒绝。

一律拒绝的两类：

1. **自身流转**（任意 `X → X`）：避免无意义的状态变更污染 `ticket_log`；
2. **跳步流转**：如 `待分配 → 已解决`、`待分配 → 待反馈`、`已挂起 → 待分配`、`已解决 → 待分配`。

有意排除的边：`待反馈 → 已关闭`。理由：关闭必须经过「已解决」，使第7天的关闭接口具备实质校验，而不是"任意状态都能关"。

## 四、关键取舍与理由

| 取舍 | 选择 | 理由 |
|---|---|---|
| 流转规则存放位置 | **枚举内部**静态白名单 + `checkTransitionTo` | 规则与取值同处一个类，高内聚；对外只有一个校验入口 |
| 校验入口数量 | **唯一入口**，禁止在 Controller/Service 另写 if-else | 规则复制成多份必然不一致；第7天指派/关闭接口只能调用同一方法 |
| 白名单集合类型 | `Set.of(...)`（不可变） | `EnumSet` 可变：外层 `unmodifiableMap` 只保护 Map 结构，挡不住拿到集合后 `add` 篡改规则（本次实测已踩，见第七节） |
| 非法流转的异常 | `BusinessException(INVALID_STATUS_TRANSITION=10001)` | 抛 `IllegalArgumentException` 会被系统异常兜底成 50000，语义错位 |
| 未知状态值的处理 | `fromCode` 抛 `BusinessException(UNKNOWN_STATUS_CODE=10002)` | 库中/请求中出现未确认状态时明确失败，而不是静默当成默认值 |
| 中文描述 | 枚举持有 `description` 字段 | 提示信息与后续前端展示共用一处，避免中文散落在代码里 |
| 优先级枚举范围 | 仅 `LOW/MEDIUM/HIGH/URGENT` + 中文描述 | 阶段一指导只要求"定义优先级枚举"；排序权重未确认，不提前引入 |

## 五、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 独立的 `TicketStateMachine` 类持有规则 | 规则与枚举取值分离，两处都要看；本阶段规则量小，收益不足 |
| DB 加 `CHECK` 约束保证状态合法 | 状态**流转**是跨字段的历史判断，DB 无法表达；且会形成"DB 与应用两份真相"（同时关闭上游记录的待决问题 3） |
| 把流转矩阵写在配置文件里 | 规则是编译期常量、无运行时变更需求，配置化只增加读取失败与校验成本 |
| 实体 `status` 直接改为枚举类型（`@EnumValue`） | 阶段一指导第5天明确"不涉及数据库操作"；绑定会牵动第3天实体的映射验证，且需要连库回归，收益不足以在本日承担 |
| 允许 `待反馈 → 已关闭` | 会使关闭接口失去校验意义；需要关闭时先转为已解决，语义更严格 |
| 让 `TicketPriority` 携带排序权重 | 库中 `priority` 为 VARCHAR，按优先级排序的实现方式（应用层映射 / SQL `CASE` / 冗余排序列）尚未决定，属第6天分页排序议题 |

## 六、对后续阶段的影响

1. **第6天（工单 CRUD）**：已兑现。`TicketServiceImpl#page` 用 `TicketStatus.fromCode(status)` 校验分页筛选参数，非法状态值返回 10002，而不是静默查空；实体的 `status`/`priority` 保持 `String`，应用层按需转换（**未**绑定枚举，与第 3 条决策一致）。
2. **第7天（指派 / 关闭）**：指派与关闭的状态变更**必须**经 `checkTransitionTo`，不得直接 set `status`；`ticket_log` 的 `from_status`/`to_status` 直接取流转前后的枚举名。
3. **第9天（详情缓存）**：由于「允许重开」，已关闭的工单仍可能被修改为新状态，缓存方案必须同时覆盖"关闭清缓存"与"重开清缓存"，否则前端会读到已关闭的旧快照。
4. **第8天（引入 Redis）**：不涉及状态规则，无影响。

### 7.2 测试抓到的两个真实缺陷（均已修复）

| # | 现象 | 根因 | 修法 |
|---:|---|---|---|
| 1 | `allowedNextStatusesIsUnmodifiable` 失败：期望抛 `UnsupportedOperationException` 却没抛 | 只对 Map 做了 `Collections.unmodifiableMap`，内层 `EnumSet` 仍可变 | 内层改为 `Set.of(...)`（构造即不可变） |
| 2 | `illegalTransitionThrowsBusinessException` 失败：期望抛业务异常却没抛 | 缺陷 1 的用例真的往共享集合里 `add` 成功，把「待分配 → 已解决」改成了"合法"，**污染了另一个用例** | 随缺陷 1 一并修复，集合不可变后不再有跨用例污染 |

**价值**：若无"白名单必须只读"这条断言，这个可变集合会一直存在；第7天只要有人不小心修改集合，状态机规则就会被静默篡改且极难排查。

### 7.3 错误码重复定义（真实发生过）

`ErrorCode` 曾出现 `10001`、`10002` 各被定义两次（两批常量码值相同），**Java 编译器不报错**。已合并去重，并新增守护测试 `ErrorCodeTest`：

- 码值不允许重复；
- 非成功码必须落在 1xxxx / 4xxxx / 5xxxx 分段内；
- 每个码都有非空文案。
