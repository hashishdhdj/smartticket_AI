## 二、为什么必须是两条路（本次实测的核心证据）

章程要求"双路检索 + 合并"。这不是为了凑设计，而是**两条路各有明确的失效模式**，
用同一批语料和同一个模型实测出来的对照就是证据。

### 证据一：口语化且字面零重合的查询——关键词路全军覆没

查询 `我的账号登不进去了，怎么办`（注意："登不进去"这个说法在语料里**从未出现过**）

| 排名 | 向量路 | 关键词路 |
|---|---|---|
| #1 | 0.7010 `faq/01-账户问题.md > 账号被锁定如何解锁` | 0.1429 `faq/02-支付问题.md > 支付成功但订单未生成怎么办` |
| #2 | 0.6900 `faq/01-账户问题.md > 登录时提示「验证码异常」怎么办` | 0.1429 `faq/02-支付问题.md > 如何申请开具发票` |
| #3 | 0.6535 `faq/01-账户问题.md > 如何重置登录密码` | 0.1429 `faq/04-工单流程与通用问题.md > 如何查询工单处理进度` |
| #4 | 0.5809 `tickets/01-账户问题.md > 登录页反复提示验证码错误…` | — |
| #5 | 0.5649 `tickets/01-账户问题.md > 账号被提示永久锁定…` | — |

**向量路 5 条全部落在账户主题；关键词路 3 条全部与问题无关。**
原因是这个句子里与语料有字面重合的只剩"的/怎/么/办"这类虚词，于是匹配到了毫不相关的内容。

### 证据二：字面精确的查询——关键词路精确命中

查询 `重复扣款如何申请退款`（语料里有一节标题**逐字相同**）

| 排名 | 关键词路 | 分数 |
|---|---|---|
| #1 | `faq/02-支付问题.md > 重复扣款如何申请退款` | **0.3636** |
| #2~#5 | 支付相关的其他小节 | 0.1818（并列） |

**这一条上关键词路做得比向量路更"准"**：它把同名小节单独挑到了第一位，且分数是第二名的两倍。

### 证据三：口语化但字面还有零星重合——两路都能召回，但排序质量差很多

查询 `钱被扣了但订单没出来`

| 排名 | 向量路 | 关键词路 |
|---|---|---|
| #1 | 0.7649 支付成功但订单未生成 | 0.0909 支付成功但订单未生成 |
| #2 | 0.6882 提示订单已失效但用户称已收到扣款短信 | 0.0909 支付时提示「订单已失效」 |
| #3 | 0.6662 银行卡已扣款但订单列表中没有该订单 | 0.0909 银行卡已扣款但订单列表中没有该订单 |
| #4 | 0.6507 重复扣款如何申请退款 | 0.0909 同一笔订单被扣款两次 |
| #5 | 0.6495 同一笔订单被扣款两次 | — |

两路都召回对了主题，但**向量路的分数跨度是 0.65~0.76（有区分度），关键词路全是 0.0909（完全没有区分度）**。
关键词路这一组结果的先后顺序实际上是由 tie-break（`source_file, chunk_index`）决定的，**不是由相关性决定的**。

**结论**：一条路不行的地方另一条能补，这正是双路存在的理由。

## 三、关键词检索为什么用 `word_similarity` 而不是 `similarity`

中文没有空格分词，PostgreSQL 默认的 `to_tsvector` 会把一整句中文当成一个 token，全文检索等于没用。
`pg_trgm`（PostgreSQL contrib，`pgvector/pgvector:pg16` 镜像已内置 1.6）提供的是**字符三元组**相似度，
不做分词也能用。但它有两个函数，**选错会得到完全无用的结果**——这不是推理，是实测：

| 函数 | 含义 | 在 26 条语料上的实测表现 |
|---|---|---|
| `similarity(query, content)` | 两者三元组**集合**的相似度 | 最高只有 **0.019**（短查询被长正文的分母稀释），完全没有区分度 —— **不能用** |
| `word_similarity(query, content)` | query 与 content 中**某一段连续三元组**的最大相似度 | 能正确排序，见第二节证据 —— **采用** |

另外用最小用例确认了它的语义边界，避免误诊：

| 用例 | `word_similarity('验证码异常', …)` |
|---|---|
| `'验证码异常'`（完全相同） | 1.0 |
| `'登录时提示「验证码异常」怎么办'`（**连续包含**） | 1.0 |
| `'输入验证码后提示异常或错误'`（不连续） | 0.1667 |
| `'收不到验证码短信怎么办'`（只有"验证码"命中） | 0.1667 |

**一个值得记下的排查过程**：第一版探针用 `'验证码异常'` 去查，结果主题完全对应的那一节只得了 0.1667，
而一节无关内容却得了 0.5，看起来像"排序错了"。追下去才发现**那一节的正文写的是
"输入验证码后提示异常或错误"，并没有连续出现"验证码异常"这个词**——作为纯字面匹配，
给 0.1667 恰恰是**正确**的。**问题出在探针用"标题"当查询，而不是函数选错了。**
（那节得分 0.5 的切片，正文里有一个独立的"验证码"词，词边界填充让它命中了查询的 3/6 个三元组。）

**代价**：`pg_trgm` 是字面匹配，不认同义改写；且分数普遍偏小（当前语料最高 0.36）。
**接受**：这正是它与向量路互补的地方；分数偏小不影响使用，因为第7天的融合用的是**排名**（RRF）而不是分数。

## 四、两路的分数方向必须统一

向量路的 `<=>` 是 pgvector 的**余弦距离**（0 = 完全相同，越大越远，"越小越好"）；
关键词路的 `word_similarity` 是相似度（"越大越好"）。两者方向相反。

**统一成"越大越相关"**，在 SQL 里直接换算：

```sql
1 - (embedding <=> ?) AS score
```

**为什么在 SQL 里换算而不是在 Java 里**：`ORDER BY` 里用的是距离表达式 `embedding <=> ?`，
这样 PostgreSQL 才能用上 HNSW 索引做近邻扫描；若改成按别名的相似度降序排，索引就废了。

**代价**：Java 侧看到的 `score` 与 SQL 里 `ORDER BY` 的表达式不是同一个东西，读代码时需要留意。
已在仓库方法上写明。

## 五、查询向量与库中向量必须同源（新增 10010）

第5天补过一个幂等条件：**换嵌入模型后要重新索引**，否则库里会混装两个模型的向量。
第6天在检索侧补上对应的防御——**查询向量与库中向量不同源时拒绝检索并降级**：

```text
读库中 SELECT DISTINCT model
 ├─ 为空                → 10009（库里还没数据，提示先建索引）
 ├─ 不唯一 或 ≠ 当前配置 → 10010（不同模型的向量空间不可比，请重建索引）
 └─ 与配置一致          → 正常检索
```

**为什么单独一个错误码**：不同嵌入模型产出的向量处在**不同的向量空间**，拿 A 模型的查询向量
去和 B 模型的库中向量算余弦距离，得到的是没有意义的数字——而且**不会报任何错**，
只会让检索结果变得不可解释。它的处置动作（重建索引）与 10009（查 PostgreSQL 容器）完全不同。

**一个刻意的顺序**：这个校验放在**调用嵌入接口之前**。否则要先花一次嵌入调用的钱，
才拿到一个注定没用的查询向量。单元测试专门断言了这一点（`verify(embeddingService, never()).embed(...)`）。

## 六、两条路的降级是不对称的（刻意的）

| | 依赖 | 嵌入服务挂掉时 |
|---|---|---|
| 向量路 | 嵌入服务 + 向量库 | **不可用** |
| 关键词路 | 向量库 | **仍然可用** |

这不是巧合而是设计：一条路断了另一条还能给出结果，合并层才"有的可合"。
单元测试 `keywordPathStillWorksWhenEmbeddingIsDown` 直接断言了这一点。

## 七、参数取值

| 参数 | 取值 | 依据 |
|---|---|---|
| `top-k` | 5 | 语料 26 条切片；合并后还要取前 3 条给出依据。每路 5 条既给合并层挑选余量，又不会把明显不相关的内容带进来 |
| `keyword-min-score` | 0.0 | 用 `>` 比较，因此等价于"至少得有一个字符三元组命中"。**不能省掉这个门槛**：否则每路都返回满 K 条、其中一堆分数为 0，会把合并结果一起污染（见第八节） |

`topK` 由配置注入而不是方法参数：调用方（第7天的合并层）不需要、也不应该自己挑这个数。

## 八、本次暴露的一个问题：关键词路的排名几乎没有信息量（留给第7天）

从第二节的三组实测可以看到一个规律：**关键词路的分数大量并列**。

| 查询 | 关键词路分数分布 |
|---|---|
| `重复扣款如何申请退款` | #1 = 0.3636，#2~#5 全是 0.1818 |
| `钱被扣了但订单没出来` | #1~#4 全是 0.0909 |
| `我的账号登不进去了，怎么办` | #1~#3 全是 0.1429（且都无关） |

**这对第7天的融合有直接影响**：RRF 的核心是"**只用排名，不用分数**"，前提是**排名本身携带相关性信息**。
而关键词路在并列时的顺序是由 tie-break（`source_file, chunk_index`）决定的——那是**字典序，不是相关性**。
把这些名次当作信号喂给 RRF，等于**把噪声当信号**。

第7天需要处理的三个具体点：

1. **并列要给相同名次**（dense rank），而不是让字典序把并列项拆成不同名次；
2. 关键词路在"零字面重合"的查询上会返回**有分数但毫不相关**的结果（证据一），
   需要考虑提高 `keyword-min-score` 或对结果做相关性下限过滤；
3. 融合结果要能看出"这条主要靠哪条路进来的"，否则无法解释。

**本次不处理**：这三件事都属于"合并"这一步的设计，应该在第7天与 RRF 一起决定，
而不是在检索层打补丁。

## 十、已知限制与遗留

| 序号 | 问题 | 影响 | 建议处理时机 |
|---|---|---|---|
| 1 | 关键词路排名信息量低（大量并列） | RRF 融合时可能把字典序当相关性 | **第7天**，见第八节 |
| 2 | 关键词路在零字面重合的查询上返回无关结果 | 会污染融合结果 | **第7天**，考虑抬高门槛 |
| 3 | `kw` 检索全表打分，用不上 trgm 索引 | 26 条无影响；语料上千条时会有延迟 | 语料扩充后加"先过滤再排序" |
| 4 | 未采集检索耗时以外的指标（如每路的命中率） | 无法回答"两路各自的贡献" | 第5周评估集（章程第5周任务2） |
| 5 | 未做检索结果去重 | 同一小节的多个切片可能同时进入结果 | 第7天合并时一并处理 |
| 6 | 未设置相似度下限（向量路） | 库里没有相关内容时仍会返回 K 条低分结果 | 第5周置信度阈值（章程第5周任务3） |
| 7 | 未限制查询长度 | 超长查询会原样送去嵌入，成本随长度增长 | 第5周评估时统一处理（分类侧已有 2000 字截断的先例） |
