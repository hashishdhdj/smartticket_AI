## 一、本次决策事项

| 序号 | 决策事项 | 结论 |
|---|---|---|
| 1 | 语料从哪来 | 自造**演示语料**，并在每份文件与文档中显式声明，不冒充真实数据 |

## 二、语料必须是"演示语料"，且必须明说

本项目**没有**可用的真实 FAQ 与历史工单数据。

**为什么要造语料**：第4~5周的任务是"切分 → 向量化 → 检索 → 合并结果（含效果评估）"。
检索链路的每一步都只有在**有可检索文本**时才谈得上验证——没有语料，切分器切什么、
检索器召回什么、第5周的效果评估评什么，全都无从谈起。所以语料是**链路的前置条件**，
不是可选项。

**为什么反复声明"演示语料"**：这些文本是**按通用客服知识构造的**，不是从真实工单里导出的。
把构造内容当真实数据陈述，是**事实性错误**——它会污染项目文档、面试表达与效果评估的结论。
因此三处强制标注：

| 位置 | 标注内容 |
|---|---|
| 每份语料文件的前言 | 「语料性质：演示语料，不含任何真实用户信息」 |
| `knowledge/README.md` | 语料性质、目录约定、格式要求 |
| 本决策记录 | 本条 |

**代价与后续**：演示语料只能证明"链路通了"，**不能**证明"检索质量好"——
质量取决于真实语料的分布与措辞。将来接入真实 FAQ 时，整个 `knowledge/` 目录可整体替换，
切分与检索代码不依赖具体内容（这也是把语料放在 classpath 资源里、而不是硬编码进代码的原因）。

## 三、为什么用 Markdown + `##` 作为切片边界

三种可选方案：

| 方案 | 问题 |
|---|---|
| 固定字符数滑窗 | 中文没有空格分词，机械切分极易把一句话劈成两半，**前半句与后半句各自都检索不到完整语义**，召回质量直接受损 |
| 按 token 数切 | 需要先接 tokenizer，与后续向量模型绑定；且同样不解决"切断句子"的问题 |
| **按语义结构切（本次采用）** | 需要语料本身有结构 |

语料是我们自己写的，因此可以让它**天生带结构**：一条 FAQ = 一个 `##` 小节，
一条历史工单 = 一个 `##` 小节。这样"切片单元"与"知识单元"一一对应，
切分器不需要理解语义，只需要认标题。

另外，`##` 是**深度优先于**段落与句子的第一级边界：小节内部再长才退化到下一级。
这与人类阅读 FAQ 的方式一致——先按问题找，再按段落读。

## 四、三级退化与参数取值

### 4.1 切片长度上限 500

```text
1. ## 小节           → 一个逻辑单元
2. 空行段落          → 小节超长时按自然段聚合装箱
3. 句末标点 。！？；   → 段落仍超长时断句，不在句子中间切
   （兜底）           → 单句本身就超长时按字符硬切
```

取 **500** 的依据是**实测语料规模**，而不是"参数看起来专业"：

- FAQ 的一条问答通常 150~350 字，一条历史工单 250~450 字；
- 取 500 可以让**绝大多数小节整节一个切片**，不被切开——**切不开就不会丢语义**；
- 500 字（中文约 500~700 token）在向量模型输入上限内，检索时也不会因片段过长而稀释语义重点。

**这个取值是被验证过的**：实际加载 7 份语料共 **26 个切片**，
而 7 份文件的 `##` 小节数恰好也是 **26**（FAQ 5+4+4+4 = 17，工单 3+3+3 = 9）。
切片数 == 小节数，说明**没有任何小节触发退化切分**——500 这个值对当前语料是"不切开"的。

### 4.2 重叠长度 80，且必须从完整句子开始

同一小节被切成多块时，后一块的开头带上前一块结尾的一小段。这是 RAG 的常规做法：
一个完整的论述可能跨在切分点上，重叠能让边界处的语义在两块里都完整出现。

取 **80** 约等于一到两句话：足以覆盖"跨切分点的半个论述"，又不会让相邻切片内容重复到互相抢排名。

**为什么重叠必须从完整句子开始**：直接按字符截尾会得到从半句开始的片段，
作为上下文既不通顺，还可能因为截断而改变原意。实现上从句首向后扫，
取**范围内最长的合法句子边界**作为起点；只有整块都找不到边界时（例如超长单句被硬切的结果），
才退化为按字符截尾——有重叠总比没有好，但这种情况应当少见。

### 4.3 一个被测试抓出来的 off-by-one（踩坑记录）

切片长度上界定义为 `MAX_CHUNK_CHARS + OVERLAP_CHARS = 580`。但首轮实测是 **581**。

**根因**：重叠正文与后一块之间还要插一个换行符，
"重叠 80 + 换行 1 + 正文 500 = 581"。重叠预算没有把拼接符算进去。

**修复**：`overlapOf` 内把预算先扣 1（`int budget = OVERLAP_CHARS - 1`）。

**教训**：**"上限"必须连同拼接开销一起核算**。凡是在长度预算之外还要加分隔符的地方，
都存在同类偏差；这类偏差不会让程序报错，只会让边界断言失败——
而这个断言（`chunk.content().length() <= MAX + OVERLAP`）正是靠"把上界写成可执行的断言"才抓到的。

## 五、重叠只在同一个小节内部

**不跨小节、不跨文档**。

若允许跨小节重叠，会把两段不相关的内容粘在一起——例如"如何重置密码"的结尾
接上"重复扣款如何退款"的开头。这会**制造出本来不存在的语义关联**：
检索时该切片的向量落在两个主题之间，可能同时被两类问题召回，也可能两类都召不准。
RAG 里这类"看起来能跑、实际更差"的改动最难发现，因此直接把边界钉死在实现里。

**代价**：小节边界处的上下文连续性略弱于理想情况。可接受——
`##` 小节本身就是语义完整的单元，边界外本来就不需要额外上下文。

---

## 六、文档前言不参与切分

一级标题 `#` 作为文档标题存入元数据；**一级标题与第一个 `##` 之间的内容被丢弃**。

语料各文件开头都有"语料性质：演示语料"的声明，它属于**给人看的元信息**。若被切成切片：

1. **污染检索**：用户问"如何重置密码"却召回一段声明；
2. **浪费向量**：占一条向量记录、并在排序时挤掉真正有用的内容。

**这条约定被逐条检查**：`KnowledgeCorpusLoaderTest.disclaimerNeverAppearsInAnyChunk`
对**全部**切片做包含性断言（而非抽查），保证以后新增语料时声明不会漏进正文。

## 七、扫描范围与顺序：白名单 + 排序

### 7.1 只扫 `faq/` 与 `tickets/`，不递归整个 `knowledge/`

语料根目录下有 `README.md`（说明语料性质与格式约定）。若递归扫描整个 `knowledge/`，
那份说明会被当成知识库内容检索出来——用户问"如何重置密码"却召回"本目录文件均为演示语料"。

**为什么用目录结构而不是"文件名排除列表"**：排除列表要维护（新增一个说明文件就得记得加进去），
而目录边界一旦定下就自然生效。这也是 `README.md` 放在语料根目录、而非某个子目录里的原因。

### 7.2 排序保证可复现

`classpath*:` 通配扫描返回的资源顺序**不作保证**（取决于文件系统或 jar 内的条目顺序）。
不排序的话，同一份语料在不同机器上切出的切片顺序可能不同，
于是向量库里的 id 与内容对应关系会漂移，"可复现"就无从谈起。

这里按**文件路径**排序（配合每份文档内 `chunkIndex` 递增），
保证给定同一份语料必得同一份切片序列。测试 `loadingIsDeterministic`
直接断言"两次加载结果完全一致"。

**为什么这条重要**：第5周要把切片写入 pgvector。如果同一份语料每次加载产生不同顺序，
那么"重新灌一次库"就会得到不同的向量行，**评估结论无法复现**，问题也无法定位。

## 八、切片元数据设计

```java
record KnowledgeChunk(String sourceFile,   // faq/01-账户问题.md
                      String sourceTitle,  // 账户问题 FAQ
                      String sectionTitle, // 如何重置登录密码
                      int chunkIndex,      // 文档内从 0 连续递增
                      String content) { }  // 正文
```

**为什么四项都要**：

- `sourceFile` + `sectionTitle`：章程约束"检索结果必须可追溯来源"，
  第5周的返回结构要求给出 `sourceDocuments[{title, score, summary}]`；
- `sourceTitle`：给人看的文档级标题（"账户问题 FAQ"比"faq/01-账户问题.md"更易读）；
- `chunkIndex`：同一小节被切成多块时用于**还原顺序**，也便于排查"某块切歪了"。

已提供 `sourceRef()`（`文件 # 文档标题 > 小节标题`）作为日志与调试用的单行来源串。

**文档标题取不到时回退为文件名**（去掉 `.md`）：来源信息**永不为空**。
元数据缺失在 RAG 里是"检索到了但说不清出处"，等于把可追溯性悄悄降级，因此宁可回退也不要留空。

**语料规模（实测）**

```text
[知识库规模] 切片总数=26 | FAQ 切片=17 | 历史工单切片=9 | 涉及文档数=7
[INFO] KnowledgeCorpusLoader -- 知识库语料加载完成 | 文件数=7 | 切片数=26 | 平均每份文件切片数=3.71
```

**全量回归**

```text
[INFO] Tests run: 172, Failures: 0, Errors: 0, Skipped: 2
[INFO] BUILD SUCCESS
```

本次新增 20 个用例：

| 测试类 | 数量 | 验证的层次 |
|---|---|---|
| `KnowledgeChunkerTest` | 14 | 切分规则：按小节切、前言排除、文件名回退、元数据完整、超长切多块、不在句中断开、重叠从完整句开始、重叠不跨小节、首块无重叠、超长单句硬切、空小节跳过、无小节返回空、null/空输入、HTML 注释剥离 |
| `KnowledgeCorpusLoaderTest` | 6 | 语料质量：能加载到、元数据完整、只扫两个子目录（断言无 `README.md`）、**逐条检查声明不外泄**、序号连续、两次加载结果一致 |

两个测试类都**不需要 Spring 上下文**（切分器是无状态纯函数，加载器只依赖 classpath 资源），
因此不依赖 Docker，可随时单独跑：

```powershell
mvn test -Dtest=KnowledgeChunkerTest,KnowledgeCorpusLoaderTest
```

**为什么切分要测这么细**：切分是 RAG 里"错了很难发现"的一环——
切坏了不会报错，只会在检索时表现为"明明有这条知识却召不回来"。因此这里不测"能跑"，
而是把每条切分规则都钉死。

## 十、已知限制与遗留

| 序号 | 问题 | 影响 | 建议处理时机 |
|---|---|---|---|
| 1 | 语料是演示数据 | 只能证明链路通，不能证明检索质量好 | 接入真实 FAQ 时整体替换 |
| 2 | 语料仅 26 个切片 | 规模小，召回率/排序指标的统计意义有限 | 第5周评估时若需要，扩充到 50+ |
| 3 | 三级退化中的"段落级"未被真实语料触发 | 第2级分支仅由单测覆盖，未在真实语料上跑到 | 语料扩充后自然覆盖 |
| 4 | 未做中文分词 | 关键词检索若按词匹配，需在第7周任务中确定分词方案 | 第5周（关键词检索） |
| 5 | 未处理表格、代码块 | 当前语料不含这两类结构；若将来加入，切分器会当成普通段落 | 出现时再处理 |
| 6 | 500/80 为经验值 | 未做过参数扫描（没有评估集） | 第5周建立评估集后回测 |
| 7 | 硬切分支会切断语义 | 只作为最后兜底，当前语料未触发 | 观察第5周是否出现 |
