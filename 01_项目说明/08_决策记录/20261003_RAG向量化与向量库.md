## 二、嵌入模型：DeepSeek 用不了，这不是猜的

阶段2 第1天选 DeepSeek 做对话模型时，顺带会有一个自然假设："接一家厂商就够用了"。
**这个假设是错的**：DeepSeek 只提供对话模型，没有 embeddings 端点。

不是查文档得出的结论，是**实测**（用项目里已配好的真实 DeepSeek 密钥发两个请求）：

| 探测 | 结果 |
|---|---|
| `GET https://api.deepseek.com/v1/models` | **HTTP 200**，返回的模型列表只有 `deepseek-flash`、`deepseek-v4-pro`，**没有任何嵌入模型** |
| `POST https://api.deepseek.com/v1/embeddings` | **HTTP 404** —— 端点不存在 |

**为什么值得记这一条**：网络上关于"DeepSeek embedding"的文章不少，其中混着第三方代理服务的广告
（把自家代理包装成"DeepSeek 的 embedding 模型"）。只看搜索结果会做出错误决策。
**判断"某厂商有没有某个能力"，可靠的依据是拿真实密钥打一次它的接口**，而不是看文章。

### 选型：阿里云百炼 text-embedding-v4

| 候选 | 评估 | 结论 |
|---|---|---|
| 阿里云百炼 `text-embedding-v4` | 国内直连；OpenAI 兼容端点，换厂商只改两行配置；维度可选 2048/1536/**1024**/768/512/256/128/64；开通后有 100 万 token 免费额度 | **采用** |
| 本地 Ollama + bge-m3 | 零 Key、零费用、离线，从"防泄漏"角度最优 | 否：需再拉 2~3 GB 镜像与模型，且本机 Docker 引擎本就不稳（第5天当天才第 10 次停） |
| 智谱 `embedding-3` | 国内直连，可用 | 否：无相对优势，且需另开一个平台账号 |
| OpenAI `text-embedding-3-small` | 维度 1536 | 否：需海外网络环境 |

**维度选 1024 的理由**：它在 v4 支持的维度里属于默认值，且与本地 bge-m3 的维度一致——
万一将来换成离线模型，**表结构不用动**。这一点在第8条"维度写死"里很重要。

**与对话模型分开配置**：嵌入用 `smartticket.vector.embedding.*`，对话用 `spring.ai.openai.*`，
两者 base-url 与密钥完全独立。这不是为了好看，而是因为"一个厂商同时提供对话与嵌入"在本项目不成立，
共用一个客户端就必须二选一，只能拆开。

### 接入时踩的坑：base-url 不能带 `/v1`（实测 404）

第一次配好密钥后调用直接返回 **404**。排查过程与结论：

| 直接 HTTP 探测（用同一把密钥、同一个 body） | 结果 |
|---|---|
| `POST https://dashscope.aliyuncs.com/compatible-mode/v1/embeddings` | **200**，正常返回向量 |
| `POST https://dashscope.aliyuncs.com/compatible-mode/v1/v1/embeddings` | **404** |

原因是 Spring AI 的 `OpenAiApi.Builder` **把完整路径写成了默认值**（从类常量池实证）：

```text
#25 = Utf8  /v1/chat/completions
#30 = Utf8  /v1/embeddings
```

它会把 `/v1/embeddings` 整个拼在 base-url 之后。所以 base-url 必须是**不带 `/v1` 的主机根地址**：

```text
✗ https://dashscope.aliyuncs.com/compatible-mode/v1      → .../v1/v1/embeddings → 404
✓ https://dashscope.aliyuncs.com/compatible-mode          → .../v1/embeddings    → 200
```

**为什么容易踩**：厂商文档里给的 base_url 是 `.../compatible-mode/v1`，照抄最自然。
而本项目对话侧的 DeepSeek 恰好填的是不带 `/v1` 的 `https://api.deepseek.com`——
**同一个约定，但两个厂商的文档写法不同**，很容易只在一边踩到。
这一点已写进 `application.yml`、`KnowledgeVectorProperties` 与 README 三处注释。

**更可靠的排查手法**：不要猜框架拼了什么路径，**用同一把密钥直接打两个候选 URL**，
一次就能区分"路径错"和"密钥错"——本例中 401 与 404 的处置方向完全不同。

## 三、为什么另起 PostgreSQL，而不是把向量塞进 MySQL

MySQL 8.0 **没有向量类型，也没有向量索引**。若硬把向量存成 `JSON`/`BLOB`：

- 检索只能**全表扫描 + 应用层算余弦相似度**。26 条时看不出问题，几千条时延迟不可接受；
- 无法利用 ANN 索引，也没有 `ORDER BY embedding <=> ?` 这种"把排序下推给数据库"的能力。

而 **pgvector 是 PostgreSQL 的扩展，扩展不能跨数据库安装**——所以不是"给 MySQL 加个插件"，
只能是两个数据库并存。这正好也符合"一个存储做一件事"：

| 存储 | 存什么 | 为什么 |
|---|---|---|
| MySQL | 工单、操作日志 | 事务、状态机、分页筛选是它的强项 |
| PostgreSQL + pgvector | 知识库切片与向量 | 向量类型 + ANN 索引是它的强项 |

**代价**：多一个容器、多一套凭据、多一条连接。**接受**：这是能力边界决定的，不是架构偏好。
**没有做的**：没有把工单表迁到 PostgreSQL（那会动到阶段1 全部已稳定的数据访问与 36 个接口测试，
收益为零）。

## 四、第二个数据源怎么接（本次最容易出错的地方）

Spring Boot 对数据源的自动配置带 `@ConditionalOnMissingBean(DataSource.class)`：
**容器里一旦出现任何 `DataSource` bean，MySQL 那一个的自动配置就会整体退让。**

所以"顺手加一个给 PostgreSQL 用的 `DataSource` bean"会直接顶掉 MySQL 数据源，
而 MyBatis-Plus、事务管理器、`JdbcTemplate` 全都依赖它——**整个阶段1 会塌**。
常规解法是手工声明 MySQL 数据源并加 `@Primary`，但那样必须复刻 `DataSourceProperties`
+ `@ConfigurationProperties("spring.datasource")` + `spring.datasource.hikari` 的一整套绑定逻辑，
包括那个防雪崩的 `connection-timeout: 5000`（依据 DEF-002）。为一个新功能去改主数据源的装配，风险与收益不匹配。

**本次做法**：`KnowledgeVectorRepository` 在构造期自己 `new HikariDataSource(...)`，
连接池是**普通字段**，不向容器暴露任何 `DataSource` / `JdbcTemplate` 类型的 bean。

| 维度 | 标准多数据源配置 | 本次做法 |
|---|---|---|
| 对主数据源的影响 | 需改为主数据源手工声明，改动面大 | **零影响** |
| 连接池是否由 Spring 管理生命周期 | 是 | 否（用 `@PreDestroy` 手工 close） |
| 是否符合"规范做法" | 是 | 略偏，但对本项目是正确取舍 |

**两个关键参数**：

```java
hikariConfig.setInitializationFailTimeout(-1);
```

默认值（1ms）会让容器**在应用启动阶段**就去连一次 PostgreSQL，连不上直接启动失败——
那就变成"没起 PostgreSQL 就跑不起来服务"，违背本项目「AI/RAG 是可选增强」的一贯约定。
设为 `-1` 后，连接失败被推迟到真正读写向量库的那一刻，再由上层降级。

```java
hikariConfig.setMaximumPoolSize(4);
```

向量库只在"建索引"与"检索"两处被访问，频率远低于业务库。池子开大只是白占 PostgreSQL 的连接数。

**验证**：加了这个数据源之后，应用启动耗时 3.061 秒、`TicketApiTest` 36 个用例全绿、
工单接口与 AI 分析接口实测均返回 200——主数据源确实没被动过。

## 五、不用 Spring AI 官方 PgVectorStore，手写 SQL

官方 `spring-ai-starter-vector-store-pgvector` 能用，代码量也更少。没用的理由是三条具体的：

| 理由 | 说明 |
|---|---|
| 章程第4周任务 6/7 要求「**实现**向量检索」与「**实现**关键词检索」 | 用 `similaritySearch()` 是"调用"，写 `ORDER BY embedding <=> ? LIMIT k` 是"实现"。关键词检索更是任何现成 VectorStore 都不提供，必然要自己写 SQL——那不如两边用同一套访问方式 |
| **幂等控制** | 需要按 `content_hash` + `model` 跳过未变化的切片，避免重复调用按量计费的嵌入接口。官方 store 的 upsert 不提供"内容没变就不重算"这一层 |
| **不引入新依赖** | 官方 starter 会连带引入它自己的建模与配置，而本项目只需要一张表和几条 SQL |

**代价**：需要自己处理向量参数的类型（见第九节）、自己建索引、自己写 upsert。
**接受**：这些正是第6~8 天要做的事，提前一天面对比第6 天补要好。

## 六、索引什么时候建：默认不建

`smartticket.vector.index-on-startup` **默认 false**，需显式打开：

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--smartticket.vector.index-on-startup=true"
```

**为什么不默认建**：这个动作会**调用外部接口且按量计费**，并依赖 PostgreSQL 容器。
把它设成启动必经步骤，等于让"能不能启动"取决于"嵌入服务今天是否可用"——
与阶段2「AI 失败不影响主流程」的验收标准冲突。

**为什么不用"加个接口手动触发"**：章程没有这个需求，本项目也一直遵守"不擅自新增接口"。
启动开关 + 幂等已经能覆盖"建立/刷新索引"这个真实需要。

## 七、幂等有两个条件，不是只有一个

判断"这条切片要不要重新向量化"，必须同时看两件事：

| 条件 | 不看会怎样 |
|---|---|
| 正文的 SHA-256 变了 | 语料改了却不重算，检索到的是旧内容 |
| 生成该行向量的**模型名**变了 | 换嵌入模型后正文一个字没变 → 哈希相同 → 判为"无需更新" → 库里**同时躺着两个模型产出的向量** |

第二个条件是本轮实现时补上的。**不同模型的向量空间不可比**，混在一起检索的结果无法解释，
而且**整个过程不会报任何错**——这类"静默的正确性问题"比报错难查得多。
把 `model` 列纳入比对后，混装在结构上就不可能发生。

**为什么用哈希而不是直接比对全文**：哈希定长 64 字符，可建索引、比较廉价，
并且本身就是一个可读的"内容指纹"，排查时能直接看出"这行是不是最新的"。

## 八、表结构：三处刻意的设计

```sql
CREATE TABLE knowledge_chunk (
    id            BIGSERIAL    PRIMARY KEY,
    source_file   VARCHAR(255) NOT NULL,
    source_title  VARCHAR(255) NOT NULL,
    section_title VARCHAR(255) NOT NULL,
    chunk_index   INTEGER      NOT NULL,
    content       TEXT         NOT NULL,
    content_hash  VARCHAR(64)  NOT NULL,
    embedding     VECTOR(1024) NOT NULL,
    model         VARCHAR(100) NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_knowledge_chunk_source ON knowledge_chunk (source_file, chunk_index);
CREATE INDEX idx_knowledge_chunk_embedding ON knowledge_chunk USING hnsw (embedding vector_cosine_ops);
```

**① 唯一键是 `(source_file, chunk_index)`，不是 `content_hash`**

用内容做唯一键会**跨来源去重**：FAQ 与历史工单里若有完全相同的句子，只会留下一条，
另一个来源就丢了——而"来源可追溯"要求每个来源各自留痕。
`(文件, 序号)` 才是切片的自然身份，它同时是幂等写入（`ON CONFLICT`）的依据。

**② 维度写死为 1024，并由程序二次校验**

改维度就必须改 DDL 并清表重建，因为不同维度的向量无法比较。
程序侧用 `smartticket.vector.embedding.dimensions` 校验每次返回的向量长度，
长度不符时**在写库前**就报 `AI_RESPONSE_UNPARSABLE`——
比让 PostgreSQL 抛类型错误更早，也比"写进去一半再失败"干净。

**③ HNSW + `vector_cosine_ops`**

- 余弦距离与嵌入模型的语义一致（`text-embedding-v4` 的相似度即余弦相似度）；
- HNSW 不需要预训练。IVFFlat 必须在**有数据之后**才能建索引，且 `lists` 参数选错会显著掉召回——
  当前只有 26 条切片，直接选召回质量更好的 HNSW，建索引几乎瞬间完成；
- `m` / `ef_construction` 采用 pgvector 默认值（16/64），不做无依据的调参。

**注意**：数据量很小（几十条）时，PostgreSQL 规划器很可能选择顺序扫描而不走索引
（走索引反而更慢）。这不影响正确性，索引是为语料扩充准备的。

## 九、向量怎么写入：用 PGobject，不用 `?::vector`

写 `vector` 列时，把参数拼成字符串再靠 `?::vector` 转换是常见写法，但它依赖
**服务端把该参数当作 `unknown` 处理**；一旦 JDBC 驱动把参数定性为 `varchar`，
就会报 `cannot cast type character varying to vector`。

改用驱动的 `PGobject` 显式声明类型：

```java
PGobject pgVector = new PGobject();
pgVector.setType("vector");
pgVector.setValue("[0.1,-0.2,...]");
ps.setObject(7, pgVector);
```

**代价**：`org.postgresql.util.PGobject` 是驱动里的类，所以 PostgreSQL 依赖**不能是 `runtime` scope**
（MySQL 驱动是）——运行时才可见的话编译不过。这一点已在 `pom.xml` 注释里写明，
避免以后有人"顺手"把它改回 `runtime`。

### 10.5 库里到底存了什么（用 pgvector 自己的函数读回）

```text
 rows | models |    model_name     | min_dim | max_dim | files
------+--------+-------------------+---------+---------+-------
   26 |      1 | text-embedding-v4 |    1024 |    1024 |     7

    source_file     | chunk_index |       model       | dims |  norm
--------------------+-------------+-------------------+------+--------
 faq/01-账户问题.md |           0 | text-embedding-v4 | 1024 | 1.0000
 faq/01-账户问题.md |           1 | text-embedding-v4 | 1024 | 1.0000
 ...
```

26 行、全部 1024 维、只有一个模型、来源覆盖 7 份文件。

**顺带发现：`norm = 1.0000`** —— 百炼返回的向量**已经是 L2 归一化的**。
这解释了为什么用余弦距离是合适的（归一化之后余弦距离与内积等价），
也意味着**不需要在应用侧再手工归一化一次**。

### 10.6 语义验证：向量真的带语义，不是"存了一堆数字"

不调任何接口，直接在库里算余弦距离。锚点取 `faq/01-账户问题.md` 的第 0 条
（「登录时提示「验证码异常」怎么办」），与各文件第 0 条比较：

| 余弦距离 | 切片 | 主题 |
|---|---|---|
| 0.0000 | `faq/01#0` 登录时提示「验证码异常」 | 锚点自己 |
| **0.1723** | `tickets/01#0` 登录页反复提示验证码错误，多设备均无法登录 | **账户（同一主题）** |
| 0.3941 | `faq/03#0` 页面一直转圈或白屏 | 功能异常 |
| 0.5106 | `tickets/02#0` 银行卡已扣款但订单列表中没有该订单 | 支付 |
| 0.5255 | `faq/02#0` 支付成功但订单未生成 | 支付 |
| 0.5468 | `tickets/03#0` 订单列表条数与详情页不一致 | 功能异常 |
| 0.6469 | `faq/04#0` 工单的处理流程与时限 | 工单流程 |

**同主题（验证码错误）以 0.17 排第一，与其余全部（0.39 以上）拉开了明显差距**，
而且这次匹配是**跨文档**的（faq → tickets）。

这条证据的意义：它把"向量化"从"写进去了 26 行数据"变成了"写进去的东西是有语义的"。
后者才是第6~8 天做检索的前提——如果向量没有语义，检索再怎么写都是摆设。

这也是第4天造的"FAQ 与历史工单一一对应"那份语料设计第一次体现出价值：
**同一件事的两种写法，向量确实是接近的。**

### 10.7 验证过程暴露的一个测试隔离缺陷（已修）

真实索引建好之后回看，发现集成测试`KnowledgeVectorIntegrationTest`有个**会毁掉真实数据**的问题：

它当时是对**真实语料**调 `indexAll()`，用桩嵌入模型写入 26 条**假向量**。
由于 `upsert` 的键是 `(source_file, chunk_index)`，它与真实索引**共用同一批行**——
也就是说 **`mvn clean test` 会把真实向量覆盖成假向量**。

更糟的是第二层：覆盖之后，行的 `content_hash` 与 `model` 都变成了测试桩的值。
下一次真实索引启动时，桩的 model 与真实 model 不同 → 会被判为需要更新 → 会重新算。
**所以这一层是能自愈的**，但中间那段时间库里躺的是无意义的向量，而且
`count()`、维度检查这些断言都会通过，**看不出任何异常**。

**修法**：集成测试改为在**独立的来源命名空间**（`__test__/`）里造自己的合成数据，
只测仓库层（写入 / 维度读回 / `ON CONFLICT DO UPDATE` 不产生重复行），
并在每个用例结束后按前缀删除。真实语料能否完整落库由
`KnowledgeIndexingServiceTest`（编排逻辑，mock 仓库）与真实环境的索引运行覆盖。

**为什么不让测试"跑完再恢复原状"**：它已经把真实行改成假值，恢复所需的"原值"就是被它覆盖掉的东西，
必须提前备份——那是给测试加一套数据快照机制，代价远大于收益。

**验证修复有效**：跑完整 `mvn clean test`（186 用例全绿）后复查库：

```text
 total_rows |    model_name     | model_count
------------+-------------------+-------------
         26 | text-embedding-v4 |           1     ← 真实向量未被触碰

 test_rows
-----------
          0                                       ← 测试数据已清理干净
```

**教训**：测试如果与被测数据共用同一张表和同一批主键，就要先问一句
"它跑完之后，这张表还是原来那张表吗"。这个缺陷在"测试全绿"时是看不见的。

## 十一、已知限制与遗留

| 序号 | 问题 | 影响 | 建议处理时机 |
|---|---|---|---|
| 1 | **base-url 依赖 Spring AI 的默认路径约定** | 配置填的是"主机根"，`/v1/embeddings` 由框架拼。框架若改默认路径，配置会静默失配（表现为 404） | 升 Spring AI 版本时重跑一次真实索引 |
| 2 | 未采集嵌入的 Token 消耗 | 算不出向量化成本（接口返回里有 `usage`，未取） | 第5周评估时补 |
| 3 | 未做输入脱敏 | 语料正文会发往嵌入厂商；当前语料是演示数据，风险低 | 接入真实 FAQ 前必须处理（隐私合规） |
| 4 | 孤儿行不清理 | 语料删掉某个小节后，库里那一行会留下（`upsert` 只增改不删） | 语料变更频繁时加"按文件全量对齐" |
| 5 | HNSW 索引在小数据量下不会被规划器选中 | 当前 26 条走顺序扫描，索引是"为将来准备" | 语料扩到数百条后复测执行计划 |
| 6 | 连接池生命周期不由 Spring 管理 | 用 `@PreDestroy` 手工 close；若将来需要多数据源事务会不够用 | 出现"跨库事务"需求时改回标准多数据源 |
| 7 | 索引是同步的 | 语料大时启动会被嵌入调用阻塞 | 第5周评估后若语料显著扩充，改异步 |
| 8 | 应用侧未做向量归一化 | **实测服务端返回的向量已是 L2 归一化（norm=1.0000）**，因此当前不需要。但若换一家不归一化的嵌入服务，改用内积（`<#>`）之前必须先自己归一化 | 换嵌入厂商时核对 norm |
| 9 | 部署时 `127.0.0.1` 需改服务名 | 应用容器化后连不上（同 Redis） | 阶段3（工程化/部署） |
