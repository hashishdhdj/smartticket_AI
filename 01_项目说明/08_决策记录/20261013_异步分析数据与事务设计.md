## 1. ID、版本和时间

task_id/event_id/trace_id使用服务端生成的标准UUID字符串，数据库CHAR(36)，消息String。每张新表使用BIGINT UNSIGNED自增id作为存储主键；ticket_id对应既有ticket.id。Java Long只使用正数且不超过Long.MAX_VALUE。

ticket新增version BIGINT NOT NULL DEFAULT 0，相关修改原子递增；消息inputVersion来自创建任务时的ticket.version。首版所有业务修改均使该版本变化，后台结果可以因此保守标记STALE；无需先区分内容版本与状态版本。

数据时间使用DATETIME(3)，应用/数据库配置明确同一时区，初版沿用Asia/Shanghai；occurredAt消息用带偏移ISO8601字符串。租约与调度取一致时钟，并测试过期边界。时间字段的自动填充规则在迁移/映射实现时统一，不同时混用应用和数据库默认而未说明。

任务状态：PENDING → RUNNING → SUCCEEDED/DEGRADED/FAILED/STALE；瞬时失败RUNNING → PENDING并设置next_retry_at。已终态消息不再次分析；人工重放是新任务。RUNNING过期不直接宣称成功，恢复流程必须使旧令牌失效。

首版不存正文快照：领取后读取当前工单并检查版本，不匹配直接STALE；模型调用前后都检查输入有效性。正文已改变时不会尝试还原历史正文。将来要重现历史输入再单独设计快照与数据留存。

| confidence | DECIMAL(6,5) | 可空，校验0–1，不表示已校准准确率 |

成功结果插入与任务SUCCEEDED更新同事务，使用lease_token校验领取权。FAILED/STALE/没有建议的DEGRADED只记录任务状态和原因，不为了填结果表生成伪建议。规则降级产生实际建议时才建RULE结果。

人工分类/优先级仍在ticket，AI建议不自动覆盖。查询最新结果必须检查input_version与当前ticket.version；版本不符不能当当前有效建议。

## 4. outbox_event：可靠待发送清单

| 字段 | 类型建议 | 规则 |
|---|---|---|
| id | BIGINT UNSIGNED | 自增主键 |
| event_id | CHAR(36) | NOT NULL，唯一 |
| task_id | CHAR(36) | NOT NULL，关联任务 |
| dispatch_sequence | INT | NOT NULL DEFAULT 0，同任务首次0，后续调度递增 |
| event_type | VARCHAR(64) | NOT NULL，ticket.analysis.requested |
| payload | JSON | NOT NULL，已定义7字段交接单 |
| status | VARCHAR(20) | NOT NULL，初始PENDING |
| attempts | INT | NOT NULL DEFAULT 0，投递尝试次数，与任务执行次数不同 |
| next_attempt_at | DATETIME(3) | 可空，下一次投递时间 |
| lease_until/lease_token | DATETIME(3)/CHAR(36) | 可空，防并发领取及过期投递者覆盖 |
| error_summary | VARCHAR(500) | 可空，脱敏失败摘要 |
| created_at/updated_at | DATETIME(3) | NOT NULL |

唯一键(event_id)、(task_id,dispatch_sequence)。索引(status,next_attempt_at,id)、(status,lease_until,id)。状态PENDING → SENDING → SENT；失败SENDING → PENDING，超过有界投递策略可FAILED并告警/人工恢复，不能静默丢弃。

投递失败重试同一事件，eventId不变；分析任务的下一轮业务重试创建新eventId/dispatch_sequence，taskId不变。调度器的多次扫描必须用唯一约束及条件更新防重复安排，而不只依赖“先查后插”。

## 5. 关系与事务

首版不加跨表物理外键，保持与已有工单/日志的一致风格；关联存在性、孤儿数据检查由应用和集成测试验证。此取舍不允许随意产生孤儿任务，后续清理需要按任务/事件/结果关系设计。

创建事务：工单+CREATE日志+任务+Outbox同成同败。模型/MQ均不在此事务内。

投递事务：领取+租约短事务 → 事务外发送与确认 → 令牌保护的短事务标SENT；两段之间崩溃可能重复投递，由消费者幂等承受。

消费事务：领取+令牌短事务 → 读取版本与事务外模型调用 → 短事务锁定/核对工单版本与任务领取权，插入唯一结果及终态 → 提交后ACK。工单写入与最终核对需建立可靠数据库互斥或条件验证，不能只靠一次读到旧版本的Java判断。

业务瞬时失败：更新任务PENDING/next_retry_at → 对原消息ACK，调度器到期事务内领取重试安排权并写下一条Outbox。调度中崩溃必须可恢复；同一重试只创建一个dispatch_sequence。确定性失败保存DEGRADED/FAILED，不无限重试。

重试耗尽：保存FAILED及原因；若演示死信，用明确的拒绝不重入队路由至独立DLQ，并验证DB终态与死信记录。人工重放新taskId/generation，同时记录replay_of_task_id；重放请求仍需幂等/确认保护。
