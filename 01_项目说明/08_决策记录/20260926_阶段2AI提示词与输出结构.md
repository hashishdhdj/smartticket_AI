## 二、分类受控取值（对应上游未决问题 5）

阶段1 第2天曾明确「不定义分类枚举，保持自由文本」，理由是分类诉求未明确前固化取值没有依据。**现在那个时刻到了**：阶段2 要做 AI 自动分类，如果不同时给出受控取值集合，模型的输出会变成自由文本——「账号问题」「账户问题」「登录问题」都会写进同一个字段，分类等于没做。

**采用方案**：新增 `TicketCategory`，同时供两处使用——

```text
TicketCategory.allLabels() ──┬──→ 渲染进 Prompt（告诉模型只能选这些）
                             └──→ 校验解析结果（清单外一律拒绝）
```

**边界必须说清楚**（已写进枚举类注释，并回填上游决策记录）：

> 本枚举约束的是 **AI 分类接口的输出**，不是工单表字段。
> 库里 `category VARCHAR(50)` 仍是自由文本，人工建单可以填任意分类，**没有加任何数据库约束**。

若把枚举当成表字段约束去加 CHECK 或改列类型，会与阶段1 的决策冲突（"分类诉求未明确前不固化取值"当时针对的就是表字段），也会挡住人工填写的合理自定义分类。

**为什么用中文标签而不是英文码**：与章程给出的输出示例一致；与库中人工填写的分类风格一致；且 2026-09-25 的实测中模型返回「功能异常」正落在清单内，说明中文标签的遵循度够用。**切换条件**：若第5周评估集显示模型频繁返回同义变体（如「账号问题」）导致降级率偏高，则改为英文码 + 映射表——依据是评估数据，不是感觉。

## 三、Prompt 模板的三个工程决策

### 1. 分隔符必须改成 `<>`

Spring AI 的 `PromptTemplate` 默认以 `{}` 作占位符分隔符。而**分类 Prompt 里必然含 JSON 输出示例**，示例本身就是花括号：

```text
{"category":"功能异常","priority":"HIGH",...}
```

用默认分隔符时，StringTemplate 会把 `{"category":...}` 当作占位符去解析，**在模板加载阶段就抛错**（不是渲染时才失败）。症状会很迷惑：报错指向模板语法，而模板看起来完全正常。

改用 `<>` 后花括号成为普通字符，JSON 示例可以原样写在模板里。

### 2. 版本注释在渲染时剥离

模板首行有 `<!-- prompt-version: ticket-classify-v1 -->`。它是给人看的元信息，发给模型只会白花 token、并可能干扰指令遵循，因此在 `loadTemplate` 阶段剥掉。

### 3. 分类清单从枚举渲染，不在模板里手写

模板中写的是 `<categories>` 占位，渲染值来自 `TicketCategory.allLabels()`。这样"Prompt 里加了一类、校验白名单忘了加"（以及反过来）这类漂移在结构上不会发生。

**代价**：模板不能脱离代码单独看懂（要读 `TicketCategory` 才知道有哪几类）。**接受**：可读性损失远小于两份真值漂移的代价，而且模板首行已指向本目录与决策记录。

## 四、输出结构：为什么严格拒绝未知字段

`AiClassificationParser` 对 JSON 的解析启用 `FAIL_ON_UNKNOWN_PROPERTIES`。模型多返回一个字段（例如自己加一个 `"suggestion"`）会让整次解析失败并降级。

**选择严格而非宽松的理由**：多出字段说明模型**没有按 Schema 走**。此时同一响应里的其他字段同样不可信——它可能同时把 `confidence` 理解成了百分数。静默忽略多余字段，等于把"模型开始不守规矩"这个信号吃掉；而这类漂移一旦被忽略，往往要等到线上分类结果变脏才被发现。

代价是**更脆**：模型无害地多写一个字段也会降级。**接受**：AI 分类在本项目里是"可选增强"，降级为人工的代价可控；而脏数据进入工单表后很难清理。

**唯一放宽的地方是 priority 的大小写**：Prompt 要求大写，模型偶尔返回 `high`。大小写不改变语义，为此把整次分类降级不划算，因此接受并统一转大写。归一在解析层做掉，不留给写库时——否则库里会同时存在 `HIGH` 与 `high` 两种值。

## 五、JSON Schema 与 Java 常量：两份真值如何不漂移

同一个契约现在有两份表达：给人看/给厂商看的 `ai-classification-result.schema.json`，和真正执行校验的解析器常量与枚举。**只定义 Schema 而不守护它，等于写了一份没人执行的文档。**

因此新增 `AiClassificationSchemaTest`，把"改动必须同步"变成机械检查：

| 断言 | 防的问题 |
|---|---|
| schema 的 `category` 枚举 == `TicketCategory.allLabels()`（含顺序） | 枚举加了分类，Schema 没加 |
| schema 的 `priority` 枚举 == `TicketPriority` 全部取值（含顺序） | 优先级枚举变了，Schema 没变 |
| schema 的字段集 == `AiClassificationResult` 的 record 组件 | 改了 record 字段名，Schema 没改 |
| `required` 覆盖全部 5 个字段 | 新增字段忘了设必填 |
| `keywords.maxItems` / `items.maxLength` / `reason.maxLength` == 解析器常量 | Schema 说最多 8 个，代码放宽到 10 个 |
| `additionalProperties` 为 false | Schema 说允许额外字段，与解析器的拒绝策略相反 |

## 六、真实模型验证证据

单元测试用的是我们自己构造的输入，**只能证明"解析器能处理合规输出"，证明不了"模型会产出合规输出"**。因此扩展了冒烟测试，把真实返回直接喂给解析器（`AiRealVendorSmokeTest#realModelOutputIsAcceptedByParser`）：

```text
[真实分类] promptVersion = ticket-classify-v1
[真实分类] success = true | cost = 553ms
[真实分类] 原始返回 = {"category":"功能异常","priority":"HIGH","confidence":0.95,
                      "keywords":["登录页","验证码异常","无法登录","验证码错误","换了浏览器"],
                      "reason":"用户输入正确验证码仍提示错误，且多设备多浏览器均无法登录，
                                属于核心登录功能异常，影响面广，故判为高优先级。"}
```

| 检查项 | 结果 |
|---|---|
| 不使用 Markdown 代码块包裹 | ✓ 裸 JSON |
| 字段数量与名称与 Schema 完全一致（不多不少） | ✓ |
| category 逐字取自白名单 | ✓ |
| 长度与数值约束全在界内 | ✓ reason ≈85 字、keywords 5 个、confidence 0.95 |

**全量回归**：

```text
[INFO] Tests run: 137, Failures: 0, Errors: 0, Skipped: 2
[INFO] BUILD SUCCESS
```

其中 Skipped 2 = 两个真实厂商调用测试（默认跳过，需 `AI_SMOKE=true`，避免每次跑测试都产生费用）。本次新增 30 个用例：

| 测试类 | 数量 | 验证的层次 |
|---|---|---|
| `AiClassificationParserTest` | 15 | 解析与逐项校验；每条非法输入都断言**具体失败原因** |
| `AiPromptFactoryTest` | 8 | 模板渲染（含 JSON 花括号不被吞、版本号一致、注入内容不被二次解析） |
| `AiClassificationSchemaTest` | 6 | Schema 与 Java 常量的一致性守护 |
| `AiRealVendorSmokeTest` | +1 | 真实模型的输出能被解析器接受 |

## 七、已知限制与遗留

| 序号 | 问题 | 影响 | 建议处理时机 |

## 八、Prompt 变更流程（操作规范）

Prompt 是高风险改动，一句话措辞变化就可能让输出格式崩掉。固定流程与操作细节见
`02_AI约束与规范/03_Prompt模板/README.md` 第四节，要点是：

1. 改模板正文 → 2. 改模板首行版本号 → 3. 改 `AiPromptFactory.PROMPT_VERSION`
   （第 2、3 步漏做任一步，`AiPromptFactoryTest` 会直接失败——这是刻意设计的机械检查）
   → 4. 追加版本记录 → 5. 跑单元测试 → 6. 跑 `AI_SMOKE=true` 真实验证

第 6 步不可省。第5周做评估集时，本步骤会从"单条冒烟"扩展为"批量评估"。
