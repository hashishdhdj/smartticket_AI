## 1. 结论与完成目标

当前处于“核心功能完成、工程验收通过、评审后改进”阶段。优先消除工程结构和错误契约问题，补足可解释的质量证据，再增加动态知识沉淀。已有的人工确认、数据库版本防护、可靠异步链继续保留。

### R03：统一错误契约

先写错误码到 HTTP 状态映射：参数 400、未认证 401、无权 403、不存在 404、版本/状态冲突 409、限流 429、不可恢复服务错误 5xx。合法的业务降级可以返回正常业务响应，但必须带明确 status/reason/needHuman，不能与异常混用。

采用单一响应结构约定，由统一工厂/处理器生成；ControllerAdvice 与安全 Filter 共用错误序列化逻辑，因为过滤器失败不能指望 MVC Advice 全部接管。业务原错误码尽量保留。模型输出、SQL、密钥和内部异常详情不进入对外错误。同步更新 Postman、HTTP 断言、接口说明和历史契约废弃说明。

验收：真实 HTTP 覆盖上述状态及未知异常；同类错误结构一致；权限失败不泄露对象内容；原客户端兼容影响已记录。改变错误响应的提交单独审查，不夹带业务功能。

### R04：验证已存在的可靠性，而非重复实现

1. 在真实应用装配的测试中，让模型替身阻塞；模型调用入口断言没有活动的业务事务。阻塞期间并行创建/更新其他工单，记录连接池、响应耗时和任务状态。
2. 保留数据库同版本单胜者测试，补服务层真实并发更新/指派，以及人工更新与异步结果提交竞争：冲突不能静默成功，审计不得重复，旧分析只能 STALE 或独立建议。
3. 重跑 MQ 不可用、重复投递、结果提交后 ACK 丢失、租约过期、模型重试耗尽、人工重放等已有场景；仅补当前证据没有覆盖的用例。
4. 检查 Agent 线程池容量、排队、拒绝、超时取消与身份清理。调用 Future.cancel 不代表底层 HTTP 已停止，应验证客户端超时能真正回收资源。
5. 在隔离库以有限 5/10/20 并发试验，使用延迟模型替身，报告设备、数据量、p50/p95、错误率、数据库连接和队列变化；指标用于暴露瓶颈，不据此宣布生产容量。

当前任务重试为分档退避，基础设施故障会暂停消费者等待恢复。记录上限、暂停/恢复条件、死信策略和告警查询，不将其包装为永不丢消息或完全无重复。发现锁顺序、连接池或排队问题时，再形成具体修复项并做针对性回归。

验收：模型替身阻塞时核心业务仍可用；所有写入有数据库最终防护；失败与恢复能追踪；资源开销和限制有实测证据。全程不需要付费模型。

### R05：动态知识闭环，先候选和审核，再发布

首版使用结构化解决说明 + 确定性模板 + 本地 BGE-M3，先不新增收费的 LLM 提炼。当前 resolve() 主要把 remark 保存到日志，需补充可复用解决记录的数据契约；仅“处理完毕”不足以成为知识。

建议流程：

```mermaid
flowchart LR
    T[工单解决] --> M[MySQL短事务: 解决记录和待处理事件]
    M --> O[Outbox确认投递]
    O --> Q[RabbitMQ知识处理队列]
    Q --> C[生成有版本的知识候选]
    C --> H[授权审核人脱敏和确认适用范围]
    H --> P[发布任务和Outbox]
    P --> E[事务外本地BGE-M3]
    E --> V[PG按来源版本幂等更新]
    V --> S[MySQL更新索引状态]
    S --> R[RAG可检索并显示工单知识来源]
```

关键设计：

- 首次解决只生成候选。关闭时可能是“待分配→关闭”的取消场景，不能一概当成成功案例。关闭不重复生成已解决事件。
- 增加解决记录、知识候选与发布/索引任务。候选保留 ticketId、解决版本、作者、审核人、适用范围、正文哈希、状态、来源关联和时间；不在此计划中提前固定迁移序号或过早承诺表数量。
- 候选审核状态与索引任务状态分开：DRAFT/APPROVED/REJECTED/RETRACTED；PENDING/RUNNING/INDEXED/FAILED。已有身份权限策略复用，客户端不能自行声明 APPROVED。
- 事件包含 eventType、schemaVersion、eventId、来源 ID 和版本；复用可靠投递模式，独立队列和消费者。现有 Outbox 与分析任务结构有关联，先核查耦合，选择向后兼容泛化或独立知识 Outbox；禁止直接塞入旧消费者。
- MySQL 与 PG 不能假装同一事务。PG 成功但 MySQL 回执失败时，以稳定来源键、发布版本、内容哈希幂等补偿；旧版本不得覆盖新版本，多切片替换及旧切片清理在 PG 短事务完成，嵌入计算放在事务外。
- 只发布审核后的脱敏内容；原工单描述和 TicketLog 不自动对其他角色开放。首版只允许发布为明确的共享演示知识；有私密范围但暂不支持检索 ACL 时拒绝发布，不能用 Prompt 代替访问控制。
- 动态来源使用独立命名空间。当前 KnowledgeProvenance 依赖文件来源推断，需要明确支持动态来源与适用范围，不能把工单真实经验标成“模拟 FAQ”，也不能错误宣称项目支持附件/支付等功能。
- 撤回必须停止召回；建立来源发布状态的服务端过滤/校验，保证 PG 删除延迟或失败时也不返回撤回内容。历史报告保留原始来源版本。
- 未来增加 LLM 提炼时，仅提出候选，不自动认可事实；需要新的资料外发和调用授权。当前授权的演示语料不自动涵盖未来真实工单。

最小演示：创建并解决一张合成工单 → 审核前检索不到 → 审核并发布 → 本地嵌入索引 → 换一种问法召回到该解决记录及版本 → 撤回后不再召回。可先只验收检索，无需付费生成。

故障验收至少包括：事件重复只有一个候选；未审核不可检索；跨用户审核被拒；取消关闭不产出成功知识；PG/Ollama 故障不影响结单且可恢复；回执失败不重复索引；旧消息不覆盖新版本；切片减少不残留；撤回与发布竞争无错误复活；源文本含指令不能改变权限策略。

### R06：质量复核与交付收口

148 条待人工语义复核仍是待办，代码测试和专家总体评价不能代签。先抽样检查答案正确、来源支持、模拟范围、拒答合理性，保留全部待复核数量和剩余安排；完整验收需处理全部条目或明确缩小验收范围。

冻结下一组独立问题及参考答案，再运行；旧题用于回归，新题用于检验泛化。动态知识和记忆变更后分别统计检索 Recall@k/MRR、负样本误放行、答案支持度、任务完成率和工具越权，不能混合成一个“准确率”。若新题被用于修复，它就转为回归题，另补新的独立样本。

变更后重新生成源码清单和公开 JAR，重跑包内敏感配置检查；旧 JAR 只代表旧版本。同步更新文档、执行远程 CI、演示业务链/异步链/Agent人工确认/动态知识链。本人能说明一次失败及修复、一致性边界、RRF 和双库取舍。

### R07：有限会话记忆，可选

用 conversationId + 服务端 actor 绑定，Redis TTL 与轮次/字节上限；上下文只保留摘要、引用和结构化对象 ID。历史提到工单不代表现在仍有权限，每次工具执行重查权限和版本；历史“同意”也不能替代独立确认。

同一会话并发请求使用版本或串行化机制防覆盖，覆盖跨账号访问、过期、Redis 不可用、注入、长会话截断和并发写测试。记忆和执行审计分别保存。不把模型内部推理写入记忆。

SSE 以后独立实现，优先考虑现有 Spring MVC 的异步接口；结构化回答当前依赖完整 JSON 校验，未验证的模型碎片不直接当作可信答案流出。重排器只有在独立题显示排序瓶颈时做本地/云端对照，不预设一定提升。
