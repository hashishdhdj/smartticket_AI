2026-10-23。状态：**第一步G1已经实现并通过本地验收**。维护代码位于`D:\SmartTicket-AI\.workspaces\review`；根目录的本说明仅为阅读副本，不代表原根目录源码已同步升级。

## 1. 这一步完成了什么

可以把它理解为给一线客服增加了“处理记录本”：员工回复了什么、排查时做了什么、哪些建议失败、后来怎样纠正，都能够保存下来。后续知识图谱先从这些记录中提炼经验，再经审核发布，Agent才能检索复用。

目前员工记录本已可用，知识图谱尚未建立，也没有训练DeepSeek。员工日常写记录不需要管理员逐条批准；将经验变成共享知识时才进入后续审核环节。

已交付：

| 内容 | 具体行为 |
|---|---|
| 两张真实MySQL表 | `ticket_interaction`保存回复/步骤/纠正；`experience_feedback`保存采用、有效、失败、纠正和待核实反馈 |
| 四个HTTP接口 | 追加/分页查询员工记录，追加/分页查询效果反馈 |
| 可信身份与对象权限 | 作者来自API Key；当前处理人或管理员可访问，提交人与其他处理人不能访问内部记录 |
| 并发与重试 | 相同requestId和内容重试返回原记录；冲突内容或过期工单版本被拒绝 |
| 完整纠错历史 | 错误回复不覆盖，追加纠正记录，再通过反馈关联原文与纠正 |
| 来源标记 | 合成材料明确标为AI_SYNTHETIC_DEMO，其反馈只能标为SIMULATED_DEMO |
| 可复现演示 | 12条冻结合成案例，三个随机员工身份，经真实HTTP写入隔离数据库并核对结果 |

这组接口是内部记录，不会直接给客户发消息，不是客户端聊天功能；也不会自动改变工单状态、创建知识候选、构建图关系或获得新的业务权限。

## 2. 如何实现

```text
员工携带本项目的身份凭据提交记录
→ Controller校验字段、枚举和长度，拒绝伪造身份等未知字段
→ Service开启事务，锁定当前工单行
→ 检查可信角色、当前处理人、工单版本、幂等键和纠正关系
→ Repository使用参数化SQL写入MySQL
→ 返回数据库生成的记录ID、作者、时间和工单版本快照
```

首次追加必须提交当前工单版本，避免把记录挂在已发生变化的工单上下文中。追加本身不增加工单版本；工单的指派、修改和状态流转仍由原有业务接口控制。网络超时后应保留原请求和requestId重试，不要每次重新生成UUID。

数据库唯一索引阻止重复追加，复合外键阻止跨工单关联。事务中的工单行锁保证权限检查与写入期间不会被重新指派穿插。即使原请求曾成功，工单转交后原员工再来重试，也先检查当前权限并拒绝访问。

反馈中的“有效”表示员工报告有效，不代表系统独立核实了客户问题已经解决。演示中预设的业务反馈、开发者预期与真正的程序断言分开保存。引用路径当前仅保存为待核查文本，不会自动读取文件或成为Agent可引用的已发布证据。

新功能由`smartticket.experience.enabled`控制，默认关闭。需先应用新增的`06_staff_experience.sql`，再显式启用。已有01–05迁移未被修改。开发库未自动迁移，本次使用的是隔离验收库。
