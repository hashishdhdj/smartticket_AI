# AI协作总规则

> 项目名称：AI驱动的智能工单服务系统  
> 文档版本：V1.0  
> 适用范围：本项目全部阶段、全部AI Coding会话、全部AI生成代码与文档  
> 核心原则：需求先于代码，约束先于生成，输出必须验证，过程必须留痕，错误必须复盘。

## 一、总则

1. **每次AI生成前必须明确任务边界。**
   - 必须写清楚当前阶段、任务目标、输入内容、期望输出、涉及文件、不涉及范围、验收标准。
   - 禁止使用“帮我做一个工单系统”“把项目写完整”这类模糊指令。
   - 如果边界不清楚，先让AI做需求拆解，不允许直接生成代码。
   - 每次任务边界必须记录到 `03_AI对话日志`。

2. **每次AI生成前必须给出技术栈约束。**
   - 默认技术栈：Java 17、Spring Boot 3.3.x、MyBatis-Plus、MySQL 8、Redis 7、RabbitMQ、PostgreSQL + pgvector、Spring AI、Maven、Docker。
   - 必须明确当前阶段允许实现什么、禁止实现什么。
   - 必须要求AI先复述约束，再给出方案或代码。
   - 禁止AI自行替换框架、版本、数据库或引入未确认技术。

3. **AI输出必须先保存到05_AI输出代码，再审查。**
   - 保存路径：`05_AI输出代码/raw`。
   - 审查后移动到：`reviewed`、`accepted` 或 `rejected`。
   - 命名建议：`YYYYMMDD_模块名_AI初版.java`。
   - 被拒绝的代码也必须保留原因，用于复盘和面试素材。

4. **未经审查的AI代码不得进入正式源码目录。**
   - 正式源码目录：`06_项目源代码`。
   - 只有经过人工阅读、编译验证、接口测试、边界测试后的代码，才允许进入正式源码。
   - 禁止直接复制AI输出到正式项目。
   - 禁止因为“看起来能跑”就跳过审查。

5. **AI不得擅自新增数据库字段。**
   - 任何表结构变更必须先写决策记录，位置：`01_项目说明/08_决策记录`。
   - 必须同步更新SQL脚本、实体类、Mapper、接口文档和测试数据。
   - 禁止AI在没有明确需求的情况下增加字段、索引、枚举或关联表。
   - 发现AI擅自新增字段时，必须回滚并更新禁止事项清单。

6. **AI不得擅自新增业务状态。**
   - 工单状态只能来自已确认状态机，例如：待分配、处理中、待反馈、已解决、已关闭、已挂起。
   - 禁止AI自行增加“草稿”“审批中”“已撤回”等未确认状态。
   - 状态流转必须有校验，非法流转必须被拒绝。
   - 状态变更必须记录到 `ticket_log`。

7. **AI不得引入未确认的依赖。**
   - 新增Maven依赖、Docker镜像、外部服务、AI模型服务前，必须先确认。
   - 必须记录到 `09_项目依赖与资源/01_依赖清单`。
   - 禁止引入当前阶段不需要的复杂依赖。
   - 禁止使用来源不明、长期不维护或与项目技术栈冲突的依赖。

8. **AI输出必须说明验证方式。**
   - 每次AI生成代码后，必须给出：启动方式、接口调用方式、测试命令、预期结果、异常场景验证方式。
   - 输出顺序建议：假设说明 → 设计思路 → 文件列表 → 代码 → 验证步骤 → 风险提示。
   - 没有验证方式的AI输出，不允许进入审查通过状态。
   - 必须覆盖正常流程、异常流程和边界条件。

9. **所有重要AI对话必须记录日志。**
   - 日志位置：`03_AI对话日志`。
   - 命名建议：`YYYYMMDD_主题_模型名.md`。
   - 必须记录：日期、模型、当前阶段、对话目标、输入内容、AI输出摘要、采纳情况、发现问题、下一步行动、是否更新约束。
   - 重要对话包括：需求拆解、数据库设计、状态机设计、AI分类Prompt设计、RAG调优、并发问题排查、踩坑复盘。

10. **每次踩坑后必须更新约束清单。**
   - 更新位置：`02_AI约束与规范/06_禁止事项清单.md`。
   - 同时更新：`02_AI约束与规范/01_AI协作总规则.md` 或对应阶段约束。
   - 必须在 `03_AI对话日志` 中记录踩坑过程、原因、修复方式、后续预防措施。
   - 踩坑案例可作为 `10_面试与复盘/03_踩坑案例` 的面试素材。

## 二、阶段范围约束

| 阶段 | 允许做 | 禁止提前做 |
|---|---|---|
| 阶段0 | 建目录、写章程、依赖清单、AI约束、首次需求拆解 | 写业务代码、引入复杂架构 |
| 阶段1 | Spring Boot骨架、MySQL、MyBatis-Plus、工单CRUD、基础状态机、Redis缓存、Docker Compose | RAG、MQ、复杂权限、分布式锁、前端、监控 |
| 阶段2 | Spring AI接入、AI分类、优先级推荐、RAG知识库、置信度阈值、AI评估集 | 生产级部署、多租户、模型训练 |
| 阶段3 | RabbitMQ异步、AI降级、分布式锁、缓存一致性、限流、Micrometer指标 | 复杂前端、Kubernetes、商业化计费 |
| 阶段4 | 集成测试、README、复盘、简历描述、面试话术 | 新增核心功能、范围扩张 |

## 三、标准AI协作流程

明确任务 → 编写需求描述 → 加载约束条件 → 让AI生成方案或代码 → 保存到 `05_AI输出代码/raw` → 人工逐行审查 → 编译运行验证 → 构造边界用例 → 决定采纳或拒绝 → 进入正式源码或归档 → 记录日志与复盘 → 必要时更新约束清单。

## 四、AI输出格式要求

AI每次输出必须包含：

1. 假设说明；
2. 设计思路；
3. 涉及文件列表；
4. 可运行代码；
5. 验证方式；
6. 异常处理说明；
7. 风险与未覆盖内容。

禁止：

- 用伪代码冒充可运行代码；
- 硬编码密钥、密码、Token；
- 删除已有业务逻辑；
- 修改无关文件；
- 假设某个接口已经实现；
- 跳过异常处理；
- 擅自扩大当前阶段范围。

## 五、代码审查最低清单

AI生成代码进入正式源码前，必须检查：

1. 是否遗漏原始需求；
2. 是否存在隐藏假设；
3. 是否有空指针风险；
4. 是否有并发问题；
5. 是否有事务问题；
6. 是否异常吞噬；
7. 是否有性能问题；
8. 是否有安全问题；
9. 是否违反AI约束；
10. 是否补充必要测试。

## 六、违规处理

一旦发现AI输出违反本规则：

1. 立即停止采纳；
2. 将代码移入 `05_AI输出代码/rejected`；
3. 记录问题、原因、影响范围；
4. 更新禁止事项清单；
5. 更新Prompt模板；
6. 在周报和复盘中记录；
7. 必要时作为面试踩坑案例沉淀。
